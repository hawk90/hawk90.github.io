양산이 시작되면 버그는 실험실보다 고객의 손에서 먼저 발견됩니다. bring-up 때는 문제가 생기면 디버거를 붙이고, 전압을 바꾸고, 보드를 바꿔 끼울 수 있었습니다. 필드에서는 그 어느 것도 할 수 없습니다. 고장 난 제품은 멀리 떨어진 곳에 있고, 증상은 "가끔 재부팅된다" 한 줄뿐이며, 같은 제품 수만 대 중 몇 대에서만 일어납니다.

이 장은 Ch 10에서 시작한 post-silicon 파트의 마지막 장입니다. 필드 불량을 다루는 데 필요한 네 가지, 즉 죽은 순간의 기록을 남기는 SoC ramdump, 불량 제품을 돌려받는 RMA 흐름, 개별 사례보다 집단의 패턴을 보는 통계적 triage, 그리고 칩을 물리적으로 분석하는 실패 분석(FA) 팀과의 협업을 정리합니다. 커널 크래시 덤프 자체를 분석하는 방법은 Postmortem Debugging 시리즈와 Modern Embedded Recipes의 포스트모템 글에서 다뤘으므로, 여기서는 **SoC와 제품 수준에서 데이터를 모으고 원인 영역을 좁히는 일**에 집중합니다.

## 실험실 밖의 불량

필드 불량은 실험실의 버그와 성격이 다릅니다. 가장 큰 차이는 **규모**입니다. 실험실에서는 보드 몇 장으로 같은 증상을 반복해서 보지만, 필드에서는 수만 대 중 0.1%에서만 일어나는 증상을 다룹니다. 이런 문제는 한 대를 깊이 파는 것만으로는 잘 풀리지 않습니다. 감염병이 돌 때 역학 조사관이 환자 한 명을 진찰하는 대신 환자들이 어디에 살고, 무엇을 먹었고, 언제 아프기 시작했는지를 모아 공통점을 찾는 것처럼, 필드 불량도 **집단의 패턴**에서 출발합니다.

필드 불량의 원인은 크게 네 갈래로 나뉩니다.

| 갈래 | 특징 | 예 |
|---|---|---|
| SW 버그 | 특정 펌웨어 버전·기능·사용 패턴에 몰림 | 드문 경쟁 조건, 메모리 누수 |
| 초기 불량 | 출하 후 짧은 기간 안에 발생, 특정 로트에 몰리기도 함 | 제조 결함, 조립 불량 |
| 마모·열화 | 사용 시간이 길수록 늘어남 | 납땜 접합부 피로, 회로 노화 |
| 환경 | 온도·습도·전원 품질과 상관 | 고온 지역, 불안정한 전원 |

이 중 초기 불량과 마모는 시간에 따른 고장률로 보면 잘 구분됩니다. 신뢰성 공학에서는 이를 **욕조 곡선**(시간에 따른 고장률이 처음에 높았다가 낮게 유지된 뒤 다시 올라가는 모양)으로 설명합니다.

![욕조 곡선 — 사용 초기에는 제조 결함으로 고장률이 높고, 중간에는 낮고 일정하며, 노화가 쌓이면 다시 올라간다](/images/blog/debugging/embedded/diagrams/ch21-bathtub.svg)

곡선의 어느 구간에서 불량이 몰리는지를 보면 원인 갈래를 짐작할 수 있습니다. 출하 직후에 몰리면 제조·조립 결함, 오래 쓴 제품에 몰리면 마모나 열화를 먼저 의심합니다. 신뢰성 요구가 높은 제품에서 출하 전에 칩을 높은 온도와 전압에서 일정 시간 돌리는 **번인**(burn-in, 초기 불량을 출하 전에 미리 드러내 걸러 내는 공정)을 하는 것도, 곡선의 왼쪽 구간을 공장 안에서 지나가게 하려는 목적입니다.

## SoC ramdump 수집

필드에서 제품이 죽으면, 그 순간의 상태를 남겨 두지 않는 한 아무것도 알 수 없습니다. 비행기가 블랙박스를 싣고 다니는 이유와 같습니다. 사고가 난 뒤에 무슨 일이 있었는지 알려면, 사고 전부터 기록하고 있어야 합니다. **ramdump**(시스템이 죽은 순간의 DRAM 내용을 보존했다가 나중에 꺼내 분석하는 것)는 SoC 제품의 블랙박스 역할을 합니다.

ramdump를 남기는 방법은 크게 세 가지입니다.

- **warm reset 뒤 보존된 DRAM 읽기:** watchdog 리셋처럼 DRAM 전원을 끊지 않는 리셋이라면, DRAM 내용이 다음 부팅까지 남아 있을 수 있습니다. 다음 부팅의 초기 단계에서 이 내용을 저장 장치로 복사합니다. 리셋 동안 DRAM이 내용을 유지하도록 self-refresh(컨트롤러 없이 DRAM이 스스로 내용을 유지하는 모드)로 들어가는 기능이 SoC와 보드에 있어야 합니다.
- **kdump:** 리눅스가 패닉을 감지하면 미리 준비해 둔 작은 커널로 넘어가 메모리 덤프를 저장합니다. 커널이 패닉을 감지할 수 있을 만큼 살아 있어야 합니다. 자세한 내용은 Kernel Debugging 시리즈에서 다뤘습니다.
- **pstore·ramoops:** 전체 메모리 대신 커널 로그와 패닉 메시지만 리셋에도 남는 예약 메모리 영역에 기록합니다. 용량이 작지만 가장 가볍고, 필드 제품에서 기본으로 켜 두기 좋습니다.

리눅스에서 ramoops는 device tree의 예약 메모리 영역으로 설정합니다. 아래 예시는 그 구조를 보여 줍니다. 주소와 크기는 보드마다 정해야 하는 예시 값입니다.

```text
reserved-memory {
    #address-cells = <2>;
    #size-cells = <2>;
    ranges;

    ramoops@9ff00000 {
        compatible = "ramoops";
        reg = <0x0 0x9ff00000 0x0 0x100000>;   /* 1 MiB, 예시 주소 */
        record-size = <0x20000>;               /* 패닉·oops 기록 */
        console-size = <0x20000>;              /* 직전 부팅의 콘솔 로그 */
        pmsg-size = <0x20000>;                 /* 사용자 공간 메시지 */
        ecc-size = <16>;                       /* 기록 손상 방지용 ECC */
    };
};
```

SoC 제품에서는 커널 로그만으로 부족한 경우가 많습니다. 커널이 패닉을 찍기도 전에 하드웨어 hang이나 watchdog 리셋이 일어나면 로그가 남지 않기 때문입니다. 그래서 리셋 직후 부트 단계에서 다음 정보를 함께 모아 두면 필드 분석이 훨씬 쉬워집니다.

| 수집 항목 | 어디서 얻나 | 무엇을 알 수 있나 |
|---|---|---|
| reset reason | SoC의 리셋 원인 레지스터(Ch 11) | watchdog, 전원 이상, 소프트웨어 리셋 중 무엇인지 |
| 마지막 postcode | 리셋에도 유지되는 scratch 레지스터(Ch 14) | 어느 단계까지 진행했는지 |
| 버스 timeout·에러 기록 | 인터커넥트 에러 레지스터 | hang을 일으킨 접근 주소 |
| 온도·전압 기록 | 센서 로그, PMIC 상태 | 환경 조건과의 상관 |
| 펌웨어·하드웨어 식별자 | 버전 문자열, 칩 리비전, 보드 리비전 | 집단 분석의 기준 축 |

마지막 행은 빠뜨리면 안 됩니다. 개별 덤프의 내용보다, 그 덤프가 **어떤 칩·보드·펌웨어에서 나왔는지**가 다음 절의 통계 분석을 가능하게 합니다.

## RMA 흐름과 불량 샘플

데이터만으로 원인을 못 찾으면 실제 불량 제품을 돌려받아야 합니다. 이 절차를 **RMA**(return merchandise authorization, 불량 제품을 반품받아 분석하는 공식 절차)라고 부릅니다. 택배를 반품할 때 반품 사유를 적듯, RMA에서도 제품과 함께 증상과 사용 환경 정보가 따라와야 합니다. 사유 없이 상자만 돌아오면 분석하는 쪽은 무엇을 찾아야 할지 모릅니다.

![필드 불량에서 근본 원인까지 — 불량 보고, 로그·ramdump 수집, 통계 분류, RMA 샘플 회수까지는 SW·시스템 팀이 데이터를 모으고, 재현 시험 뒤 비파괴·파괴 분석은 FA 팀이 맡아 근본 원인과 조치로 이어진다](/images/blog/debugging/embedded/diagrams/ch21-rma-fa-flow.svg)

돌아온 제품은 먼저 **재현 시험**을 거칩니다. 시스템 상태로 같은 조건을 만들어 증상이 다시 나오는지 보고, 칩 단위로는 양산 테스트 장비(ATE, automatic test equipment)에서 출하 때와 같은 시험을 다시 돌립니다. 여기서 흔한 결과가 **NTF**(no trouble found, 돌려받았지만 문제가 재현되지 않음)입니다. NTF 비율이 높다면 두 가지를 의심합니다. 하나는 시험 조건이 필드 조건(온도, 부하, 사용 시간)을 충분히 흉내 내지 못하는 경우이고, 다른 하나는 원인이 하드웨어가 아니라 SW나 시스템 통합 쪽에 있는 경우입니다.

RMA 샘플과 함께 받아야 할 정보는 다음과 같습니다.

- 증상과 발생 빈도, 처음 발생한 시점
- 가능한 경우 ramdump와 로그, reset reason
- 사용 환경(설치 장소의 온도, 전원 상태, 사용 패턴)
- 제품의 일련번호와 칩의 로트 정보(date code, 로트 번호)

## 통계적 triage — 로트·온도·사용 패턴

필드 불량 분석에서 가장 흔한 실수는 **절대 개수**만 보는 일입니다. A 로트에서 불량이 100건, B 로트에서 10건이 나왔다면 A 로트가 문제처럼 보입니다. 그런데 A 로트가 10만 개, B 로트가 1,000개 출하됐다면 불량률은 B가 열 배 높습니다. 그래서 항상 **출하량이나 가동 시간으로 나눈 비율**로 봅니다.

아래 스크립트는 불량 기록과 출하량을 결합해 로트별 불량률을 계산하고, 전체 평균보다 뚜렷이 높은 로트를 표시합니다. 입력 CSV 형식은 설명을 위한 예시입니다.

```python
import csv
from collections import Counter

def lot_failure_rates(fail_csv, shipped_csv, factor=3.0, min_fail=3):
    shipped = {r["lot"]: int(r["qty"]) for r in csv.DictReader(open(shipped_csv))}
    fails = Counter(r["lot"] for r in csv.DictReader(open(fail_csv))
                    if r["lot"] in shipped)          # 출하 기록이 없는 로트는 제외

    total_rate = sum(fails.values()) / sum(shipped.values())
    for lot, qty in sorted(shipped.items()):
        n = fails.get(lot, 0)
        rate = n / qty
        flag = "  <-- check" if n >= min_fail and rate > factor * total_rate else ""
        print(f"{lot:10s} shipped={qty:7d} fails={n:4d} rate={rate:.4%}{flag}")
    print(f"overall rate={total_rate:.4%}")

lot_failure_rates("field_failures.csv", "shipments.csv")
```

로트 말고도 같은 방식으로 볼 축이 여러 개 있습니다.

| 분석 축 | 몰리면 의심할 원인 |
|---|---|
| 칩 로트·웨이퍼·date code | 특정 시기의 제조 공정 편차 |
| 보드 리비전·조립 공장 | 보드 설계 변경이나 조립 공정 |
| 펌웨어 버전 | SW 버그 또는 설정 변경 |
| 설치 지역의 온도 | 열 마진, 열 순환 피로 |
| 가동 시간 | 마모·열화(욕조 곡선의 오른쪽) |

가동 시간 축이 결정적이었던 사례가 있습니다. 2017년 초, Intel은 실적 발표에서 Atom C2000 계열의 품질 문제를 언급했고, 비슷한 시기 Cisco 등 이 칩을 쓴 장비 회사들이 자사 제품 영향을 공지했습니다. 클럭 관련 회로가 시간이 지나면서 열화되어, 오래 가동한 장비가 재부팅 후 다시 켜지지 않을 수 있다는 내용이었습니다. 같은 칩을 쓴 NAS와 네트워크 장비에서도 비슷한 문제가 보고됐고, Intel은 보드 수준의 조치와 수정된 스테핑으로 문제를 해결했다고 밝혔습니다. 이런 결함은 출하 직후에는 전혀 보이지 않다가 가동 시간이 쌓인 뒤에야 드러나기 때문에, 가동 시간 축으로 불량을 집계하지 않으면 원인을 짐작하기 어렵습니다.

## 실패 분석 팀과의 협업

데이터와 재현 시험으로도 원인이 확정되지 않으면 칩을 물리적으로 열어 봐야 합니다. 이 일을 하는 곳이 **FA**(failure analysis, 불량 칩과 패키지를 물리적으로 분석해 원인을 찾는 일) 팀입니다. 의사가 원인을 알 수 없는 사망 사례에서 부검을 하는 것과 비슷합니다. 다만 부검처럼 한 번 열면 되돌릴 수 없으므로, 열기 전에 할 수 있는 일을 모두 해야 합니다.

FA는 보통 비파괴 분석에서 파괴 분석 순으로 진행합니다.

| 단계 | 대표 방법 | 무엇을 보나 |
|---|---|---|
| 전기적 확인 | ATE 재시험, 핀별 전기 특성 측정 | 어느 핀·블록이 이상한지 |
| 비파괴 분석 | X-ray, 초음파 현미경(SAM, 패키지 내부의 박리·공극을 초음파로 보는 장비) | 납땜 볼, 와이어, 패키지 내부 박리 |
| 결함 위치 찾기 | 발광·열 분석 장비 등 | 다이 위에서 이상 전류가 흐르는 지점 |
| 파괴 분석 | 디캡(패키지를 벗겨 다이를 드러냄), 단면 절단, 전자 현미경 | 결함의 물리적 형태 |

SW와 시스템 팀이 FA 팀에 줄 수 있는 가장 큰 도움은 **정확한 실패 조건**입니다. "가끔 재부팅됨" 같은 표현보다 "고온에서 DDR 접근이 많은 워크로드를 30분 이상 돌리면 watchdog 리셋, 마지막 postcode는 DDR 초기화 직후"처럼 구체적일수록, FA 팀은 어느 블록을 먼저 볼지 정할 수 있습니다. 재현 시험 프로그램을 함께 넘기면 더 좋습니다.

FA 결과가 칩 결함만 가리키는 것은 아닙니다. 실제로는 **EOS**(electrical overstress, 정격을 넘는 전압·전류로 생긴 손상)나 정전기 손상, 패키지 납땜 문제처럼 칩 밖의 원인이 자주 나옵니다. EOS 판정이 나오면 보드의 전원 설계나 취급 과정을 봐야 하므로, 다시 보드·시스템 팀의 일이 됩니다. 패키지와 납땜 문제가 큰 비용으로 이어진 유명한 사례가 Microsoft Xbox 360의 고장 사태입니다. 2007년 Microsoft는 고장이 잦던 Xbox 360의 보증 기간을 3년으로 늘리면서 10억 달러가 넘는 비용을 처리했습니다. 원인으로는 발열과 열 순환이 반복되면서 칩 주변 납땜 접합부에 생긴 문제가 널리 지목됐습니다. 원인 분석이 칩 설계보다 패키지·보드·열 설계 쪽으로 이어지는 경우도 많다는 점을 보여 줍니다.

## 작은 예시 — 더운 지역의 재부팅

특정 지역에서 재부팅 불량이 늘어난 사례를 데이터부터 FA까지 따라가 보겠습니다. 이름과 수치는 가상입니다.

1. **보고:** 특정 지역 고객들에게서 "가끔 재부팅된다"는 보고가 늘어납니다.
2. **데이터:** 부트 단계에서 모은 기록을 보니 reset reason은 watchdog, 마지막 postcode는 DDR 접근 구간입니다. ramoops에는 패닉 기록이 없습니다. 커널이 패닉을 찍기 전에 하드웨어가 멈춘 것으로 보입니다.
3. **통계:** 불량률을 축별로 나눠 보니 칩 로트 하나와 고온 지역에 몰려 있고, 펌웨어 버전과는 상관이 없습니다.
4. **RMA:** 돌려받은 제품을 상온에서 시험하면 NTF가 나옵니다. 온도 챔버에서 고온으로 올리자 재현됩니다.
5. **FA:** 초음파 현미경으로 보니 해당 로트의 일부 패키지에서 DDR 쪽 볼 근처에 박리가 보입니다. 고온에서 접합이 불안정해져 DDR 접근 중에 시스템이 멈춘 것으로 판단합니다.
6. **조치:** 패키지 공정을 개선하고, 출하 시험에 고온 조건을 추가하며, 해당 로트 제품을 우선 교체합니다.

이 예시에서 상온 재현 시험만 하고 NTF로 닫았다면 원인을 영영 못 찾았을 것입니다. 통계에서 본 "고온 지역" 패턴이 재현 조건을 알려 줬습니다.

## Post-silicon 파트를 돌아보며

Ch 10에서 실리콘이 도착한 첫날로 시작해, 이 장에서 고객의 손에 있는 제품까지 왔습니다. 열두 장의 흐름을 한 번에 정리하면 다음과 같습니다.

| 장 | 주제 | 핵심 질문 |
|---|---|---|
| 10 | bring-up 방법론 | 어떤 순서로 살려 내는가 |
| 11 | 전원·클럭·리셋 | 칩이 깨어나기는 하는가 |
| 12 | BootROM 정지 | ROM은 무엇을 하고 있는가 |
| 13 | SoC JTAG 접속 | 디버거가 왜 안 붙는가 |
| 14 | JTAG 없는 hang | 칩이 스스로 흔적을 남기게 하려면 |
| 15 | trace 링 버퍼 | 죽기 직전에 무엇을 했는가 |
| 16 | scan dump | 모든 길이 막혔을 때 |
| 17 | 메모리 triage | 보드냐 설정이냐 칩이냐 |
| 18 | SerDes bring-up | 물리 계층은 비트를 옮기는가 |
| 19 | HW/SW 판정 | 누구의 버그인가 |
| 20 | errata·ECO | 확정된 버그를 어떻게 다루는가 |
| 21 | 필드 불량 | 실험실 밖의 불량을 어떻게 추적하는가 |

열두 장에 걸쳐 되풀이된 원칙은 세 가지입니다. 아래 칸이 확실해야 위 칸으로 올라갑니다. 판정은 증거로 합니다. 그리고 SW와 HW가 같은 데이터를 보며 함께 일합니다.

## 정리

- 필드 불량은 규모가 크고 재현이 어려워서, 개별 사례보다 집단의 패턴에서 출발합니다.
- 욕조 곡선의 어느 구간에 불량이 몰리는지 보면 제조 결함과 마모를 구분하는 단서가 됩니다.
- SoC ramdump는 제품의 블랙박스입니다. warm reset 뒤 DRAM 보존, kdump, pstore·ramoops를 상황에 맞게 쓰고, reset reason·postcode·식별자를 함께 남깁니다.
- RMA 샘플은 증상·환경·로트 정보와 함께 받아야 하고, NTF 비율이 높으면 시험 조건이나 SW 쪽을 의심합니다.
- 통계는 절대 개수가 아니라 출하량·가동 시간으로 나눈 비율로 보고, 로트·보드·펌웨어·온도·가동 시간 축으로 나눕니다.
- FA는 비파괴에서 파괴 순으로 진행하며, 정확한 실패 조건을 넘길수록 빨라집니다. 결과가 칩 밖(EOS, 패키지, 보드)을 가리키는 경우도 많습니다.
