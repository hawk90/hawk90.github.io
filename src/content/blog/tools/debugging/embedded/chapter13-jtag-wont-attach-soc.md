MCU에서 JTAG이 안 붙는 원인은 대개 배선과 설정입니다. SoC에서는 디버그 로직 자체가 꺼진 전원 도메인에 있거나, 보안 설정으로 잠겨 있거나, 클럭이 없는 경우가 더 많습니다. 배선을 아무리 다시 확인해도 소용없는 이유가 여기에 있습니다.

핀 연결, 전압 매칭, 클럭 속도, MCU의 읽기 보호처럼 MCU 수준의 점검은 [Modern Embedded Recipes의 "JTAG·SWD 안 붙을 때"](/blog/embedded/modern-recipes/part10-02-jtag-swd)에서 단계별로 다뤘습니다. 이 장은 그 점검을 모두 통과했는데도 디버거가 SoC를 다루지 못하는 경우에 집중합니다. JTAG·SWD 신호와 CoreSight 구조의 기초는 [Ch 2](/blog/tools/debugging/embedded/chapter02-jtag-swd-coresight)에서 다뤘으니, 여기서는 그 구조가 *어디서 막히는지*를 봅니다.

## MCU와 SoC의 차이

MCU의 디버그 경로는 짧습니다. 디버거가 SWD 두 선으로 칩에 붙으면, 바로 코어 하나와 메모리에 접근할 수 있습니다. SoC는 경로가 깁니다. 디버거는 먼저 DP(Debug Port, 디버거와 칩 사이의 첫 관문)에 붙고, DP를 통해 여러 AP(Access Port, 특정 버스나 영역으로 들어가는 문)를 열고, AP를 거쳐야 비로소 코어의 디버그 레지스터나 메모리에 닿습니다. 이 구조를 Arm은 ADI(Arm Debug Interface) 아키텍처로 정의합니다.

![디버거에서 코어까지 — DP, MEM-AP, 대상까지 가는 길에 디버그 전원, 디버그 인증, 코어 전원·클럭이라는 세 개의 문이 있다](/images/blog/debugging/embedded/diagrams/ch13-dap-path.svg)

큰 건물의 출입 절차를 떠올리면 됩니다. 정문(DP)을 통과해도, 층마다 출입 카드(인증)가 필요하고, 찾아간 사무실에 불이 꺼져 있으면(전원·클럭) 사람을 만날 수 없습니다. MCU는 문 하나짜리 단층 건물이고, SoC는 보안 게이트가 여러 겹인 고층 빌딩입니다.

그래서 SoC에서 "JTAG이 안 붙는다"는 말은 너무 넓습니다. 정문에서 막혔는지, 층 게이트에서 막혔는지, 사무실 앞에서 막혔는지에 따라 원인이 완전히 다릅니다. 아래 표는 막힌 위치별로 SW 쪽에서 보이는 증상과 HW 쪽 원인을 짝지었습니다.

| 막힌 위치 | SW(디버거) 쪽 증상 | HW 쪽 원인 후보 |
|---|---|---|
| DP 이전 | IDCODE를 못 읽음, 응답 없음 | 배선, I/O 전압, 신호 속도, 리셋 상태 |
| DP | IDCODE는 읽히는데 power-up 요청에 응답 없음 | 디버그 전원 도메인 꺼짐, 디버그 리셋 |
| AP | AP 목록이 비어 있거나 접근 시 에러 | 디버그 인증 차단, 보안 잠금 |
| 코어 | AP는 보이는데 코어 halt 실패 | 코어 전원 꺼짐, 클럭 게이팅, WFI 상태 |

## 진단 순서 — 네 개의 질문

막힌 위치를 찾으려면 바깥쪽부터 안쪽으로 한 단계씩 확인합니다. 각 단계는 "예/아니오"로 답할 수 있는 질문 하나로 정리됩니다.

![SoC에 디버거가 안 붙을 때의 네 질문 — IDCODE, DP power-up 응답, AP 목록, 코어 halt 순서로 확인](/images/blog/debugging/embedded/diagrams/ch13-attach-triage.svg)

첫 질문인 IDCODE(칩이 JTAG·SWD로 돌려주는 식별 번호)가 읽히지 않는다면 MCU와 같은 원인이므로 Recipes 글의 점검으로 돌아갑니다. IDCODE가 읽힌다는 것은 디버거와 DP 사이의 전기적 연결은 살아 있다는 뜻입니다. 이제부터가 SoC 고유의 문제입니다.

OpenOCD에서는 각 단계를 명령 몇 개로 확인할 수 있습니다. 먼저 설정 파일에서 SWD로 연결하도록 지정합니다. 아래는 설정 파일의 앞부분 예시이며, 칩에 맞는 target 설정은 생략했습니다. OpenOCD 자체의 사용법은 [Ch 3](/blog/tools/debugging/embedded/chapter03-openocd)를 참고합니다.

```tcl
# board.cfg 예시: 프로브와 전송 방식, 속도만 지정
source [find interface/cmsis-dap.cfg]
transport select swd
adapter speed 1000
```

OpenOCD가 시작되면 telnet 콘솔에서 DAP(DP와 AP를 묶어 부르는 이름)의 AP 정보와 코어 상태를 차례로 확인합니다.

```text
> dap info 0
> dap info 1
> targets
```

OpenOCD가 시작될 때 IDCODE를 읽고, `dap info`로 AP 번호별 정보를 확인하고, `targets`로 코어 상태를 봅니다. 어느 명령에서 에러가 나는지가 곧 막힌 위치입니다. 출력 형식은 OpenOCD 버전과 칩에 따라 다르므로, 정상 동작하는 보드에서 미리 한 번 돌려 기준 출력을 남겨 두면 비교가 쉽습니다.

## IDCODE는 읽히는데 power-up 응답이 없을 때 — 디버그 전원 도메인

SoC는 전력을 아끼려고 디버그 로직에도 전원 도메인을 따로 둡니다. 평소에는 디버그 영역의 전원을 꺼 두고, 디버거가 요청할 때만 켜는 방식입니다. ADIv5 계열 DP에는 이 요청을 위한 비트 쌍이 있습니다. 디버거가 CDBGPWRUPREQ(디버그 영역 전원 요청)와 CSYSPWRUPREQ(시스템 영역 전원 요청)를 세우면, 칩의 전원 제어기가 전원을 켠 뒤 각각의 ACK 비트로 응답합니다.

이 응답이 오지 않는다면, 디버거는 문을 두드렸는데 안에서 아무도 대답하지 않는 상태입니다. 원인 후보는 다음과 같습니다.

- **전원 제어기가 요청을 처리하지 않음:** 전원 제어 펌웨어가 아직 안 돌았거나, 디버그 전원 요청이 전원 제어기에 연결돼 있지 않은 설계 문제입니다.
- **디버그 도메인 레일이 없음:** Ch 11에서 본 전원 레일 중 디버그 영역에 공급되는 레일이 꺼져 있거나 낮습니다.
- **디버그 리셋이 풀리지 않음:** 디버그 로직이 별도의 리셋을 갖는 칩에서, 그 리셋이 계속 걸려 있습니다.

이 단계는 HW 측정과 칩 문서가 핵심입니다. 디버그 전원 도메인이 어느 레일에서 오는지, 전원 요청이 어떤 경로로 처리되는지를 칩 문서에서 찾아 HW 엔지니어와 함께 확인합니다. Co-simulation 시리즈 Ch 16의 테이프아웃 전 체크리스트에 "디버그 포트 접근"이 들어가 있는 이유가 이것입니다.

## 디버그 인증과 잠금

전원이 켜지고 AP가 보이는데 접근하면 에러가 난다면, 다음 후보는 **디버그 인증**(debug authentication, 칩이 디버거 접근을 허용할지 결정하는 장치)입니다. Arm 기반 칩에는 DBGEN, NIDEN, SPIDEN, SPNIDEN 같은 인증 신호가 있습니다. 앞의 두 신호는 일반 영역의 침입형 디버그(코어를 멈추는 디버그)와 비침입형 디버그(trace처럼 코어를 멈추지 않는 관찰)를 허용하고, 뒤의 두 신호는 보안 영역(Secure world)에 대해 같은 역할을 합니다.

이 신호들은 보통 fuse나 보안 펌웨어가 정합니다. 양산 제품은 보안을 위해 디버그를 끄는 경우가 많고, 개발 샘플은 켜 두는 것이 원칙입니다. 문제는 개발 샘플이 실수로 양산용 설정을 받거나, 보안 부팅 펌웨어가 부팅 도중 디버그를 끄는 경우입니다. 이때 SW 쪽 증상은 독특합니다. 리셋 직후 아주 짧은 순간에는 디버거가 붙는데, 부팅이 조금 진행되면 갑자기 접근이 막힙니다. 펌웨어가 중간에 문을 잠갔습니다.

칩 회사들은 이 잠금을 여러 단계로 제공합니다. 예를 들어 NXP i.MX 계열은 fuse 설정으로 JTAG을 열어 두거나, 키 기반 인증(secure JTAG)을 요구하거나, 완전히 막는 모드 중 하나를 고를 수 있습니다. 그래서 디버거가 안 붙는 샘플을 받으면, 그 칩의 디버그 잠금 모드가 무엇으로 설정돼 있는지부터 확인합니다.

진단 방법은 두 가지입니다. 하나는 리셋 직후 바로 코어를 멈추는 방법입니다. OpenOCD의 `reset halt`처럼 리셋과 동시에 halt를 걸면, 펌웨어가 문을 잠그기 전에 들어갈 수 있는 칩이 있습니다. 다른 하나는 fuse와 보안 설정 확인입니다. fuse 구조와 디버그 영구 비활성화는 [Bootloader Internals Ch 23](/blog/embedded/bootloader/chapter23-bootrom-efuse-otp)에서 다뤘습니다.

인증 문제는 보안팀과의 협업이 필요한 영역이기도 합니다. 개발 단계에서 디버그를 다시 여는 방법(인증된 디버그 잠금 해제 절차 등)이 칩마다 정해져 있고, 이 절차와 권한은 대개 별도 문서와 승인으로 관리됩니다.

## 코어가 클럭 게이팅·WFI 상태일 때

AP까지 정상인데 특정 코어만 halt가 안 된다면, 그 코어가 지금 일을 할 수 없는 상태일 가능성이 큽니다. 세 가지 경우가 흔합니다.

- **코어 전원이 꺼짐:** 멀티코어 SoC에서는 부팅 초기에 코어 0만 켜지고 나머지는 꺼져 있습니다. 꺼진 코어에 halt를 거는 것은 빈 사무실에 전화를 거는 것과 같습니다. 보조 코어가 켜지는 과정은 [Bootloader Internals Ch 33](/blog/embedded/bootloader/chapter33-smp-secondary-cpu-bringup)에서 다뤘습니다.
- **클럭 게이팅:** 전력을 아끼려고 코어나 디버그 로직의 클럭을 꺼 둔 상태입니다. 클럭이 없으면 디버그 레지스터도 응답하지 못합니다.
- **WFI 상태:** WFI(Wait For Interrupt, 인터럽트가 올 때까지 코어를 재우는 명령)로 잠든 코어는 칩에 따라 디버그 요청에도 깨어나지 않을 수 있습니다. 리눅스의 idle 루프가 WFI를 자주 쓰기 때문에, 부팅 후 디버거를 붙일 때 특정 코어만 반응하지 않는 현상으로 나타납니다.

이 경우의 단서는 "언제 붙느냐"입니다. 부팅 직후에는 붙는데 OS가 올라온 뒤에 안 붙는다면 전원 관리가 원인일 가능성이 큽니다. 리눅스라면 `cpuidle.off=1` 같은 부팅 인자로 깊은 idle 상태를 막고 증상이 바뀌는지 확인합니다. 증상이 사라지면 원인을 전원 관리로 좁힐 수 있습니다.

## 리셋을 붙잡은 채로 접속하기

부팅이 진행되면 접속이 막히는 칩이라면, 반대로 **리셋 상태에서 접속**하는 방법이 효과적입니다. 디버거가 칩의 리셋 핀을 붙잡은 채로 DP에 연결하고, 리셋을 푸는 순간 코어를 멈추게 하면 펌웨어가 한 줄도 실행되기 전에 들어갈 수 있습니다. 펌웨어가 디버그를 잠그든, 클럭을 끄든, WFI로 잠들든 그 전에 붙는 셈입니다. 문이 잠기기 전에 먼저 들어가 기다리는 것과 같습니다.

이 방법이 통하려면 보드에서 디버거가 칩의 시스템 리셋 핀(보통 nSRST)을 제어할 수 있어야 합니다. 디버그 커넥터에 리셋 핀이 배선돼 있는지 회로도에서 먼저 확인합니다. OpenOCD에서는 `reset_config`로 리셋 핀 사용 방식을 지정합니다. 아래는 리셋을 건 상태에서 접속하도록 설정하는 예시입니다.

```tcl
# 디버거가 시스템 리셋 핀을 쓰고, 리셋을 건 채로 접속한다
reset_config srst_only srst_nogate connect_assert_srst
adapter srst delay 100
```

이 설정으로 접속한 뒤 `reset halt`를 쓰면, 리셋 해제와 동시에 코어가 리셋 벡터에서 멈춥니다. 다만 모든 칩에서 통하지는 않습니다. 리셋 중에는 디버그 로직까지 함께 리셋돼 DP가 응답하지 않는 칩도 있고, 리셋 해제 뒤 BootROM이 보안 검사를 마칠 때까지 디버그를 열어 주지 않는 칩도 있습니다. 칩 문서에서 "리셋 중 디버그 접근" 항목을 확인하고, 통하지 않으면 앞의 인증·전원 진단으로 돌아갑니다.

HW 쪽에서 함께 볼 신호도 정리해 둡니다. 디버거 로그만으로 판단이 어려울 때는 아래 신호를 스코프나 로직 분석기로 동시에 보면 어느 쪽이 먼저 움직였는지 알 수 있습니다.

| 신호 | 볼 것 | 이상할 때의 의미 |
|---|---|---|
| SWDIO·SWCLK | 디버거가 보낸 요청에 칩이 응답하는가 | 응답이 끊기는 시점이 막힌 시점 |
| nSRST | 리셋이 언제 걸리고 풀리는가 | 디버거와 리셋 회로가 서로 다투는지 |
| 디버그 도메인 레일 | power-up 요청 뒤 전압이 오르는가 | 오르지 않으면 전원 제어 문제 |
| 코어 클럭 출력(있으면) | 접속 실패 시점에 클럭이 도는가 | 멈춰 있으면 클럭 게이팅 |

## 작은 예시 — 부팅 중간에 끊기는 디버거

개발 보드 한 장에서 실제로 겪을 법한 장면입니다. 디버거를 붙이면 처음에는 IDCODE도 읽히고 코어도 멈춥니다. 그런데 코어를 풀어 부팅을 진행시키면, 몇 초 뒤 디버거가 "AP 접근 실패"를 내며 연결이 끊깁니다.

네 질문으로 정리하면, IDCODE는 읽히고 DP 전원 요청도 응답합니다. 그런데 부팅이 진행된 뒤에는 AP 접근이 실패합니다. 두 번째 문인 디버그 인증에서 막혔다는 뜻입니다. 같은 보드에서 리셋 직후 halt를 걸고, 부팅 코드를 한 단계씩 실행하며 언제 끊기는지 찾아봅니다. 보안 부팅 펌웨어가 특정 지점에서 디버그 인증 신호를 끄는 설정을 실행하는 순간 연결이 끊깁니다.

원인은 펌웨어 빌드 설정이었습니다. 개발 빌드여야 할 이미지가 양산용 보안 설정으로 빌드돼, 부팅 중에 디버그를 잠그고 있었습니다. 빌드 설정을 고치자 디버거가 OS 부팅 뒤에도 연결을 유지했습니다. SW 쪽 증상은 "디버거가 불안정하다"였지만, 실제로는 소프트웨어가 의도대로 문을 잠그고 있었습니다.

## 자주 하는 실수

- **IDCODE가 읽히면 연결은 끝났다고 생각합니다.** IDCODE가 읽혔다면 정문만 통과했을 뿐입니다. AP와 코어까지 가는 길이 남아 있습니다.
- **배선만 반복해서 확인합니다.** IDCODE가 읽힌다면 배선은 대체로 정상입니다. 전원 도메인과 인증으로 넘어가야 합니다.
- **기준 출력을 남겨 두지 않습니다.** 정상 보드의 `dap info` 출력이 있으면 이상 보드와 한 줄씩 비교할 수 있습니다.
- **OS가 올라온 뒤에만 붙여 봅니다.** 리셋 직후와 OS 부팅 후를 비교해야 전원 관리와 보안 설정의 영향을 가를 수 있습니다.
- **잠금 해제를 혼자 시도합니다.** 디버그 인증은 보안 절차와 얽혀 있습니다. 칩 문서와 보안팀의 절차를 따릅니다.

## 정리

- SoC의 디버그 경로는 **DP → AP → 대상**으로 길고, 그 사이에 디버그 전원, 디버그 인증, 코어 전원·클럭이라는 세 개의 문이 있습니다.
- 진단은 **IDCODE → DP power-up 응답 → AP 목록 → 코어 halt** 순서의 네 질문으로 막힌 위치를 찾습니다.
- IDCODE가 읽히면 배선은 대체로 정상입니다. 이후 문제는 SoC 고유의 전원·보안·클럭 문제입니다.
- DP 전원 요청에 응답이 없으면 디버그 전원 도메인과 디버그 리셋을 HW 쪽에서 확인합니다.
- 부팅 중간에 접근이 끊기면 펌웨어가 디버그 인증을 끄고 있을 가능성이 큽니다. 리셋 직후 halt로 비교합니다.
- 특정 코어만 반응하지 않으면 전원 꺼짐, 클럭 게이팅, WFI를 의심하고, 리셋 직후와 OS 부팅 후를 비교합니다.
