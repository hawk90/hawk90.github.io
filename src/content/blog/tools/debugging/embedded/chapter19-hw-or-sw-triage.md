post-silicon 버그 회의에서 가장 자주 나오는 질문은 "이거 HW 버그야, SW 버그야?"입니다. 이 질문에 대한 답에 따라 담당 팀과 일정, 비용이 완전히 달라집니다. SW 버그라면 패치 하나로 끝나지만, HW 버그라면 errata를 쓰고 workaround를 만들고 다음 스테핑을 고민해야 합니다. 그래서 양쪽 모두 쉽게 "우리 쪽은 아니다"라고 말하고 싶어집니다.

Ch 10에서 세 가지 판정 질문(여러 보드 재현, 조건 민감도, 최소 코드 재현)을 소개했습니다. 이 장은 그중 판정이 가장 어려운 영역, 즉 **증상은 SW에서 보이는데 원인이 HW와 SW의 경계에 걸쳐 있는 버그**를 다룹니다. 전압·온도·주파수를 바꿔 보는 실험과 그 결과를 그린 shmoo plot, 그리고 캐시·MMU·메모리 순서처럼 HW와 SW가 함께 지켜야 하는 규칙에서 생기는 버그를 차례로 봅니다. pre-silicon 단계의 같은 질문(RTL 버그인가, 테스트벤치·모델 버그인가)은 Co-simulation 시리즈 Ch 15에서 다룹니다.

## 경계 버그가 어려운 이유

경계 버그는 국경 근처에서 벌어진 사건과 비슷합니다. 양쪽 모두 상대 영토에서 일어난 일이라고 주장하고, 실제로 양쪽에 조금씩 걸쳐 있는 경우도 많습니다. 예를 들어 드라이버가 메모리 장벽(barrier)을 빠뜨렸는데, 이전 세대 칩에서는 메모리 접근 순서가 우연히 지켜져서 문제가 없었다면 이건 누구의 버그일까요? 엄밀히는 SW 버그지만, 새 칩에서 처음 드러났으니 HW 팀이 먼저 불려 오기 쉽습니다.

경계 버그가 어려운 이유는 세 가지입니다.

- **증상과 원인이 멀리 떨어져 있습니다.** 증상은 커널 패닉이나 데이터 손상으로 나타나지만, 원인은 몇백만 cycle 전의 캐시 상태나 버스 순서에 있습니다.
- **관찰하면 바뀝니다.** 로그를 추가하거나 디버거를 붙이면 타이밍이 달라져 증상이 사라지는 경우가 많습니다.
- **양쪽 모두 그럴듯한 가설이 있습니다.** HW 쪽은 타이밍 마진이나 coherency 회로를, SW 쪽은 경쟁 조건이나 누락된 캐시 관리를 의심할 수 있습니다.

| 흔한 경계 증상 | HW 쪽 가설 | SW 쪽 가설 | 가르는 실험 |
|---|---|---|---|
| 무작위 크래시, 위치가 매번 다름 | 타이밍 마진 부족, 전원 노이즈 | 메모리 오염, 경쟁 조건 | 전압·온도·주파수를 바꿔 빈도 변화 관찰 |
| 캐시를 켜면 데이터 손상 | 캐시·coherency 회로 결함 | 캐시 관리 누락, 메모리 속성 오류 | 캐시 관리 코드를 보강해서 재시험 |
| DMA 후 가끔 옛날 데이터 | 인터커넥트의 snoop 설정 문제 | invalidate 누락 | 같은 버퍼를 non-cacheable로 바꿔 재시험 |
| 장치가 가끔 잘못된 명령 실행 | 장치 쪽 버스 순서 처리 결함 | 장벽 누락으로 쓰기 순서가 뒤집힘 | 장벽 추가 후 재시험, 버스 trace 확인 |

표의 오른쪽 열이 이 장의 핵심입니다. 판정은 논쟁이 아니라 **실험으로 증상이 어느 가설을 따라가는지 보는 일**입니다.

## 재현 조건 — 전압·온도·주파수

날씨가 흐려지면 무릎이 쑤시는 사람이 있습니다. 통증이 기압을 따라간다면 관절 상태를 의심할 근거가 됩니다. 칩도 비슷합니다. 증상이 전압·온도·주파수를 따라 변한다면 전기적 원인을 의심할 근거가 생깁니다. 이 세 가지를 묶어 흔히 **PVT 조건**(process·voltage·temperature, 칩 동작에 영향을 주는 공정 편차·전압·온도)이라고 부르는데, bring-up 랩에서 실제로 바꿀 수 있는 것은 전압·온도·주파수입니다.

| 조건 | 바꾸는 방법 | 증상이 따라오면 |
|---|---|---|
| 코어 전압 | 전원 칩(PMIC) 설정을 조금씩 올리고 내림 | 전압 마진, 즉 회로 속도가 경계에 걸려 있을 가능성 |
| 온도 | 온도 챔버나 국소 가열·냉각 장비 | 온도에 따라 회로 속도와 누설 전류가 바뀌는 영향 |
| 주파수 | PLL 설정으로 클럭을 올리고 내림 | 타이밍 경로 마진 부족 또는 SW 경쟁 조건의 타이밍 변화 |

주의할 점이 하나 있습니다. **주파수를 바꾸면 SW의 타이밍도 바뀝니다.** 클럭을 낮춰서 증상이 사라졌다고 무조건 HW 마진 문제라고 할 수 없습니다. SW 경쟁 조건도 실행 속도가 바뀌면 드러나거나 숨을 수 있습니다. 그래서 주파수는 고정하고 **전압만 바꾸는 실험**이 더 깨끗한 판정 근거가 됩니다. 전압은 회로 속도에는 영향을 주지만 SW가 보는 cycle 단위 실행 순서는 거의 바꾸지 않기 때문입니다.

또 하나, 여러 칩 샘플을 함께 봐야 합니다. 칩마다 공정 편차가 있어서 같은 조건에서도 어떤 칩은 통과하고 어떤 칩은 실패합니다. 실패가 특정 칩에 몰리면 개별 편차, 모든 칩에서 비슷하게 나오면 설계 공통 문제나 SW 문제일 가능성이 큽니다.

## shmoo plot 읽기

전압과 주파수 두 조건을 격자로 바꿔 가며 테스트를 돌리고, 칸마다 통과와 실패를 칠한 그림을 **shmoo plot**이라고 부릅니다. 등고선 지도가 한눈에 산의 모양을 보여 주듯, shmoo plot은 칩이 어떤 조건에서 버티고 어떤 조건에서 무너지는지를 한눈에 보여 줍니다.

![Shmoo plot — 주파수가 높을수록 통과에 더 높은 전압이 필요해 경계선이 대각선으로 생기고, 통과 영역 안쪽의 고립된 실패 칸은 마진이 아닌 다른 원인을 가리킨다](/images/blog/debugging/embedded/diagrams/ch19-shmoo.svg)

그림에서 읽을 수 있는 패턴은 다음과 같습니다.

| 패턴 | 의미 | 다음 행동 |
|---|---|---|
| 깔끔한 대각선 경계 | 정상적인 속도-전압 관계. 경계 위치가 곧 마진 | 규격 동작점이 경계에서 충분히 떨어져 있는지 확인 |
| 규격 동작점이 경계에 붙음 | 마진 부족. 온도나 노화로 실패 가능 | 해당 실패를 일으키는 타이밍 경로를 HW 팀이 분석 |
| 통과 영역 안의 고립된 실패 칸 | 마진과 무관한 원인. 논리 버그나 경쟁 조건 | 그 조건에서 반복 재현되는지 보고, SW·논리 쪽 가설 검토 |
| 전압과 무관하게 특정 주파수에서만 실패 | 특정 주파수 비율에서 생기는 문제 | 클럭 도메인 간 비율, 또는 SW 타이밍 의존성 의심 |
| 아무리 올려도 전부 실패 | 마진 문제 아님 | 기능 버그로 보고 최소 재현부터 |

shmoo plot을 그리는 일은 대부분 자동화합니다. 아래 코드는 그 흐름을 보여 주는 **예시**입니다. 전압·주파수 설정 함수와 테스트 실행 함수는 랩 환경에 맞게 구현해야 하는 가상의 함수입니다.

```python
def shmoo(vdd_list, freq_list, run_test, set_vdd, set_freq, repeat=3):
    grid = {}
    for f in freq_list:
        set_freq(f)
        for v in vdd_list:
            set_vdd(v)
            fails = sum(not run_test() for _ in range(repeat))
            grid[(v, f)] = fails          # 0이면 통과, 반복 중 몇 번 실패했는지 기록
            set_vdd(max(vdd_list))        # 다음 칸 전에 안전한 전압으로 복귀
    return grid

def render(grid, vdd_list, freq_list):
    for v in reversed(vdd_list):          # 위쪽이 높은 전압
        row = "".join("." if grid[(v, f)] == 0 else str(grid[(v, f)]) for f in freq_list)
        print(f"{v:5.3f} V | {row}")
    print("          " + "-" * len(freq_list) + "  (freq →)")
```

여기서 한 칸을 여러 번 돌려 실패 횟수를 기록하는 이유가 있습니다. 경계 근처의 칸은 같은 조건에서도 통과와 실패가 섞여 나옵니다. 한 번만 돌리면 이 칸을 우연히 통과로 칠할 수 있습니다. 실패 횟수를 숫자로 남겨 두면, 확실한 실패와 경계의 흔들림을 구분할 수 있습니다.

## 캐시·MMU를 켜면 죽을 때

bring-up 초반에는 캐시와 MMU(가상 주소를 물리 주소로 바꾸고 메모리 속성을 정하는 장치)를 끈 채로 시작하는 경우가 많습니다. 모든 것이 느리지만 단순합니다. 그런데 캐시를 켜는 순간 시스템이 이상해지는 일이 매우 흔합니다. 이것은 bring-up의 단골 경계 버그입니다.

캐시는 도서관 책을 복사해 책상 위에 두고 보는 것과 같습니다. 빠르지만, 누군가 원본(메모리)을 고쳐도 책상 위 복사본은 그대로입니다. CPU 혼자 쓰는 메모리라면 문제가 없지만, DMA 장치가 메모리를 직접 고친다면 CPU는 계속 옛날 복사본을 읽게 됩니다.

![캐시를 켜면 DMA 데이터가 옛날 값으로 보이는 이유 — CPU가 캐시에 복사본을 둔 뒤 DMA가 DRAM을 바꾸면 CPU는 캐시의 옛 값을 읽고, DMA 완료 뒤 invalidate해야 새 값을 읽는다](/images/blog/debugging/embedded/diagrams/ch19-dma-cache-stale.svg)

캐시나 MMU를 켰을 때 생기는 문제의 흔한 원인을 정리하면 다음과 같습니다.

| 원인 | 증상 | 어느 쪽 문제인가 |
|---|---|---|
| DMA 버퍼의 캐시 관리 누락 | 수신 데이터가 가끔 옛날 값, 송신 데이터가 가끔 깨짐 | SW(드라이버가 캐시 관리 API를 안 씀) |
| 장치 레지스터를 일반 메모리 속성으로 매핑 | 레지스터 쓰기가 사라지거나 합쳐지거나 순서가 바뀜 | SW(페이지 테이블 속성 오류) |
| 코드를 메모리에 쓴 뒤 명령 캐시를 안 비움 | 새로 올린 코드 대신 옛 코드가 실행됨 | SW(로더·부트로더) |
| 인터커넥트의 snoop·coherency 설정 누락 | 하드웨어 coherency를 기대한 장치에서 옛날 데이터 | 설정(부트 펌웨어) 또는 문서 오류 |
| 캐시·coherency 회로 자체의 결함 | 위 SW 원인을 모두 고쳐도 남는 손상 | HW |

표에서 보듯 대부분은 SW나 설정 문제입니다. 그래서 캐시를 켜서 문제가 생기면, HW 결함을 의심하기 전에 SW 쪽 규칙을 먼저 점검합니다. 리눅스 드라이버라면 DMA 버퍼를 직접 캐시 관리하지 말고 DMA API를 써야 합니다. 아래 코드는 수신 버퍼에서 흔히 보이는 실수와 고친 형태입니다. 고친 쪽에서는 DMA가 끝난 뒤 `dma_unmap_single()`이 필요한 캐시 처리를 해 주므로, CPU가 DRAM의 새 값을 읽게 됩니다.

```c
// 회피: 캐시 가능한 버퍼의 물리 주소를 그대로 장치에 넘김
buf = kmalloc(len, GFP_KERNEL);
dev_set_rx_addr(hw, virt_to_phys(buf));   /* 캐시 관리 없음 */
wait_rx_done(hw);
process(buf, len);                        /* 캐시의 옛 값을 읽을 수 있음 */

// Good: DMA API가 매핑과 캐시 관리를 맡음
buf = kmalloc(len, GFP_KERNEL);
dma = dma_map_single(dev, buf, len, DMA_FROM_DEVICE);
if (dma_mapping_error(dev, dma))
    return -ENOMEM;
dev_set_rx_addr(hw, dma);
wait_rx_done(hw);
dma_unmap_single(dev, dma, len, DMA_FROM_DEVICE);   /* CPU가 볼 수 있게 정리 */
process(buf, len);
```

SW 규칙을 다 지켰는데도 문제가 남는다면, 그때 HW 쪽을 의심합니다. 이때 좋은 실험은 문제 버퍼만 캐시 불가(non-cacheable) 속성으로 바꿔 보는 방법입니다. 캐시를 우회했더니 문제가 사라지고, 캐시 관리 코드가 올바르다는 것도 확인됐다면, 캐시나 coherency 경로의 결함을 의심할 근거가 생깁니다.

## coherency와 메모리 순서 버그

메모리 순서 문제는 경계 버그 중에서도 가장 까다롭습니다. Arm 같은 아키텍처는 성능을 위해 메모리 접근 순서를 엄격하게 지키지 않는 **약한 메모리 순서 모델**(weak memory ordering, 프로그램에 쓴 순서와 다른 순서로 다른 관찰자에게 보일 수 있는 모델)을 씁니다. 택배 두 상자를 순서대로 보내도 도착은 순서대로 오지 않을 수 있는 것과 같습니다. 순서가 중요하다면 "앞 상자가 도착한 뒤에 다음 상자를 보내라"는 표시, 즉 **장벽**(barrier)을 붙여야 합니다.

드라이버에서 가장 흔한 순서 버그는 DMA 디스크립터를 메모리에 쓴 뒤 장치의 도어벨 레지스터를 쳐서 "새 일이 있다"고 알리는 패턴에서 생깁니다. 아래 코드에서 회피 쪽은 장벽이 없는 `writel_relaxed()`를 써서, 장치가 디스크립터가 완성되기 전에 도어벨을 볼 수 있습니다. 리눅스에서 `writel()`은 앞선 메모리 쓰기가 장치보다 먼저 보이도록 순서를 보장하므로, 보통은 이것으로 충분합니다.

```c
// 회피: 디스크립터 쓰기와 도어벨 사이에 순서 보장이 없음
desc->addr = dma;
desc->len  = len;
desc->ctrl = DESC_OWN_HW;
writel_relaxed(ring->tail, hw->base + REG_DOORBELL);

// Good: writel()이 앞선 메모리 쓰기를 먼저 보이게 함
desc->addr = dma;
desc->len  = len;
dma_wmb();                                 /* addr·len이 ctrl보다 먼저 보이게 */
desc->ctrl = DESC_OWN_HW;
writel(ring->tail, hw->base + REG_DOORBELL);
```

이런 버그는 이전 세대 칩에서는 우연히 순서가 지켜져 숨어 있다가, 새 칩의 인터커넥트나 코어가 더 공격적으로 순서를 바꾸면서 드러나곤 합니다. 그래서 새 칩에서 처음 보는 무작위 손상은 HW 버그처럼 보이지만, 장벽을 보강해서 사라진다면 SW 버그입니다.

반대 방향의 사례도 있습니다. 2017년에는 Intel Skylake와 Kaby Lake 프로세서의 hyper-threading 관련 결함이 알려졌습니다. OCaml 컴파일러 개발자들이 특정 조건에서 프로그램이 무작위로 크래시하는 현상을 추적하던 것이 계기가 됐고, Debian 등 리눅스 배포판이 사용자에게 주의를 알렸습니다. Intel은 마이크로코드 업데이트로 문제를 고쳤습니다. 처음에는 컴파일러나 런타임의 SW 버그처럼 보였지만, 원인은 프로세서였습니다. SW 쪽에서 재현 조건을 끈질기게 좁혔기 때문에 HW 결함으로 확정할 수 있었다는 점에서, 이 장의 판정 흐름을 잘 보여 주는 사례입니다.

## 판정과 다음 행동

판정은 한 번의 실험으로 끝나지 않고, 증거를 모아 가며 점점 확실해집니다. 아래 표에 모은 증거에 따른 잠정 판정과 다음 행동을 정리했습니다.

| 모인 증거 | 잠정 판정 | 다음 행동 |
|---|---|---|
| 전압·온도에 따라 빈도가 뚜렷이 변하고, 경계가 shmoo에 나타남 | HW 마진 | HW 팀이 해당 경로 분석, 규격 동작점 재검토 |
| 전압·온도와 무관, SW 규칙(캐시 관리·장벽)을 고치면 사라짐 | SW | 패치, 같은 패턴이 다른 드라이버에도 있는지 점검 |
| SW 규칙을 모두 지켜도 남고, 최소 코드로 재현됨 | HW 논리 결함 의심 | pre-silicon에서 같은 시나리오 재현(Co-sim Ch 15), 확정되면 Ch 20 흐름으로 |
| 특정 칩 샘플에만 몰림 | 개별 칩 편차 | 해당 샘플 격리, 통계적으로 추적(Ch 21) |
| 재현 빈도가 너무 낮아 판정 불가 | 미정 | 재현율을 높이는 조건 탐색, 관찰 수단 추가(Ch 14·15) |

판정 회의에서는 결론보다 **증거를 먼저** 말하는 습관이 도움이 됩니다. "HW 버그 같습니다"보다 "전압을 3% 올리면 실패율이 10분의 1로 줄고, 캐시 관리 코드를 보강해도 변화가 없습니다"가 훨씬 생산적인 회의를 만듭니다.

## 작은 예시 — 두 개의 무작위 손상

같은 SoC에서 비슷해 보이는 두 문제가 나왔다고 해 봅시다. 이름과 수치는 가상입니다.

**문제 A — 네트워크 수신 데이터 손상.** 패킷 몇만 개 중 하나가 깨집니다. 전압을 바꿔도 빈도가 그대로이고, 캐시를 끄면 사라집니다. 드라이버를 보니 수신 버퍼를 DMA API 없이 넘기고 있었습니다. DMA API로 바꾸자 손상이 사라집니다. 판정은 SW입니다.

**문제 B — 특정 연산 결과가 가끔 틀림.** 몇 시간에 한 번 계산 결과가 틀립니다. 코어 전압을 조금 올리면 빈도가 크게 줄고, 낮추면 늘어납니다. shmoo를 그려 보니 규격 동작점이 경계에 붙어 있습니다. 여러 칩 샘플에서 정도만 다를 뿐 같은 경향이 나옵니다. 판정은 HW 마진이고, HW 팀이 해당 연산 유닛의 타이밍 경로를 분석합니다.

두 문제 모두 처음 증상은 "가끔 데이터가 틀린다"였습니다. 전압 실험 하나가 둘을 완전히 다른 길로 보냈습니다.

## 자주 하는 실수

- **주파수 실험만으로 판정합니다.** 주파수는 SW 타이밍도 바꿉니다. 전압만 바꾸는 실험을 함께 해야 합니다.
- **한 칩 샘플로 결론을 냅니다.** 공정 편차를 무시하면 개별 불량을 설계 결함으로, 또는 그 반대로 오해합니다.
- **캐시를 끄고 문제를 덮습니다.** 캐시를 끄면 증상은 사라지지만 원인은 그대로이고, 성능은 크게 떨어집니다.
- **장벽을 아무 데나 넣습니다.** 증상이 사라질 때까지 장벽을 뿌리면, 진짜 원인을 모른 채 성능만 잃습니다. 어느 순서가 깨졌는지 설명할 수 있어야 합니다.
- **shmoo 칸을 한 번만 돌립니다.** 경계 근처는 확률적으로 실패하므로, 반복 횟수를 정해 두고 실패 횟수를 기록합니다.

## 정리

- 경계 버그는 증상이 SW에서 보이지만 원인이 HW와 SW 사이에 걸쳐 있어서 판정이 어렵습니다.
- 판정은 논쟁이 아니라 실험입니다. 증상이 어느 가설을 따라가는지 봅니다.
- 전압·온도·주파수 중 **전압 실험**이 SW 타이밍을 덜 바꿔서 가장 깨끗한 근거가 됩니다.
- shmoo plot의 깔끔한 경계는 마진을, 통과 영역 안의 고립된 실패는 마진 외의 원인을 가리킵니다.
- 캐시·MMU를 켜면 죽는 문제는 대부분 캐시 관리 누락이나 메모리 속성 오류 같은 SW·설정 문제입니다.
- 약한 메모리 순서 모델에서는 장벽이 필요하고, 새 칩에서 처음 드러나는 순서 버그가 많습니다.
- 회의에서는 결론보다 증거를 먼저 말하고, 증거에 따라 잠정 판정과 다음 행동을 정합니다.
