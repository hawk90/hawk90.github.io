Ch 10의 bring-up 로그 예시에 이런 항목이 있었습니다. "write leveling 단계에서 byte lane 2만 실패, VDD_DDR를 올려도 변화 없음." 실제 bring-up에서 DDR은 이런 기록이 가장 길게 쌓이는 칸입니다. 첫 코드는 하루 만에 SRAM에서 돌았는데, DDR은 몇 주째 붙잡혀 있는 일이 흔합니다.

DDR 초기화와 training 단계 자체는 이미 다른 글에서 자세히 다뤘습니다. Modern Embedded Recipes의 DDR 초기화 실패 진단 글이 ZQ calibration, write leveling, gate training, walking bit 테스트를 단계별로 설명합니다. 이 장은 그 단계를 다시 설명하지 않습니다. 대신 **실패가 났을 때 그 원인이 보드에 있는지, PHY 설정에 있는지, 칩에 있는지를 가르는 방법**에 집중합니다. 메모리 bring-up이 오래 걸리는 진짜 이유는 이 판정이 어렵기 때문입니다.

## DDR이 오래 걸리는 이유

DDR 인터페이스 하나가 동작하려면 여러 주체가 각자 맞게 일해야 합니다. 칩 안의 메모리 컨트롤러와 PHY(칩과 DDR 사이에서 전기 신호를 다루는 물리 계층 회로), 패키지와 보드 배선, 종단 저항, DDR 칩 자체, 그리고 그 모두를 설정하는 펌웨어입니다. 어느 하나가 어긋나도 증상은 비슷하게 "메모리가 안 뜬다"로 나타납니다.

**DDR training**(메모리 컨트롤러가 DDR 신호 타이밍을 맞추는 초기화 과정)은 오케스트라가 공연 전에 음을 맞추는 일과 비슷합니다. 지휘자(컨트롤러)가 악기 파트(byte lane)마다 소리를 들어 보고 박자와 음높이를 조정합니다. 그런데 한 파트만 계속 박자가 어긋난다면, 연주자 탓인지, 악기 탓인지, 그 자리의 음향이 나쁜 탓인지 바로 알 수 없습니다. DDR도 같습니다. 한 lane이 실패하는 원인은 보드 배선일 수도, PHY 설정일 수도, 칩의 아날로그 회로일 수도 있습니다.

게다가 DDR 신호는 빠르고 여유가 좁아서, 작은 차이가 통과와 실패를 가릅니다. 같은 설계의 보드라도 조립 편차 때문에 어떤 보드는 되고 어떤 보드는 안 될 수 있습니다. 그래서 DDR triage는 한 번의 측정으로 끝나지 않고, **조건을 바꿔 가며 증상이 어떻게 따라오는지 보는 실험의 연속**이 됩니다.

## 실패 증상 분류 — 인식 불가·training 실패·간헐 오류

실험을 설계하기 전에 증상부터 세 갈래로 나눕니다. 갈래마다 의심할 영역이 다르기 때문입니다.

![DDR 실패 증상 분류 — 인식 불가는 전원·클럭·설정값 기본 오류, training 실패는 lane별 배선·PHY 설정, 부팅 후 간헐 오류는 마진·온도·패턴 의존을 먼저 의심한다](/images/blog/debugging/embedded/diagrams/ch17-symptom-tree.svg)

| 증상 | SW 쪽에서 보이는 것 | HW 쪽에서 확인할 것 | 먼저 의심할 영역 |
|---|---|---|---|
| **인식 불가** | 부트로더가 DDR 초기화 첫 단계에서 멈추거나 timeout | DDR 전원 레일, 기준 전압(Vref), DDR 클럭, 리셋 핀 | 전원·클럭·리셋, 또는 DDR 종류·용량 설정값 자체의 오류 |
| **training 실패** | 특정 training 단계에서 특정 lane만 실패 로그 | 해당 lane의 신호 품질, 배선 길이, 종단 저항 | lane별 보드 문제나 PHY 설정 |
| **부팅 후 간헐 오류** | 커널은 뜨지만 무작위 크래시, ECC 에러, 메모리 테스트 실패 | 온도·전압을 바꿨을 때의 변화, 마진 측정 | 마진 부족, 데이터 패턴 의존, 전원 노이즈 |

이 분류의 요점은 **증상이 얼마나 "보편적"인가**입니다. 모든 보드에서 똑같이 인식이 안 된다면 설정값이나 설계 공통의 문제일 가능성이 크고, 특정 lane이나 특정 보드에서만 실패한다면 국소적인 원인을 찾아야 합니다. Ch 10의 세 가지 판정 질문(여러 보드에서 재현되는가, 조건에 민감한가, 최소 코드로 재현되는가)을 DDR에 맞게 구체화한 셈입니다.

## 가르는 실험 — 보드 교체·설정 변경·주파수 낮추기

자동차가 달릴 때 떨림이 있으면 정비사는 앞뒤 타이어 위치를 바꿔 끼워 봅니다. 떨림이 타이어를 따라 움직이면 타이어 문제이고, 그 자리에 남아 있으면 차체 문제입니다. DDR triage의 실험도 같은 원리입니다. **무언가를 바꿨을 때 증상이 따라오는지, 남아 있는지**를 봅니다.

| 실험 | 증상이 따라오면 | 증상이 남아 있으면 |
|---|---|---|
| 같은 설정으로 다른 보드에서 실행 | 그 보드 개별 문제(조립·부품) | 설계 공통 또는 설정 문제 |
| 같은 보드에서 다른 칩 샘플로 교체 | 칩 개별 편차 | 보드나 설정 문제 |
| DDR 칩을 다른 제조사·로트로 교체 | DDR 칩 특성과의 궁합 | 컨트롤러·PHY·보드 쪽 |
| 동작 주파수를 낮춤 | 증상이 사라지면 타이밍 마진 부족 | 주파수와 무관한 기본 오류 |
| ODT·구동 세기·Vref 설정을 바꿈 | 증상이 바뀌면 신호 품질(SI) 쪽 | 설정과 무관한 원인 |
| 온도를 바꿈(가열·냉각) | 마진이 경계에 걸려 있음 | 온도와 무관한 원인 |

여기서 **ODT**(on-die termination, DDR 칩이나 PHY 안에 들어 있는 종단 저항)와 **구동 세기**(출력 드라이버가 신호를 얼마나 세게 미는지)는 신호 반사와 모양을 바꾸는 설정입니다. 이 설정을 바꿨을 때 실패 lane이 바뀌거나 통과 범위가 넓어진다면, 원인은 전기적 신호 품질에 있을 가능성이 큽니다. 이런 문제를 **SI**(signal integrity, 신호가 왜곡 없이 전달되는 정도) 문제라고 부릅니다.

실험 순서에도 원칙이 있습니다. 가장 싸고 빠른 실험부터 합니다. 주파수를 낮추거나 설정값을 바꾸는 일은 펌웨어만 고치면 되므로 몇 분이면 끝납니다. 보드나 칩을 바꾸는 실험은 준비가 필요하고, DDR 칩 교체는 납땜 작업이 들어가므로 가장 나중에 합니다. 그리고 실험 하나에 **한 가지만** 바꿉니다. 주파수와 ODT를 동시에 바꾸면 어느 쪽이 효과를 냈는지 알 수 없습니다.

## 마진 측정과 ECC 에러 패턴

training이 통과했다고 끝이 아닙니다. 통과는 했지만 여유가 거의 없는 상태라면, 온도가 조금 오르거나 전압이 조금 흔들릴 때 바로 오류가 납니다. 그래서 bring-up에서는 통과 여부와 함께 **마진**(정상 동작하는 설정 범위에 남아 있는 여유)을 잽니다. 다리가 설계 하중보다 얼마나 더 실어도 버티는지 재 보는 일과 비슷합니다.

마진은 보통 delay나 Vref 설정값을 한쪽 끝에서 다른 쪽 끝까지 훑으며 읽기·쓰기가 통과하는 구간을 찾는 방식으로 잽니다. 많은 메모리 컨트롤러가 이런 마진 측정 기능을 펌웨어나 진단 도구로 제공합니다. 결과를 lane별로 늘어놓으면 문제가 눈에 보입니다.

![byte lane별 통과 window — lane 0, 1, 3은 넓은 통과 구간 가운데에 동작점이 있지만, lane 2만 구간이 좁고 동작점이 가장자리에 붙어 있다](/images/blog/debugging/embedded/diagrams/ch17-lane-margin.svg)

그림처럼 한 lane만 통과 구간(window)이 좁거나 한쪽으로 치우쳐 있다면, 그 lane의 배선이나 종단부터 의심합니다. 모든 lane의 window가 고르게 좁다면 보드 전체의 전원 노이즈나 클럭 품질, 또는 설정값 전반을 봅니다.

부팅 후 간헐 오류 단계에서는 **ECC**(error-correcting code, 저장된 데이터에 검사 비트를 붙여 1비트 오류를 고치고 2비트 오류를 감지하는 부호)가 좋은 단서가 됩니다. ECC가 고친 오류(correctable error)는 시스템을 멈추지 않지만, 어디서 얼마나 자주 생기는지를 기록으로 남깁니다. 체온을 매일 재 두면 열이 나기 시작한 날을 알 수 있는 것처럼, ECC 기록은 마진이 무너지기 시작하는 곳을 알려 줍니다.

ECC 에러를 모았다면 위치별로 묶어 봅니다. 아래 스크립트는 ECC 에러 기록을 byte lane, rank, bank, row 단위로 집계해서 어느 차원에 몰려 있는지 보여 줍니다. 입력 CSV 형식은 설명을 위한 예시이며, 실제로는 리눅스 EDAC 로그나 칩의 진단 도구 출력을 이 형식으로 바꿔서 씁니다.

```python
import csv
from collections import Counter

def summarize(path):
    by = {k: Counter() for k in ("lane", "rank", "bank", "row", "dq_bit")}
    total = 0
    with open(path) as f:                 # 열: time,temp_c,rank,bank,row,col,dq_bit
        for r in csv.DictReader(f):
            bit = int(r["dq_bit"])
            by["lane"][bit // 8] += 1     # x8 단위 byte lane
            by["dq_bit"][bit] += 1
            for k in ("rank", "bank", "row"):
                by[k][r[k]] += 1
            total += 1
    for k, c in by.items():
        top, n = c.most_common(1)[0]
        print(f"{k:7s} top={top!s:6s} share={n / total:5.1%}  distinct={len(c)}")

summarize("ecc_log.csv")
```

집계 결과는 대략 이렇게 읽습니다.

| 몰린 곳 | 의심할 원인 |
|---|---|
| DQ 비트 하나 | 그 신호선 하나의 배선·납땜·종단 |
| byte lane 하나 | 그 lane의 배선 묶음, DQS(데이터 스트로브) 타이밍, lane별 PHY 설정 |
| 특정 rank·DDR 칩 하나 | 그 DDR 칩 자체의 불량이나 해당 칩 주변 배선 |
| 특정 row 근처 | DDR 셀 특성이나 접근 패턴 의존 오류 |
| 고르게 퍼짐, 온도에 비례 | 전체 마진 부족, 전원 노이즈, 리프레시 설정 |

"특정 row 근처" 패턴과 관련해 알아 둘 만한 사례가 있습니다. 2014년 카네기멜런 대학과 Intel 연구진은 DRAM의 한 row를 매우 빠르게 반복해서 읽으면 이웃 row의 비트가 뒤집힐 수 있다는 연구를 ISCA 학회에 발표했습니다. 이 현상은 이후 **Rowhammer**라는 이름으로 널리 알려졌고, 보안 공격으로까지 이어졌습니다. bring-up 관점에서의 교훈은 메모리 오류가 *데이터와 접근 패턴*에 따라 달라질 수 있다는 점입니다. 단순한 순차 쓰기·읽기 테스트를 통과했다고 해서 실제 워크로드에서도 안전하다고 단정하면 안 됩니다.

## 보드·SI 팀과 협업하는 법

DDR triage에서 SW 엔지니어가 가장 많이 하는 일은 측정이 아니라 **정확한 데이터를 HW 팀에 넘기는 일**입니다. "DDR이 불안정해요"라는 보고로는 아무도 움직일 수 없습니다. 아래 항목을 갖춰서 넘기면 대화가 빨라집니다.

- **실패한 lane과 단계:** training 로그에서 어느 단계, 어느 lane이 실패했는지를 정리합니다.
- **lane 번호와 보드 신호 이름의 대응:** 보드 설계에서는 배선을 쉽게 하려고 DQ 비트 순서를 바꿔 연결하는 일이 흔합니다. 이를 DQ swizzle이라고 부릅니다. 그래서 펌웨어의 "lane 2, bit 5"가 회로도의 어떤 신호선인지 대응표가 있어야 HW 팀이 해당 배선을 찾을 수 있습니다.
- **마진 측정 결과:** lane별 window 폭과 동작점 위치를 표나 그림으로 정리합니다.
- **실험 기록:** Ch 10의 bring-up 로그 형식대로, 어떤 보드와 칩에서 어떤 조건을 바꿨고 무엇이 변했는지 남깁니다.
- **ECC 집계:** 위 스크립트 같은 집계 결과를 붙입니다.

HW 팀은 이 데이터를 받아 오실로스코프로 해당 신호의 파형과 eye(여러 비트를 겹쳐 그린 신호 모양, Ch 18 참고)를 보고, 보드 시뮬레이션 결과와 비교하고, 필요하면 X-ray로 납땜 상태를 확인합니다. 반대로 HW 팀이 종단 저항 값이나 ODT 권장값을 바꿔 달라고 하면, SW 팀은 그 설정만 바꾼 펌웨어를 빠르게 만들어 같은 실험을 다시 돌립니다. 이 주고받기의 속도가 DDR bring-up 기간을 결정합니다.

## 작은 예시 — lane 2의 범인

Ch 10의 BU-0142 기록을 이어서 따라가 보겠습니다. 보드 이름과 수치는 가상입니다.

1. **증상:** 보드 EVB-A03에서 write leveling 단계에 lane 2만 실패합니다. 전압을 올려도 변화가 없었습니다.
2. **보드 교체:** 같은 펌웨어를 보드 B02와 B05에서 돌려 봅니다. 두 보드 모두 통과합니다. 증상이 A03에 남아 있으므로 보드 개별 문제로 좁혀집니다.
3. **설정 실험:** A03에서 ODT 설정을 바꾸자 training은 통과하지만, 마진을 재 보니 lane 2의 window만 다른 lane의 절반 정도이고 동작점이 가장자리에 붙어 있습니다.
4. **HW 확인:** 대응표로 lane 2의 신호선을 찾아 HW 팀에 넘깁니다. 확인해 보니 lane 2 근처의 종단 저항 하나가 설계값과 다른 값으로 실장되어 있었습니다.
5. **재발 방지:** 저항을 교체한 뒤 마진이 다른 lane 수준으로 돌아옵니다. 조립 공정에 해당 부품 확인 항목을 추가하고, bring-up 로그에 결과를 기록합니다.

이 예시에서 펌웨어 설정을 바꿔 training을 통과시킨 3단계에서 멈췄다면, 마진이 좁은 보드가 다음 단계로 올라갔을 것입니다. 통과 여부가 아니라 마진을 봐야 하는 이유입니다.

## 자주 하는 실수

- **통과하면 끝이라고 생각합니다.** training 통과는 출발점일 뿐입니다. 마진을 재지 않으면 나중에 온도 시험이나 필드에서 다시 만나게 됩니다.
- **한 번에 여러 설정을 바꿉니다.** 운 좋게 통과하더라도 무엇이 효과를 냈는지 알 수 없어서, 다른 보드에서 같은 문제가 나오면 처음부터 다시 해야 합니다.
- **lane 번호를 그대로 HW 팀에 넘깁니다.** DQ swizzle 대응표 없이 "lane 2"라고만 하면 HW 팀은 엉뚱한 배선을 볼 수 있습니다.
- **특정 보드의 설정을 전체 기본값으로 삼습니다.** 문제 있는 보드에 맞춰 조정한 설정이 정상 보드의 마진을 오히려 줄일 수 있습니다.
- **간단한 메모리 테스트만 돌립니다.** 순차 패턴만으로는 패턴 의존 오류를 놓칩니다. 다양한 데이터·주소 패턴과 실제 워크로드를 함께 돌려야 합니다.

## 정리

- DDR은 컨트롤러·PHY·보드·DDR 칩·펌웨어가 모두 맞아야 동작해서, bring-up 계단에서 가장 오래 걸리는 칸이 되기 쉽습니다.
- 증상을 **인식 불가 / training 실패 / 부팅 후 간헐 오류**로 나누면 먼저 의심할 영역이 정해집니다.
- 판정 실험의 원리는 타이어 바꿔 끼우기와 같습니다. 보드·칩·DDR 부품·주파수·설정·온도를 하나씩 바꾸며 증상이 따라오는지 봅니다.
- 실험은 싸고 빠른 것부터, 한 번에 하나씩 바꿉니다.
- training 통과 뒤에는 lane별 마진을 재고, 좁거나 치우친 lane을 먼저 의심합니다.
- ECC 에러는 비트·lane·rank·row 단위로 집계하면 원인 영역을 가리킵니다. 메모리 오류는 Rowhammer처럼 접근 패턴에 따라 달라질 수 있습니다.
- HW 팀에는 실패 단계, DQ swizzle 대응표, 마진, 실험 기록, ECC 집계를 갖춰서 넘깁니다.
