Ch 1~9에서는 디버거와 trace 도구를 하나씩 들여다봤습니다. 모두 *이미 살아 있는 칩*을 전제로 한 도구입니다. 이 장부터 Ch 21까지는 그 전제가 없는 상황, 즉 **칩이 처음 나와서 아직 아무것도 확실하지 않은 상황**을 다룹니다.

이 단계를 **bring-up**이라고 부릅니다. 새로 만든 칩과 보드를 처음 켜서 리눅스 같은 OS가 안정적으로 돌 때까지 하나씩 살려 내는 과정입니다. 이 장은 bring-up 전체를 내려다보는 지도 역할을 합니다. 어떤 순서로 올라가는지, 막혔을 때 문제가 어디 있는지 어떻게 가르는지, 그리고 팀이 무엇을 기록하고 어떻게 움직이는지를 정리합니다. 각 단계의 깊은 이야기는 Ch 11부터 이어집니다.

## 어떤 문제를 푸는가

실리콘이 도착한 첫날을 떠올려 보겠습니다. 테이프아웃 후 몇 달을 기다린 끝에 샘플 칩이 실장된 보드 몇 장이 책상에 올라옵니다. 전원을 넣었더니 아무 반응이 없습니다. UART에는 한 글자도 안 찍히고, 디버거도 칩을 찾지 못합니다.

이때 원인 후보는 수백 개입니다. 보드 조립 불량일 수도, 전원 칩 설정이 틀렸을 수도, 클럭이 안 돌 수도, 칩 자체에 결함이 있을 수도, BootROM이 엉뚱한 곳에서 부팅하려 할 수도 있습니다. 소프트웨어는 아직 한 줄도 돌지 않았는데 이미 SW 팀과 HW 팀 모두가 용의자입니다.

pre-silicon 단계에서는 waveform으로 모든 신호를 볼 수 있었습니다. 실리콘에서는 그렇지 않습니다. 보이는 것은 핀 몇 개와 측정 장비 화면, 그리고 미리 심어 둔 디버그 훅뿐입니다. 그래서 bring-up의 핵심은 **넓은 원인 후보를 체계적으로 좁혀 가는 순서**입니다. 이 순서를 모르면 증상 하나에 일주일을 쓰고, 알면 하루에 몇 단계를 올라갑니다.

## Bring-up은 계단이다

bring-up은 건물을 아래층부터 올리는 일과 같습니다. 1층 기둥이 흔들리는데 3층 인테리어를 고민해 봐야 소용이 없습니다. 칩도 마찬가지입니다. 전원이 불안정한데 DDR training 실패를 분석하면, 원인이 아닌 증상을 쫓게 됩니다.

![Bring-up 계단 — 전원, 클럭·리셋, 디버그 접속, BootROM, 첫 코드, DDR, 부트로더, 커널·드라이버 순서로 한 칸씩 올라간다](/images/blog/debugging/embedded/diagrams/ch10-bringup-ladder.svg)

여덟 칸은 크게 네 묶음으로 나뉩니다.

- **전기(전원, 클럭·리셋):** 소프트웨어가 개입하기 전입니다. 멀티미터와 오실로스코프로 확인합니다.
- **접속(디버그 접속, BootROM):** 칩과 처음 대화하는 단계입니다. JTAG이 붙는지, ROM이 무엇을 하고 있는지 봅니다.
- **메모리(첫 코드, DDR):** 코드를 둘 자리를 확보하는 단계입니다. 칩 내부 SRAM에서 작은 코드를 먼저 돌리고, 그다음 외부 DDR을 살립니다.
- **SW 스택(부트로더, 커널·드라이버):** 여기부터는 Bootloader Internals와 BSP Development 시리즈에서 다룬 익숙한 세계입니다.

원칙은 하나입니다. **아래 칸이 확실하다고 증명되기 전에는 위로 올라가지 않습니다.** "아마 괜찮을 것"은 증명이 아닙니다. 측정값이나 로그가 있어야 확실하다고 말할 수 있습니다.

## 단계마다 무엇을 보나

같은 단계에서도 SW 엔지니어가 보는 증상과 HW 엔지니어가 측정할 것이 다릅니다. 아래 표에 두 시점을 나란히 놓았습니다. 회의에서 "UART가 안 찍혀요"라는 말이 나오면, 표의 오른쪽 두 열을 함께 채워 보면 어느 칸에서 막혔는지 금방 드러납니다.

| 단계 | SW 쪽에서 보이는 증상 | HW 쪽에서 측정할 것 | 자세히 |
|---|---|---|---|
| 전원 | 아무 반응 없음 | 각 전원 레일 전압, 켜지는 순서, 전류 | Ch 11 |
| 클럭·리셋 | 아무 반응 없음, 또는 계속 재부팅 | 오실레이터 출력, PLL lock 신호, 리셋 핀 | Ch 11 |
| 디버그 접속 | 디버거가 칩을 못 찾음 | JTAG/SWD 핀 신호, 디버그 전원 도메인 | Ch 13 |
| BootROM | UART 무출력, 디버거로 보면 PC가 ROM 안 | boot mode 핀 레벨, 부트 미디어 신호 | Ch 12 |
| 첫 코드 | 디버거로 올린 코드가 안 돎 | (SW로 확인) SRAM 읽기·쓰기, GPIO 토글 | 이 장 |
| DDR | 부트로더가 메모리 초기화에서 멈춤 | DDR 신호, 전원 노이즈, 보드 배선 | Ch 17 |
| 부트로더 | 부트로더 로그가 중간에 끊김 | (SW 위주) 저장 장치, 주변 장치 신호 | Bootloader Ch 22 |
| 커널·드라이버 | 커널 패닉, 특정 장치만 실패 | 해당 주변 장치의 버스 신호 | BSP Ch 10~11 |

표를 보면 아래 칸일수록 HW 측정 비중이 크고, 위 칸일수록 SW 로그 비중이 커집니다. bring-up 초반에 SW 엔지니어가 측정 장비 앞에 HW 엔지니어와 함께 앉아 있어야 하는 이유입니다.

## 첫날 — 연기가 나지 않는지부터

첫 전원 인가는 의외로 조심스러운 작업입니다. 보드에 단락(short)이 있거나 전원 칩 설정이 틀렸다면, 전원을 넣는 순간 칩이 손상될 수 있습니다. 샘플 칩은 몇 개 없고 다시 받으려면 몇 주가 걸리기 때문에, 첫날의 목표는 "부팅"이 아니라 **"아무것도 망가뜨리지 않기"**입니다. 업계에서 이 첫 확인을 smoke test라고 부르는 것도 "연기가 나지 않는지 본다"는 뜻에서 왔습니다.

첫날 순서는 보통 이렇습니다.

1. **눈으로 확인합니다.** 부품이 빠지거나 뒤집혀 실장되지 않았는지, 납땜이 붙어 버린 곳은 없는지 봅니다.
2. **전원을 넣지 않고 저항을 잽니다.** 각 전원 레일과 접지 사이 저항이 0Ω에 가깝다면 단락입니다.
3. **전류 제한을 걸고 전원을 넣습니다.** 실험실 전원 공급기의 전류 제한을 낮게 걸어 두고 천천히 올립니다. 수도관에 새는 곳이 있는지 볼 때 수도꼭지를 조금만 트는 것과 같습니다. 문제가 있으면 큰 사고가 나기 전에 전류가 막힙니다.
4. **레일 전압과 순서를 잽니다.** 모든 레일이 설계값에 있는지, 정해진 순서로 켜지는지 오실로스코프로 확인합니다.
5. **클럭과 리셋을 봅니다.** 오실레이터가 진동하는지, 리셋 신호가 정상적으로 풀리는지 확인합니다.

여기까지 통과하면 비로소 소프트웨어의 차례가 옵니다. 각 단계의 측정 방법과 실패 패턴은 Ch 11에서 자세히 봅니다.

## 가장 작은 첫 코드

전기가 확인되고 디버거가 붙으면, 다음 목표는 **칩이 내가 쓴 코드를 실행한다는 증거**를 얻는 것입니다. 이때 처음부터 부트로더를 올리지 않습니다. 부트로더는 DDR, 저장 장치, 클럭 설정 등 너무 많은 것에 의존하기 때문입니다. 대신 칩 내부 SRAM에 들어갈 만큼 작은 코드를 디버거로 직접 올립니다.

아래 코드는 그런 첫 코드의 전형입니다. 외부 메모리에 전혀 의존하지 않고, 살아 있다는 신호를 세 가지 방법으로 남깁니다. UART가 안 나와도 GPIO나 scratch 레지스터로 진행 상황을 알 수 있게 하려는 설계입니다.

```c
/* 첫 코드: SRAM에서 실행, 스택도 SRAM. 모든 주소는 예시 값 */
#define GPIO_OUT     (*(volatile uint32_t *)0x40020014u)
#define SCRATCH0     (*(volatile uint32_t *)0x40000100u)  /* 리셋에도 유지되는 레지스터라고 가정 */
#define UART_THR     (*(volatile uint32_t *)0x40030000u)
#define UART_LSR     (*(volatile uint32_t *)0x40030014u)
#define LSR_THRE     (1u << 5)

static void postcode(uint32_t code) { SCRATCH0 = code; }

static void uart_putc(char c)
{
    for (uint32_t spin = 0; spin < 100000u; spin++)   /* UART가 죽어 있어도 멈추지 않게 */
        if (UART_LSR & LSR_THRE) { UART_THR = (uint32_t)c; return; }
}

void first_code(void)
{
    postcode(0xB0010001u);                 /* 1: 진입 */
    GPIO_OUT ^= 1u;                        /* LED 또는 스코프로 볼 핀 */
    postcode(0xB0010002u);                 /* 2: GPIO 접근 통과 */
    for (const char *s = "hello silicon\r\n"; *s; s++)
        uart_putc(*s);
    postcode(0xB0010003u);                 /* 3: UART 출력 시도 끝 */
    for (;;) { GPIO_OUT ^= 1u; for (volatile int i = 0; i < 100000; i++) { } }
}
```

이 코드를 디버거로 SRAM에 올려 실행합니다. OpenOCD라면 telnet 콘솔에서 아래처럼 합니다. OpenOCD 자체는 Ch 3에서 다뤘습니다.

```text
> halt
> load_image first_code.bin 0x10000000 bin
> resume 0x10000000
> halt
> mdw 0x40000100
0x40000100: b0010003
```

scratch 레지스터에 `0xB0010003`이 남아 있다면 코드가 끝까지 돌았다는 뜻입니다. 그런데 UART에 글자가 없다면, 문제는 코어가 아니라 UART 경로(클럭, 핀 설정, 보드 배선)에 있다고 범위를 좁힐 수 있습니다. 반대로 `0xB0010001`에서 멈췄다면 GPIO 레지스터 접근 자체가 막혔다는 뜻이고, 버스나 주변 장치 클럭을 의심합니다. 이런 postcode 기법을 JTAG 없이 쓰는 법은 Ch 14에서 더 다룹니다.

## 막혔을 때 — 문제는 어디에 있나

계단 어딘가에서 막히면 가장 먼저 답해야 할 질문은 "무엇이 틀렸나"가 아니라 **"누구의 영역인가"**입니다. 보드인지, 칩인지, 소프트웨어인지에 따라 연락할 팀과 쓸 도구가 완전히 달라지기 때문입니다. 아래 세 질문을 순서대로 던지면 대부분의 경우 범위가 좁혀집니다.

![문제 위치 판정 — 여러 보드에서 재현되는지, 전압·온도·주파수에 민감한지, 최소 코드로도 재현되는지로 보드·실리콘 마진·SW·설계 버그를 가른다](/images/blog/debugging/embedded/diagrams/ch10-where-is-the-bug.svg)

**첫째, 여러 보드에서 똑같이 재현되나?** 보드 한 장에서만 생기는 문제는 대개 그 보드의 조립 불량이나 부품 문제입니다. 그래서 bring-up 초반에는 보드를 최소 두세 장 확보해 두는 것이 중요합니다. 의사가 한쪽 귀만 아프다는 환자를 보면 양쪽 귀를 다 들여다보는 것과 같은 이치입니다.

**둘째, 전압·온도·주파수를 바꾸면 증상이 달라지나?** 전압을 조금 올렸더니 증상이 사라지거나, 칩을 식혔더니 안정된다면 논리 버그가 아니라 전기적 마진 문제일 가능성이 큽니다. 이 실험과 그 결과를 읽는 법(shmoo)은 Ch 19에서 다룹니다.

**셋째, 최소 코드로 줄여도 재현되나?** 드라이버 전체가 아니라 레지스터 몇 개만 건드리는 작은 코드로도 같은 증상이 나온다면, 소프트웨어의 복잡한 로직보다 칩의 설계 쪽을 의심할 근거가 생깁니다. 이때는 같은 시나리오를 pre-silicon 환경에서 재현해 waveform으로 확인합니다. 그 과정은 Co-simulation 시리즈 Ch 15에서 다룹니다. 최소 코드에서 재현이 안 된다면, 드라이버의 순서나 설정이 문제일 가능성이 큽니다.

이 판정이 완벽하지는 않습니다. 보드 문제가 여러 장에 똑같이 있을 수도 있고(설계 단계의 배선 실수), SW 버그가 온도에 따라 달라질 수도 있습니다(타이밍 경쟁). 그래도 이 세 질문은 "누구를 회의에 부를지"를 정하는 데 충분히 쓸모가 있습니다.

## Bring-up 로그 — 항해일지처럼 남기기

bring-up은 몇 주에서 몇 달이 걸리고, 여러 사람이 여러 보드를 만집니다. 그래서 무엇을 언제 어떤 보드에서 해 봤는지 기록하지 않으면 같은 실험을 두 번 하거나, 이미 배제한 원인을 다시 의심하게 됩니다. 배가 항해일지를 쓰듯 bring-up 팀도 실험 하나하나를 기록합니다.

형식은 팀마다 다르지만, 나중에 검색하고 집계할 수 있게 구조화해 두면 좋습니다. 아래는 실험 하나를 기록하는 예시 형식입니다.

```yaml
- id: BU-0142
  date: 2026-10-05
  board: EVB-A03          # 보드마다 고유 ID와 수정 이력을 관리
  chip: A0-lot17-#08      # 칩 스테핑·로트·번호
  stage: ddr              # 계단의 어느 칸인가
  setup: { vdd_core: 0.80, temp: 25C, fw: bl2-dbg-0.3.1 }
  symptom: "write leveling 단계에서 byte lane 2만 실패"
  experiment: "VDD_DDR를 +3% 올려 재시도"
  result: "변화 없음"
  conclusion: "전압 마진 문제 가능성 낮음. 보드 B02에서 같은 실험 예정"
  owner: hw-ddr
```

이렇게 쌓인 기록은 나중에 패턴을 보여 줍니다. 특정 로트의 칩에서만 실패가 몰린다든지, 특정 보드 리비전에서만 문제가 난다든지 하는 사실은 기록이 있어야 보입니다. 양산 단계의 통계적 triage(Ch 21)도 결국 이 습관의 연장입니다.

## 팀 운영 — 기준 보드와 매일의 triage

bring-up은 개인 작업이 아니라 팀 작업입니다. 기술보다 운영에서 시간을 잃는 경우가 많아서, 실무에서 자주 쓰이는 습관 몇 가지를 정리합니다.

- **기준 보드(known-good board)를 지정합니다.** 한 번 끝까지 살아난 보드를 기준으로 삼고, 함부로 개조하지 않습니다. 새 증상이 나오면 기준 보드에서도 재현되는지부터 봅니다. 실험실에서 저울을 표준 분동으로 교정하듯, 기준이 있어야 차이를 잴 수 있습니다.
- **보드마다 개조 이력을 남깁니다.** 저항 하나 바꾼 보드와 원래 보드가 섞이면, 같은 실험이 다른 결과를 내는 이유를 찾느라 며칠을 잃습니다.
- **매일 짧은 triage 회의를 합니다.** 새 증상을 앞의 세 질문으로 분류하고 담당 팀을 정합니다. 결론이 안 나는 증상은 "다음에 할 실험"과 담당자를 정하고 넘어갑니다.
- **막힌 칸을 우회할 수 있으면 우회합니다.** DDR이 안 살아나도 SRAM만으로 주변 장치 테스트를 일부 진행할 수 있습니다. 계단을 병렬로 써서 한 칸에서 모든 사람이 멈춰 있지 않게 합니다.

## 실제 사례 — 빛에 꺼지는 보드

bring-up의 "아래 칸"이 얼마나 예상 밖일 수 있는지 보여 주는 유명한 사례가 있습니다. 2015년 2월, Raspberry Pi 2가 출시된 직후 사용자들이 이상한 현상을 보고했습니다. 카메라 플래시를 보드에 터뜨리면 보드가 꺼진다는 것이었습니다.

원인은 소프트웨어가 아니라 전원부였습니다. 보드의 전원 레귤레이터 칩 하나가 WL-CSP(wafer-level chip scale package)라는 패키지를 쓰는데, 이 패키지는 실리콘 다이가 거의 그대로 드러나 있습니다. 그래서 강한 빛을 받으면 광전 효과로 칩이 오동작해 전원이 끊긴 것입니다. 당시 Raspberry Pi 재단은 일상적인 사용에는 영향이 없다고 설명했고, 신경 쓰이는 사용자에게는 해당 칩을 불투명한 것으로 가리라고 안내했습니다.

이 사례는 이 장의 판정 질문으로도 설명할 수 있습니다. 여러 보드에서 똑같이 재현됐으니 개별 조립 불량은 아니었습니다. 최소 코드는커녕 어떤 코드와도 상관이 없었으니 SW 문제도 아니었습니다. 증상이 *환경 조건*(빛)에 따라 달라졌다는 점이 결정적 단서였습니다. 전압·온도·주파수만이 환경 조건은 아니라는 교훈도 함께 남습니다.

## 자주 하는 실수

- **계단을 건너뜁니다.** 부트로더 로그가 안 나온다고 부트로더 코드부터 디버깅합니다. 그 아래 칸(클럭, DDR)이 확실한지 먼저 확인해야 합니다.
- **보드 한 장으로 결론을 냅니다.** 보드 한 장에서 본 현상을 칩 버그로 보고했다가, 나중에 그 보드의 납땜 불량으로 밝혀지는 일이 흔합니다.
- **기록 없이 실험합니다.** "어제 그 설정으로 해 봤던가?"라는 질문이 나오기 시작하면 이미 시간을 잃고 있습니다.
- **첫 코드를 너무 크게 만듭니다.** 첫 코드가 DDR이나 복잡한 클럭 설정에 의존하면, 실패했을 때 원인 후보가 다시 수백 개로 늘어납니다.
- **SW와 HW가 따로 움직입니다.** 증상은 SW 쪽에서, 원인은 HW 쪽에서 보이는 경우가 많습니다. 초반에는 같은 책상에서 같은 화면을 봐야 합니다.

## 정리

- bring-up은 새 칩과 보드를 처음 켜서 OS가 안정적으로 돌 때까지 하나씩 살려 내는 과정입니다.
- 순서는 **전원 → 클럭·리셋 → 디버그 접속 → BootROM → 첫 코드 → DDR → 부트로더 → 커널·드라이버**의 계단이고, 아래 칸이 증명되기 전에는 올라가지 않습니다.
- 첫날의 목표는 부팅이 아니라 **아무것도 망가뜨리지 않는 것**입니다. 저항 측정과 전류 제한 전원으로 시작합니다.
- 첫 코드는 SRAM에서 도는 아주 작은 코드로 만들고, GPIO·scratch 레지스터·UART로 살아 있다는 신호를 여러 경로로 남깁니다.
- 막히면 **여러 보드 재현 → 전압·온도·주파수 민감도 → 최소 코드 재현** 순서로 보드·실리콘·SW·설계 중 어디인지 가릅니다.
- 실험은 보드·칩·조건·결과를 구조화해서 기록하고, 기준 보드와 개조 이력을 관리합니다.
- 환경 조건은 전압·온도만이 아닙니다. Raspberry Pi 2의 플래시 사례처럼 예상 밖의 조건이 단서가 되기도 합니다.
