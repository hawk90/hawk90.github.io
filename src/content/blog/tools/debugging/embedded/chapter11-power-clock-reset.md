첫 실리콘에서 가장 먼저 부딪히는 벽은 소프트웨어가 아니라 전기입니다. 전원과 클럭과 리셋 중 하나라도 어긋나면 디버거도 UART도 아무 말을 하지 않습니다. Ch 10의 bring-up 계단에서 맨 아래 두 칸에 해당하는 영역입니다.

MCU 보드라면 전원 하나, 수정 발진기 하나, 리셋 핀 하나를 확인하면 대부분 끝납니다. 그 단계별 점검은 [Modern Embedded Recipes의 부팅 실패 진단](/blog/embedded/modern-recipes/part10-06-boot-failure)에서 다뤘습니다. SoC는 사정이 다릅니다. 전원 레일이 열 개를 넘기도 하고, 그 레일을 PMIC(Power Management IC, 여러 전원을 정해진 순서로 만들어 공급하는 전원 관리 칩)가 순서대로 켜며, 클럭은 PLL(기준 클럭을 몇 배 높은 주파수로 끌어올리는 회로)을 거쳐 수십 개 도메인으로 나뉩니다. 이 장은 그 복잡한 전기 계층을 SW 엔지니어와 HW 엔지니어가 함께 점검하는 순서를 정리합니다.

## 아무 반응이 없을 때의 순서

전원을 넣었는데 아무 반응이 없을 때, 원인은 크게 세 갈래입니다. 전원이 제대로 들어오지 않았거나, 클럭이 돌지 않거나, 리셋이 풀리지 않은 경우입니다. 세 가지는 서로 의존합니다. PLL은 전원이 안정돼야 lock(출력 주파수가 목표에 안정적으로 맞은 상태)되고, 리셋은 보통 PLL이 lock된 뒤에 풀립니다. 그래서 점검 순서도 이 의존 관계를 따라 전원, 클럭, 리셋 순으로 갑니다.

자동차 시동이 안 걸릴 때와 같습니다. 배터리가 방전됐는데 점화 플러그부터 의심하는 사람은 없습니다. 계기판 불이 들어오는지(전원), 엔진이 도는지(클럭), 주차 브레이크가 풀렸는지(리셋)를 차례로 봅니다.

이 단계의 특징은 **SW에서 보이는 증상이 거의 똑같다**는 점입니다. 전원 문제든 클럭 문제든 리셋 문제든, SW 쪽에서는 "아무 출력이 없다" 하나로 보입니다. 그래서 아래 표처럼 HW 측정값으로 갈라야 합니다.

| SW 쪽 증상 | HW 쪽에서 볼 것 | 의심 영역 |
|---|---|---|
| 아무 출력 없음, 디버거도 칩을 못 찾음 | 전원 레일 전압, 전류 소모 | 전원 |
| 아무 출력 없음, 전류는 정상 범위 | 오실레이터 파형, PLL lock 상태 | 클럭 |
| 아무 출력 없음, 리셋 핀이 계속 low | 리셋 신호, 리셋을 붙잡는 조건 | 리셋 |
| 출력이 조금 나오다가 처음부터 다시 시작 | 리셋 원인 기록, 전원 노이즈 | 리셋 루프 |
| 무거운 작업을 시작하면 재부팅 | 부하가 걸릴 때 레일 전압 | 전원 마진 |

## 전원 레일과 시퀀스 측정

SoC에는 여러 전원 레일(칩의 각 영역에 전압을 공급하는 전원선)이 있습니다. 항상 켜진 영역용, CPU 코어용, I/O용, DDR용이 따로 있고, 각 레일의 전압도 다릅니다. 이 레일들은 정해진 **순서와 간격**으로 켜져야 합니다. 이것을 전원 시퀀스(power sequence)라고 부릅니다. 순서가 틀리면 칩이 이상한 상태로 시작하거나, 심하면 칩 내부에 과전류가 흘러 손상될 수 있습니다. 건물 전기 공사에서 차단기를 정해진 순서대로 올리지 않으면 설비가 상하는 것과 같습니다.

![전원 시퀀스 — 레일이 정해진 순서로 켜지고, PLL lock 뒤에 리셋이 풀린다 (신호 이름은 예시)](/images/blog/debugging/embedded/diagrams/ch11-power-sequence.svg)

측정은 오실로스코프(시간에 따른 전압 변화를 그래프로 보여 주는 장비)로 합니다. 채널 네 개짜리 스코프라면 레일 세 개와 리셋 신호 하나를 동시에 걸고, 전원 버튼을 누르는 순간을 트리거로 잡습니다. 확인할 것은 네 가지입니다.

- **최종 전압:** 각 레일이 설계값의 허용 범위 안에 들어오는가.
- **순서:** 데이터시트가 요구하는 순서대로 켜지는가.
- **상승 시간과 간격:** 레일이 너무 빠르거나 느리게 올라가지 않는가, 레일 사이 간격이 최소 요구를 만족하는가.
- **리셋 해제 시점:** 모든 레일이 안정된 뒤에 리셋이 풀리는가.

PC에서도 같은 원리가 쓰입니다. ATX 전원 공급기는 모든 출력 전압이 안정되면 PWR_OK라는 신호를 내보내고, 메인보드는 이 신호가 올 때까지 CPU를 리셋 상태로 붙잡아 둡니다. SoC 보드에서는 PMIC가 이 역할을 맡습니다.

## PMIC 설정과 전압 마진

PMIC는 레일마다 전압과 켜지는 순서를 설정값으로 갖고 있습니다. 이 설정은 PMIC 내부의 OTP(One-Time Programmable, 한 번만 쓸 수 있는 메모리)에 공장에서 구워져 나오거나, 부팅 초기에 소프트웨어가 I2C로 써 넣습니다. bring-up에서 흔한 문제는 PMIC 설정이 *다른 보드나 다른 칩 리비전용*으로 구워져 있는 경우입니다. 측정해 보면 레일 하나가 0.1V쯤 낮거나, 순서가 하나 바뀌어 있습니다.

PMIC 설정을 소프트웨어로 바꾸는 경우라면, 부팅 초기 코드가 I2C로 값을 읽어 기대값과 비교하는 습관이 도움이 됩니다. 아래 코드는 레일 설정을 읽어 기대값과 다르면 로그로 남기는 예시입니다. 레지스터 주소와 인코딩은 PMIC마다 다르므로 모두 예시 값입니다.

```c
/* PMIC 레지스터 주소와 전압 인코딩은 예시. 실제 값은 PMIC 데이터시트를 따른다 */
struct rail_check { const char *name; uint8_t reg; uint8_t expect; };

static const struct rail_check rails[] = {
    { "VDD_CORE", 0x20, 0x3C },   /* 예: 0.80 V */
    { "VDD_DDR",  0x28, 0x58 },   /* 예: 1.10 V */
    { "VDD_IO",   0x30, 0x7C },   /* 예: 1.80 V */
};

int pmic_verify(void)
{
    int bad = 0;
    for (unsigned i = 0; i < sizeof(rails) / sizeof(rails[0]); i++) {
        uint8_t v = pmic_read(rails[i].reg);          /* I2C 읽기 */
        if (v != rails[i].expect) {
            early_log("PMIC %s: got 0x%02x expect 0x%02x\n",
                      rails[i].name, v, rails[i].expect);
            bad++;
        }
    }
    return bad;
}
```

전압이 설계값에 맞더라도 **마진**(칩이 정상 동작하는 전압 여유)이 충분한지는 따로 봐야 합니다. CPU가 무거운 작업을 시작하면 순간적으로 전류가 크게 늘고, 그때 레일 전압이 잠깐 떨어집니다. 이 순간 하락을 droop이라고 부릅니다. 평소에는 멀쩡하다가 부하가 걸릴 때만 재부팅된다면 droop을 의심합니다. 스코프를 레일에 걸고, 부하 테스트를 시작하는 순간을 트리거로 잡아 최저 전압을 봅니다.

Raspberry Pi 사용자라면 비슷한 현상을 본 적이 있을 수 있습니다. 전원 어댑터가 약하면 무거운 작업 중에 저전압 경고가 뜨고, `vcgencmd get_throttled` 명령으로 저전압이 있었는지 이력을 확인할 수 있습니다. 이 기능은 보드가 스스로 레일을 감시해 기록을 남기는 장치이고, SoC bring-up에서도 이런 감시 기록이 있으면 droop 진단이 훨씬 쉬워집니다.

## 클럭 — 오실레이터와 PLL lock

전원이 확인되면 다음은 클럭입니다. SoC의 클럭은 보통 수정 발진기(crystal oscillator, 수정 결정의 진동으로 정확한 주파수를 만드는 부품) 하나에서 시작합니다. 이 기준 클럭은 주파수가 낮아서, PLL(Phase-Locked Loop, 기준 클럭을 받아 몇 배 높은 주파수를 만드는 회로)이 CPU와 버스가 쓸 높은 주파수로 끌어올립니다. 그 뒤 MUX(여러 클럭 중 하나를 고르는 회로)와 분주기(주파수를 정수로 나누는 회로)가 각 도메인에 맞는 클럭을 나눠 줍니다. 실패 지점은 아래 그림의 세 곳입니다.

![클럭 트리 — 기준 클럭에서 PLL, MUX·분주기를 거쳐 도메인으로. 실패 지점은 발진, lock, 선택·분주 세 곳](/images/blog/debugging/embedded/diagrams/ch11-clock-tree.svg)

**① 발진하지 않음.** 수정 발진기가 아예 진동하지 않는 경우입니다. 스코프로 발진기 핀을 보면 바로 알 수 있습니다. 원인은 납땜 불량이거나, 발진기에 붙는 부하 커패시터 값이 맞지 않는 경우가 많습니다. 다만 스코프 프로브 자체가 발진 회로에 부담을 줘서 측정하는 순간 진동이 멈추는 일도 있으니, 가능하면 발진기 출력 버퍼 쪽이나 클럭 출력 핀으로 내보낸 신호를 봅니다.

**② PLL이 lock되지 않음.** PLL은 출력 주파수가 목표에 안정적으로 맞으면 lock 상태 비트를 세웁니다. 이 비트가 서지 않으면 PLL 출력은 믿을 수 없는 클럭입니다. 원인은 기준 클럭 문제, PLL 설정값(배수·분주 계수) 오류, PLL 전원 레일의 노이즈 등입니다. 라디오 채널을 맞추는 일과 비슷합니다. 다이얼이 정확한 주파수에 맞아야 잡음이 사라지고, 그 전에는 소리가 섞여 들립니다.

**③ 잘못된 선택이나 분주.** PLL은 정상인데 MUX가 다른 클럭을 고르거나 분주 값이 틀리면, 특정 도메인만 엉뚱한 주파수로 돕니다. UART만 글자가 깨져 나온다면 UART 클럭 분주를 먼저 의심합니다.

PLL을 설정하는 펌웨어는 lock을 기다릴 때 반드시 timeout을 둡니다. lock이 안 되는 칩에서 무한히 기다리면 hang이 되고, 어디서 멈췄는지도 알 수 없기 때문입니다. 아래 코드는 timeout과 postcode(부팅 단계마다 정해진 번호를 리셋에도 남는 레지스터에 써 두는 관례, Ch 14에서 자세히 다룸)를 함께 써서, 실패해도 흔적을 남기는 PLL 설정 예시입니다.

```c
/* 레지스터 이름과 비트 위치는 예시 */
#define PLL_CTRL     (*(volatile uint32_t *)0x40001000u)
#define PLL_STATUS   (*(volatile uint32_t *)0x40001004u)
#define PLL_LOCKED   (1u << 0)

int pll_bringup(uint32_t mult, uint32_t div)
{
    postcode(0x0201);                         /* PLL 설정 시작 */
    PLL_CTRL = (mult << 8) | (div << 0) | (1u << 31);   /* 계수 설정 후 enable */

    for (uint32_t i = 0; i < 100000u; i++) {
        if (PLL_STATUS & PLL_LOCKED) {
            postcode(0x0202);                 /* lock 성공 */
            return 0;
        }
    }
    postcode(0x02EE);                         /* lock 실패: 호출자가 bypass로 전환해 계속 진행 */
    return -1;
}
```

lock에 실패했을 때 `pll_bringup()`이 -1을 돌려주면, 호출자가 바로 멈추지 않고 **bypass**(PLL을 거치지 않고 기준 클럭을 그대로 쓰는 경로)로 전환해 계속 진행하게 합니다. 이렇게 하면 느리더라도 UART까지는 살릴 수 있습니다. 느린 클럭으로라도 로그가 나오면 PLL 문제를 소프트웨어로 조사할 길이 열립니다.

## 리셋 — reason 레지스터와 리셋 루프

클럭까지 정상이면 리셋을 봅니다. 리셋 핀이 계속 low로 붙잡혀 있으면 칩은 시작하지 않습니다. 리셋을 붙잡는 조건은 보통 PMIC의 전원 정상 신호, 외부 리셋 버튼 회로, watchdog 출력 등이고, 이 중 하나가 계속 리셋을 요청하고 있는지 스코프로 확인합니다.

더 까다로운 경우는 **리셋 루프**입니다. 칩이 시작해서 잠깐 무언가를 하다가 다시 리셋되기를 반복합니다. UART에 같은 부팅 메시지 첫 줄이 반복해서 찍힌다면 리셋 루프입니다. 이때 가장 먼저 볼 것은 **리셋 원인 레지스터**(reset reason register, 칩이 마지막으로 왜 리셋됐는지 기록하는 레지스터)입니다. 대부분의 SoC는 전원 투입, 외부 핀, watchdog, 소프트웨어 요청, 전압 저하 감지 같은 원인을 비트로 구분해 남깁니다.

부팅 초기에 이 레지스터를 읽어 출력하는 코드는 bring-up 내내 쓸모가 있습니다. 아래는 그런 코드의 예시이며, 레지스터 주소와 비트 배치는 칩마다 다르므로 모두 예시입니다.

```c
/* 리셋 원인 레지스터와 비트 정의는 예시. 실제 정의는 칩 레퍼런스 매뉴얼을 따른다 */
#define RST_REASON   (*(volatile uint32_t *)0x40000200u)

static const char *const reason_name[] = {
    "power-on", "external pin", "watchdog", "software", "brown-out",
};

void report_reset_reason(void)
{
    uint32_t r = RST_REASON;
    for (unsigned b = 0; b < 5; b++)
        if (r & (1u << b))
            early_log("reset reason: %s\n", reason_name[b]);
    RST_REASON = r;                           /* write-1-to-clear: 다음 리셋을 위해 지운다 */
}
```

리셋 원인이 watchdog이라면 소프트웨어가 어딘가에서 멈췄다는 뜻이고, Ch 14의 hang 진단으로 넘어갑니다. brown-out(전압 저하 감지 회로가 리셋을 건 경우)이라면 다시 전원 마진으로 돌아가 droop을 봅니다. 외부 핀이라면 리셋 회로나 PMIC 쪽을 봅니다. 리셋 원인 하나가 다음에 볼 곳을 정해 줍니다. 필드에서 수집한 리셋 원인을 통계로 다루는 방법은 [Modern Embedded Recipes의 포스트모템 분석](/blog/embedded/modern-recipes/part10-12-postmortem-analysis)에서 다뤘습니다.

## 작은 예시 — 무거운 작업에서만 재부팅되는 보드

가상의 사례로 이 장의 순서를 한 번 따라가 보겠습니다. 리눅스까지 부팅되는 보드가 CPU 부하 테스트를 시작하면 몇 초 안에 재부팅됩니다. 가벼운 작업에서는 몇 시간을 돌려도 멀쩡합니다.

먼저 리셋 원인을 봅니다. 부팅 로그에 `reset reason: brown-out`이 찍혀 있습니다. 전압 저하가 리셋을 걸었다는 뜻이므로 전원 쪽으로 갑니다. 스코프를 VDD_CORE에 걸고, 부하 테스트 시작을 트리거로 잡습니다. 테스트를 시작하는 순간 VDD_CORE가 설계값보다 크게 떨어졌다가 회복하는 droop이 보입니다.

다음은 원인을 가르는 실험입니다. 같은 보드를 두세 장 비교해 보니 모두 같은 증상입니다. 개별 조립 불량은 아닙니다. PMIC 설정을 읽어 보니 VDD_CORE 레일의 전류 제한이 낮게 잡혀 있었습니다. 다른 제품용 설정이 그대로 들어가 있었던 것입니다. 설정을 고치자 droop이 허용 범위 안으로 들어왔고 재부팅도 사라졌습니다. SW 쪽 증상은 "재부팅"이었지만, 원인은 PMIC 설정이라는 HW와 SW의 경계에 있었습니다.

## 자주 하는 실수

- **멀티미터로만 잽니다.** 멀티미터는 평균값을 보여 줍니다. 순서, 상승 시간, 순간 droop은 스코프로만 보입니다.
- **레일을 하나씩 따로 잽니다.** 시퀀스 문제는 레일 사이의 *상대적인* 시점 문제입니다. 여러 채널을 한 화면에 함께 걸어야 보입니다.
- **PLL lock을 무한히 기다립니다.** lock이 안 되는 칩에서 펌웨어가 멈추면, 클럭 문제인지 다른 문제인지조차 알 수 없게 됩니다.
- **리셋 원인 레지스터를 지우지 않습니다.** 이전 리셋의 비트가 남아 있으면 이번 리셋의 원인과 섞여 잘못된 결론을 냅니다.
- **PMIC 설정을 확인하지 않고 칩을 의심합니다.** PMIC OTP가 다른 보드용으로 구워진 경우가 생각보다 흔합니다.

## 정리

- SoC는 레일이 여러 개이고 PMIC가 순서대로 켜기 때문에, MCU보다 점검할 것이 훨씬 많습니다.
- 점검 순서는 의존 관계를 따라 **전원 → 클럭 → 리셋**입니다. SW 쪽 증상은 모두 "아무 출력 없음"이라 HW 측정으로 갈라야 합니다.
- 전원은 스코프로 **전압·순서·상승 시간·리셋 해제 시점**을 한 화면에서 보고, 부하가 걸릴 때의 droop을 따로 확인합니다.
- PMIC 설정은 부팅 초기에 읽어 기대값과 비교합니다. 다른 보드용 설정이 들어간 경우가 흔합니다.
- 클럭은 **발진, PLL lock, 선택·분주** 세 지점을 봅니다. lock 대기에는 timeout과 postcode를 두고, 실패하면 bypass로라도 진행합니다.
- 리셋 루프는 **리셋 원인 레지스터**로 출발점을 정합니다. watchdog이면 hang, brown-out이면 전원 마진, 외부 핀이면 리셋 회로를 봅니다.
