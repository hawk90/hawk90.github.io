전원과 클럭이 정상인데 아무 출력이 없다면, 대개 BootROM이 다음 단계를 찾지 못하고 멈춰 있습니다. BootROM(칩 안에 고정된 첫 부팅 코드)은 수정할 수도, 로그를 추가할 수도 없습니다. 그래서 이 단계의 디버깅은 칩 밖에서 관찰할 수 있는 단서를 모아 ROM이 무엇을 하고 있는지 추리하는 일이 됩니다.

BootROM이 *어떻게 동작하는지*, 즉 boot mode 결정 방식과 eFuse·OTP의 역할은 [Bootloader Internals Ch 23](/blog/embedded/bootloader/chapter23-bootrom-efuse-otp)에서 자세히 다뤘습니다. 이 장은 그 동작이 *실패했을 때* 무엇을 어떤 순서로 확인하는지에 집중합니다. 메커니즘을 아는 것과 고장 난 메커니즘을 진단하는 것은 다른 기술입니다.

## ROM 단계가 어려운 이유

BootROM 단계의 디버깅이 어려운 이유는 세 가지입니다. 첫째, 코드를 바꿀 수 없습니다. 펌웨어라면 printf 한 줄을 넣어 보겠지만 ROM은 마스크(칩 제조 과정의 회로 패턴)에 새겨져 있습니다. 둘째, ROM이 출력하는 정보가 적습니다. 칩에 따라 UART로 짧은 로그를 내보내기도 하지만, 아무 출력 없이 조용히 다음 후보로 넘어가는 칩도 많습니다. 셋째, 보안 설정에 따라 ROM 실행 중에는 디버거 접근이 막혀 있을 수 있습니다.

이 상황은 블랙박스 기계를 고치는 일과 비슷합니다. 뚜껑을 열 수는 없지만, 입력을 바꿔 보고 출력을 관찰하면 안에서 무슨 일이 일어나는지 상당 부분 추리할 수 있습니다. ROM의 입력은 boot mode 핀과 fuse 설정이고, 출력은 부트 미디어 버스의 신호와 다운로드 모드 진입 여부입니다.

SW와 HW 쪽에서 보이는 단서를 나란히 놓으면 다음과 같습니다.

| SW 쪽에서 보이는 것 | HW 쪽에서 측정할 것 | 알 수 있는 것 |
|---|---|---|
| UART 무출력 | boot mode 핀 전압 | ROM이 어느 미디어를 고를지 |
| 디버거로 보면 PC가 ROM 주소 범위 안 | 부트 미디어 버스 신호 | ROM이 미디어를 읽으려 시도하는지 |
| PC에서 낯선 USB 장치가 보임 | (없음) | ROM이 모든 미디어에 실패하고 다운로드 모드로 감 |
| fuse 값이 예상과 다름 | (디버거로 읽기) | 보안 설정이 부팅을 막고 있는지 |

## BootROM의 흐름 다시 보기

진단 순서를 정하려면 ROM의 흐름을 단순화해 머릿속에 두는 편이 좋습니다. 칩마다 세부는 다르지만 대부분 아래와 같은 뼈대를 갖고 있습니다. 리셋이 풀리면 boot mode 핀을 읽고, fuse 설정을 확인하고, 우선순위에 따라 부트 미디어(SPI flash, eMMC, SD 카드 등)를 차례로 시도합니다. 모두 실패하면 USB나 UART로 이미지를 받는 다운로드 모드로 들어갑니다.

![BootROM의 흐름과 관찰 지점 — boot mode 핀, fuse, 미디어 시도, 다운로드 모드마다 밖에서 볼 수 있는 단서가 있다](/images/blog/debugging/embedded/diagrams/ch12-bootrom-flow.svg)

그림 오른쪽의 노란 상자가 각 단계에서 밖에서 확인할 수 있는 단서입니다. 진단은 이 흐름을 위에서 아래로 따라가며 "ROM이 어디까지 갔는가"를 확인하는 작업입니다. Ch 10에서 bring-up을 계단에 비유했다면, ROM 단계는 그 계단 한 칸 안에 숨은 작은 계단입니다.

## boot mode 핀과 strap

boot mode 핀(ROM이 부팅할 미디어를 고를 때 읽는 핀)은 보통 strap 핀이라고도 부릅니다. 리셋이 풀리는 순간 핀의 전압 레벨을 읽어 값을 정하고, 그 뒤에는 다른 용도로 쓰이기도 합니다. 그래서 보드에서는 저항으로 이 핀을 high나 low에 묶어 둡니다.

bring-up에서 가장 흔한 ROM 문제가 이 strap입니다. 저항 하나가 빠졌거나, 값이 틀렸거나, 같은 핀에 붙은 다른 회로가 리셋 순간에 전압을 끌어당기는 경우입니다. 확인 방법은 단순합니다. 멀티미터로 각 strap 핀의 전압을 재고, 보드 회로도와 칩 문서의 boot mode 표를 대조합니다.

다만 멀티미터 값이 맞아도 안심할 수는 없습니다. strap은 *리셋이 풀리는 순간*의 값만 의미가 있습니다. 평소에는 high였는데 리셋 해제 순간에만 다른 회로 때문에 잠깐 low로 떨어진다면, 멀티미터로는 보이지 않습니다. 의심스러우면 스코프로 리셋 신호와 strap 핀을 함께 걸고 리셋 해제 순간의 레벨을 봅니다. 사진의 셔터가 눌린 순간만 기록되는 것과 같아서, 그 순간을 정확히 잡아야 합니다.

## ROM이 남기는 흔적 — 로그와 상태 레지스터

ROM이 아무 말도 하지 않는 것 같아도 흔적을 남기는 경우가 많습니다. 칩 문서를 뒤지면 대개 다음 중 일부가 있습니다.

- **ROM UART 로그:** 특정 핀이나 fuse 설정으로 ROM이 부팅 과정을 UART에 짧게 출력하게 할 수 있는 칩이 있습니다.
- **ROM 상태 레지스터:** ROM이 마지막으로 시도한 미디어, 실패 이유 코드를 칩 내부 레지스터나 SRAM의 정해진 위치에 남기는 칩이 있습니다.
- **LED 신호:** 보드 차원에서 오류를 깜빡임 패턴으로 알리는 경우도 있습니다. Raspberry Pi는 부팅에 실패하면 초록색 LED의 깜빡임 패턴으로 오류 종류를 알려 주고, 공식 문서에 패턴별 의미가 정리돼 있습니다.

디버거가 붙는다면 ROM 실행 중에 코어를 멈추고 PC(프로그램 카운터, 지금 실행 중인 명령어 주소)를 읽어 보는 것만으로도 단서가 됩니다. 아래는 OpenOCD 콘솔에서 코어를 멈추고 PC와 ROM 상태 영역을 읽는 순서입니다. 주소는 모두 예시이고, 실제 ROM 주소 범위와 상태 영역 위치는 칩 문서를 봐야 합니다.

```text
> halt
> reg pc
pc (/32): 0x00004a18
> mdw 0x00100000 4
0x00100000: 00000003 00000002 e0000011 00000000
> resume
```

PC가 ROM 주소 범위 안의 같은 위치를 계속 맴돈다면 ROM이 무언가를 기다리고 있거나 무한 루프에 빠진 것입니다. 몇 번 멈췄다 풀었다 하며 PC를 모아 보면, ROM이 미디어 읽기를 반복 시도하는지 아예 한 곳에 멈춰 있는지 구분할 수 있습니다. 상태 영역의 값은 칩 문서의 정의와 대조해 해석합니다.

## eFuse와 보안 부팅 설정 확인

eFuse(한 번 끊으면 되돌릴 수 없는 칩 내부 퓨즈)에는 boot mode를 덮어쓰는 설정, 보안 부팅 활성화 여부, 디버그 차단 여부 같은 값이 들어 있습니다. strap 핀이 맞는데도 ROM이 엉뚱한 미디어를 고른다면, fuse가 strap보다 우선하도록 설정돼 있을 수 있습니다.

특히 위험한 경우는 **보안 부팅이 켜진 칩**입니다. 보안 부팅이 켜져 있으면 ROM은 이미지의 서명을 검증하고, 서명이 맞지 않으면 그 이미지를 버리고 다음 후보로 넘어갑니다. SW 쪽에서는 "이미지를 분명히 구웠는데 부팅이 안 된다"로 보입니다. 개발용 샘플이 실수로 양산용 fuse 설정을 받았거나, 서명 키가 다른 이미지를 구운 경우입니다. 이 경우 fuse 값을 디버거로 읽어 보안 설정을 확인하는 것이 가장 빠릅니다. fuse는 되돌릴 수 없으므로, 확인은 반드시 *읽기*로만 하고 쓰기 명령은 절대 실험 삼아 쓰지 않습니다.

## 부트 미디어 접근 실패

strap과 fuse가 맞는데도 부팅이 안 된다면, ROM이 미디어를 읽으려다 실패하는 경우입니다. 이때는 미디어 버스에 스코프나 로직 분석기(여러 디지털 신호를 동시에 기록해 보여 주는 장비)를 겁니다. SPI flash라면 CS(칩 선택)와 CLK(클럭), eMMC라면 CMD 선을 봅니다.

미디어 버스에서 볼 수 있는 상황은 대략 세 가지입니다.

| 버스에서 보이는 것 | 해석 | 다음 행동 |
|---|---|---|
| 아무 신호도 없음 | ROM이 이 미디어를 시도조차 하지 않음 | strap·fuse로 돌아가 선택된 미디어 확인 |
| 짧은 시도 후 멈춤 | ROM이 읽었지만 응답이 이상하거나 이미지가 틀림 | 미디어 전원·핀, 이미지 형식·위치 확인 |
| 같은 시도가 반복됨 | ROM이 재시도 중 | 신호 품질(클럭 속도, 풀업 저항) 확인 |

이미지 형식과 위치도 흔한 원인입니다. ROM은 미디어의 정해진 오프셋에서 정해진 헤더 형식을 찾습니다. 이미지를 파일 시스템에 복사하거나 오프셋을 틀리게 구우면, ROM 입장에서는 빈 미디어와 같습니다. 서점에서 정해진 서가에 꽂히지 않은 책은 아무리 좋은 책이어도 찾을 수 없는 것과 같습니다.

## 구운 이미지가 정말 그 자리에 있나

ROM 단계 문제의 상당수는 HW도 ROM도 아닌 **이미지 배치**에서 나옵니다. 그래서 미디어 버스를 보기 전후로, 구운 이미지가 ROM이 기대하는 자리와 형식에 정말 있는지 직접 확인하는 습관이 필요합니다. 확인은 두 방향으로 합니다. 하나는 이미지 파일 자체의 헤더가 칩 문서의 형식과 맞는지, 다른 하나는 미디어의 해당 위치에 그 이미지가 실제로 쓰여 있는지입니다.

이미지 파일의 앞부분은 `xxd`로 바로 볼 수 있습니다. ROM이 찾는 헤더에는 보통 매직 넘버(형식을 알아보기 위한 고정된 바이트열), 이미지 크기, 로드 주소 같은 값이 정해진 오프셋에 들어 있습니다. 칩 문서의 헤더 정의와 한 바이트씩 대조합니다.

eMMC라면 **boot partition**(eMMC 안의 부팅 전용 영역)과 사용자 영역을 구분해야 합니다. 리눅스에서는 boot partition이 `/dev/mmcblk0boot0`, `/dev/mmcblk0boot1` 같은 별도 장치로 보이고, 기본적으로 쓰기 보호가 걸려 있습니다. 아래는 다른 보드나 호스트에서 eMMC를 읽어, ROM이 볼 위치에 이미지가 들어 있는지 확인하고 필요하면 boot partition에 쓰는 예시입니다. 장치 이름과 오프셋은 보드에 따라 다르므로 모두 예시입니다.

```bash
xxd -l 64 boot.img                           # 이미지 헤더 확인

xxd -l 64 /dev/mmcblk0boot0                  # boot partition 앞부분이 같은지 비교

echo 0 > /sys/block/mmcblk0boot0/force_ro    # boot partition 쓰기 보호 해제
dd if=boot.img of=/dev/mmcblk0boot0 conv=fsync

mmc bootpart enable 1 1 /dev/mmcblk0         # mmc-utils: boot0에서 부팅하도록 설정
```

마지막 줄의 boot partition 활성화 설정도 자주 빠지는 단계입니다. 이미지가 boot0에 있어도 eMMC 설정이 boot partition 부팅을 가리키지 않으면 ROM은 그곳을 읽지 않습니다. SPI flash라면 플래시 프로그래머로 앞부분을 다시 읽어 와 이미지 파일과 `cmp`로 비교하는 것만으로 굽기 실패를 가려낼 수 있습니다.

## 마지막 안전망 — 다운로드 모드

모든 미디어에 실패하면 ROM은 대개 다운로드 모드로 들어갑니다. 이 모드에서는 USB나 UART로 PC에서 이미지를 받아 SRAM에 올려 실행할 수 있습니다. 칩 회사마다 이름과 도구가 다릅니다. NXP i.MX 계열은 Serial Downloader 모드와 `uuu` 도구를, Rockchip은 MaskROM 모드와 `rkdeveloptool`을, Allwinner는 FEL 모드와 `sunxi-fel`을 씁니다.

다운로드 모드는 진단 도구이기도 합니다. PC에서 해당 USB 장치가 보인다면 "ROM은 살아 있고, 모든 미디어에 실패했다"는 사실이 확인됩니다. 아래는 PC 쪽에서 칩이 다운로드 모드로 들어왔는지 확인하는 명령 예시입니다. 실제로 쓸 도구는 칩 계열에 따라 하나만 고르면 됩니다.

```bash
# 공통: USB 장치 목록에서 칩 벤더의 장치가 보이는지 확인
lsusb

# 칩 계열별 도구 (해당하는 것만 사용)
uuu -lsusb            # NXP i.MX
rkdeveloptool ld      # Rockchip
sunxi-fel version     # Allwinner
```

장치가 보이면 다운로드 모드로 Ch 10의 "가장 작은 첫 코드"를 올려 실행해 볼 수 있습니다. JTAG이 막힌 칩에서도 이 경로로 코드를 돌릴 수 있어서, bring-up 초반에 매우 유용한 우회로가 됩니다.

## 작은 예시 — 이미지를 구웠는데 아무 반응이 없는 보드

가상의 사례를 따라가 보겠습니다. eMMC에 부트 이미지를 구웠는데 보드가 아무 출력 없이 멈춥니다. Ch 11의 점검으로 전원·클럭·리셋은 정상임을 확인했습니다.

먼저 strap 핀을 잽니다. eMMC 부팅에 맞는 값입니다. 디버거로 PC를 몇 번 읽어 보니 ROM 주소 범위 안의 여러 위치를 오갑니다. ROM이 무언가를 하고 있다는 뜻입니다. eMMC CMD 선에 로직 분석기를 걸어 보니 ROM이 명령을 보내고 응답도 받고 있습니다. 그런데 몇 번 읽고는 멈추고, 잠시 뒤 PC에서 다운로드 모드 USB 장치가 보입니다.

여기까지의 단서를 모으면, ROM은 eMMC를 읽었지만 원하는 이미지를 찾지 못했습니다. 이미지 굽기 스크립트를 확인해 보니 이미지가 eMMC의 사용자 영역에 들어가 있었고, 이 칩의 ROM은 boot partition(eMMC 안의 부팅 전용 영역)에서 이미지를 찾도록 돼 있었습니다. 위치를 고치자 부팅이 시작됐습니다. 이 사례에서 HW는 모두 정상이었고, 원인은 ROM의 기대와 이미지 배치의 불일치였습니다.

## 자주 하는 실수

- **strap을 멀티미터로만 확인합니다.** 리셋 해제 순간의 레벨이 다를 수 있습니다. 의심스러우면 스코프로 그 순간을 잡습니다.
- **fuse를 실험 삼아 씁니다.** fuse는 되돌릴 수 없습니다. 개발 샘플 하나를 영구히 잃을 수 있습니다.
- **이미지 위치와 형식을 확인하지 않습니다.** ROM은 정해진 오프셋과 헤더만 봅니다. 파일 시스템 위의 파일은 보지 못합니다.
- **다운로드 모드를 활용하지 않습니다.** PC에서 USB 장치가 보이는지만 확인해도 ROM이 살아 있다는 큰 단서를 얻습니다.
- **칩 문서의 boot 장을 건너뜁니다.** ROM 동작은 칩마다 다르고, 진단에 필요한 상태 레지스터 정보는 대개 그 장에만 있습니다.

## 정리

- BootROM은 수정할 수 없으므로, 밖에서 관찰할 수 있는 단서로 ROM이 어디까지 갔는지 추리합니다.
- 진단 순서는 ROM의 흐름을 따라 **boot mode 핀 → fuse → 미디어 접근 → 다운로드 모드**입니다.
- strap 핀은 리셋 해제 순간의 값만 의미가 있으므로, 필요하면 스코프로 그 순간을 봅니다.
- ROM UART 로그, ROM 상태 레지스터, 디버거로 읽은 PC가 ROM 내부 진행을 알려 주는 흔적입니다.
- 보안 부팅이 켜진 칩은 서명이 맞지 않는 이미지를 조용히 버립니다. fuse는 읽기로만 확인합니다.
- 미디어 버스 신호로 ROM의 시도 여부를 보고, 이미지 위치·형식을 ROM의 기대와 대조합니다.
- 다운로드 모드 진입은 "ROM은 살아 있고 미디어에서 실패했다"는 확인이자, JTAG 없이 코드를 올리는 우회로입니다.
