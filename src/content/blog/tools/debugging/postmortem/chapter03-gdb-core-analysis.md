core 파일이 손에 들어왔습니다. *어디서 죽었나*, *왜 죽었나*, *어떤 변수가 잘못된 값을 가졌나*를 차례로 물어야 합니다. 이 장은 GDB로 core를 분석하는 흐름을 실제 core로 따라가고, 자주 만나는 여덟 가지 패턴을 하나씩 재현해 각 core에서 원인을 짚습니다.

모든 core와 출력은 Debian 13.7 arm64 QEMU VM(커널 6.12.116, GCC 14.2.0, GDB 16.3, glibc 2.41)에서 만들었습니다. 시험 프로그램은 `-g -O0`로 빌드했고, 시스템 라이브러리에는 debuginfo를 설치하지 않았습니다. 그래서 libc 안의 프레임은 `??`로 나옵니다. 이 빈칸을 채우는 방법은 [Ch 4](/blog/tools/debugging/postmortem/chapter04-debuginfod-minidump-automation)에서 다룹니다.

## 열기

첫 예제는 설정 파일을 읽는 C++ 서버입니다. 워커 스레드 둘은 condition variable에서, IO 스레드는 `epoll_wait()`에서 기다리고, 메인 스레드가 설정을 읽다가 죽습니다. 버그는 빈 줄의 크기를 `(size_t)-1`로 돌려주는 `get_size()`입니다.

```cpp title="server.cpp (일부)"
static size_t get_size(const std::string &line) {
    return line.empty() ? static_cast<size_t>(-1) : line.size();   // bug: empty line
}

static std::vector<std::string> load_config(const char *path) {
    std::ifstream f(path);
    std::vector<std::string> items;
    std::string line;
    items.reserve(get_size(line));
    while (std::getline(f, line)) items.push_back(line);
    return items;
}
```

인자 순서는 실행 파일이 먼저, core가 나중입니다. 실행 파일을 주지 않으면 GDB는 심볼이 없어 주소만 보여 줍니다.

```bash title="open-core.gdb.sh"
gdb ./server core.server
```

GDB는 core의 NT_PRSTATUS로 스레드를, NT_FILE과 NT_AUXV로 공유 라이브러리를 찾고, NT_PRPSINFO의 명령줄을 찍습니다([Ch 2](/blog/tools/debugging/postmortem/chapter02-elf-core-format)).

```text
[New LWP 7008]
[New LWP 7010]
[New LWP 7009]
[New LWP 7011]
[Thread debugging using libthread_db enabled]
Using host libthread_db library "/lib/aarch64-linux-gnu/libthread_db.so.1".
Core was generated by `./server /etc/hostname'.
Program terminated with signal SIGABRT, Aborted.
#0  0x0000ffffae818020 in ?? () from /lib/aarch64-linux-gnu/libc.so.6
[Current thread is 1 (Thread 0xffffaec28020 (LWP 7008))]
```

마지막 `#0`은 가장 안쪽 프레임이지만, SIGABRT core에서는 `abort()` 안의 libc 코드입니다. 원인은 몇 프레임 위에 있습니다.

### coredumpctl debug — 자동

systemd-coredump가 저장한 core는 `coredumpctl debug`로 바로 엽니다. 실행 파일 경로는 저장된 메타데이터에서 가져옵니다.

```bash
coredumpctl list
coredumpctl debug 2951
```

스크립트에서는 `--debugger-arguments`로 GDB 옵션을 넘기거나, GDB를 직접 batch 모드로 부릅니다. `-batch`는 명령을 실행하고 끝나며 inferior를 실행하지 않습니다. `-nx`는 `.gdbinit`을 읽지 않게 해서 결과가 사용자 설정에 흔들리지 않게 합니다.

```bash title="gdb-core-batch.sh"
gdb -q -nx -batch \
  -ex 'set pagination off' \
  -ex 'bt' \
  -ex 'thread apply all bt' \
  ./server core.server
```

## 첫 명령들

### bt — 죽은 곳

```text
(gdb) bt
#0  0x0000ffffae818020 in ?? () from /lib/aarch64-linux-gnu/libc.so.6

#2  0x0000ffffae7b1a84 [PAC] in abort () from /lib/aarch64-linux-gnu/libc.so.6
#3  0x0000ffffaea3c0c4 [PAC] in __gnu_cxx::__verbose_terminate_handler() () from /lib/aarch64-linux-gnu/libstdc++.so.6
#4  0x0000ffffaea39650 [PAC] in ?? () from /lib/aarch64-linux-gnu/libstdc++.so.6
#5  0x0000ffffaea30a64 [PAC] in std::terminate() () from /lib/aarch64-linux-gnu/libstdc++.so.6
#6  0x0000ffffaea399e8 [PAC] in __cxa_throw () from /lib/aarch64-linux-gnu/libstdc++.so.6
#7  0x0000ffffaea30dc8 [PAC] in std::__throw_length_error(char const*) () from /lib/aarch64-linux-gnu/libstdc++.so.6
#8  0x0000aaaadef41ee8 [PAC] in std::vector<std::__cxx11::basic_string<char, ...> >::reserve (this=0xfffff63a01d0, __n=18446744073709551615) at /usr/include/c++/14/bits/vector.tcc:71
#9  0x0000aaaadef41828 in load_config (path=0xfffff63a0e82 "/etc/hostname") at server.cpp:32
#10 0x0000aaaadef41954 in main (argc=2, argv=0xfffff63a0388) at server.cpp:40
(#8의 템플릿 인자 줄임)
```

`#0`이 가장 깊은 호출이고 아래로 갈수록 바깥 호출입니다. 맨 아래 `main`이 진입점에 가깝습니다. 읽는 순서는 이렇습니다.

- `#0`–`#7`은 libc·libstdc++입니다. uncaught exception이 `std::terminate()` → `abort()` → `raise()`로 이어졌습니다.
- `#8`이 처음 나오는 우리 쪽 코드 경계입니다. `__n=18446744073709551615`는 `(size_t)-1`이고, `reserve()`가 `length_error`를 던졌습니다.
- `#9`에서 그 값을 넘긴 곳(`server.cpp:32`)을 찾습니다.

`[PAC]`는 GDB가 복귀 주소에서 포인터 인증 서명을 떼어 냈다는 표시입니다. Debian 13의 `dpkg-buildflags --get CFLAGS`에는 `-mbranch-protection=standard`와 `-fstack-protector-strong`이 들어 있어서 배포 패키지인 libc·libstdc++ 프레임에 이 표시가 붙습니다. 손으로 부른 `gcc`의 기본값에는 둘 다 없습니다.

### bt full

`bt full`은 각 프레임의 지역 변수까지 찍습니다. debuginfo가 없는 프레임은 `No symbol table info available.`로 넘어갑니다.

```text
(gdb) frame 9
#9  0x0000aaaadef41828 in load_config (path=0xfffff63a0e82 "/etc/hostname") at server.cpp:32
32	    items.reserve(get_size(line));
(gdb) info locals
f = <incomplete type>
items = std::vector of length 0, capacity 0
line = ""
```

`line`이 빈 문자열이고 `items`가 비어 있습니다. 빈 `line`이 `get_size()`로 들어갔다는 것이 지역 변수만으로 드러납니다. `f`가 `<incomplete type>`인 것은 libstdc++의 `std::ifstream` 정의가 debuginfo 없이는 불완전하기 때문입니다.

`*`가 시그널을 받은 스레드입니다. 나머지 셋은 libc 안에서 멈춰 있지만, 어디서 기다리는지는 이 표만으로 보이지 않습니다.

### thread apply all bt

모든 스레드의 콜스택을 한 번에 찍습니다. 여러 스레드가 얽힌 사고에서는 이 명령이 첫 명령입니다. 출력에서 우리 코드가 처음 나오는 프레임까지만 옮겼습니다.

## siginfo — 죽음의 정체

`$_siginfo`는 core의 NT_SIGINFO를 `siginfo_t` 타입으로 보여 줍니다. 위 core는 이렇습니다.

```text
(gdb) p $_siginfo.si_signo
$4 = 6
(gdb) p $_siginfo.si_code
$5 = -6
(gdb) p $_siginfo._sifields._kill
$6 = {si_pid = 7008, si_uid = 0}
```

`si_code = -6`은 `SI_TKILL`입니다. 하드웨어 fault가 아니라 프로세스 7008이 스스로 `tgkill()`로 SIGABRT를 보냈다는 뜻이고, `abort()`가 그렇게 동작합니다. fault 시그널(SIGSEGV, SIGBUS, SIGILL)에서는 `si_code`가 양수이고 `_sigfault.si_addr`가 의미를 가집니다.

### si_code 해독

`linux-libc-dev 6.12.117`의 `asm-generic/siginfo.h` 값입니다.

| 시그널 | si_code |
| --- | --- |
| SIGSEGV | 1 MAPERR, 2 ACCERR, 3 BNDERR, 4 PKUERR, 8 MTEAERR, 9 MTESERR |
| SIGBUS | 1 ADRALN, 2 ADRERR, 3 OBJERR, 4 MCEERR_AR, 5 MCEERR_AO |
| SIGILL | 1 ILLOPC, 2 ILLOPN, 3 ILLADR, 4 ILLTRP, 5 PRVOPC, 6 PRVREG, 7 COPROC, 8 BADSTK |
| SIGFPE | 1 INTDIV, 2 INTOVF, 3 FLTDIV, 4 FLTOVF, 5 FLTUND, 6 FLTRES, 7 FLTINV, 8 FLTSUB |
| 사용자 전송 | 0 SI_USER (`kill`), -6 SI_TKILL (`tgkill`, `abort()`) |

### 정확한 진단

아래 패턴 절의 core 여덟 개에서 실제로 나온 조합입니다.

| 시그널 조합 | 진단 | 패턴 |
|-------------|------|------|
| SIGSEGV, MAPERR, `si_addr` = 0 | NULL 포인터에서 offset 0을 읽음 (vptr 로드) | 1 |
| SIGSEGV, MAPERR, `si_addr` = 작은 값(0x10) | NULL 포인터의 멤버 접근 | 1 |
| SIGSEGV, MAPERR, `si_addr` = 0x4141414141414151 | 문자열 바이트가 포인터 자리에 들어감 | 2, 6 |
| SIGBUS, ADRALN, PC = 0x0042424242424242 | 덮어쓴 복귀 주소로 점프 | 3 |
| SIGABRT, `SI_TKILL` | `assert()`, `abort()`, glibc의 heap 검사 | 5, 8 |
| SIGSTOP, `si_code` 128 | `gcore`로 뜬 core, 프로세스는 죽지 않았음 | 4 |
| SIGSEGV, MAPERR, `si_addr`가 `$sp` 바로 아래 | 스택 끝을 넘음 | 7 |

`si_addr`가 매핑 안에 있는지는 `info proc mappings`의 표에서 찾습니다. 위 core의 표는 실행 파일·libm·libc·libgcc_s·libstdc++·ld.so의 매핑 22줄이고, NT_FILE 내용 그대로입니다(익명 매핑은 표에 없습니다).

## 프레임 이동

`frame N`으로 프레임을 고르고 `list`로 그 줄 주변 소스를 봅니다.

```text
(gdb) frame 9
#9  0x0000aaaadef41828 in load_config (path=0xfffff63a0e82 "/etc/hostname") at server.cpp:32
32	    items.reserve(get_size(line));
(gdb) list
32	    items.reserve(get_size(line));
33	    while (std::getline(f, line)) items.push_back(line);
34	    return items;
35	}
...
(gdb) p get_size(line)
You can't do that without a process to debug.
```

core에서는 함수를 호출할 수 없습니다. 함수를 부르려면 CPU에서 코드를 실행할 프로세스가 있어야 하는데, core는 메모리의 사진일 뿐입니다. 변수와 메모리를 읽는 표현식은 됩니다.

```text
(gdb) p line
$1 = ""
(gdb) p items
$2 = std::vector of length 0, capacity 0
(gdb) p path
$3 = 0xfffff63a0e82 "/etc/hostname"
```

`get_size()`를 부를 수는 없지만, `line`이 빈 문자열이라는 사실과 `#8`의 `__n=18446744073709551615`를 합치면 `get_size()`가 빈 문자열에 `(size_t)-1`을 돌려줬다는 결론이 나옵니다.

## info — 메타 정보

`info auxv`는 NT_AUXV를, `info proc mappings`는 NT_FILE을 보여 줍니다([Ch 2](/blog/tools/debugging/postmortem/chapter02-elf-core-format)). `info shared`는 동적 라이브러리만 보여 주고, `Syms Read` 열과 `(*)` 표시로 debuginfo가 있는지 알려 줍니다.

```text
(gdb) info shared
From                To                  Syms Read   Shared Object Library
0x0000ffffaea30880  0x0000ffffaeb4fe7c  Yes (*)     /lib/aarch64-linux-gnu/libstdc++.so.6
0x0000ffffae9535c0  0x0000ffffae96b4c8  Yes (*)     /lib/aarch64-linux-gnu/libgcc_s.so.1
0x0000ffffae7b19c0  0x0000ffffae8d74f4  Yes (*)     /lib/aarch64-linux-gnu/libc.so.6
0x0000ffffae6eda40  0x0000ffffae739594  Yes (*)     /lib/aarch64-linux-gnu/libm.so.6
0x0000ffffaebf8b80  0x0000ffffaec158a8  Yes (*)     /lib/ld-linux-aarch64.so.1
(*): Shared library is missing debugging information.
```

다섯 개 모두 `(*)`입니다. 동적 심볼(`raise`, `abort`)은 이름이 나오지만, 정적 함수와 소스 줄은 없어서 libc 프레임 여럿이 `??`였습니다.

## 변수 검사

### 단순

```text
(gdb) print x
(gdb) print obj.field
(gdb) print *p           # deref
(gdb) print arr[5]
(gdb) print *arr@10      # arr[0]부터 10개
```

`@`는 왼쪽 값부터 연속된 원소를 배열로 보여 줍니다. `main` 프레임에서 `p *argv@argc`를 하면 인자 배열이 한 번에 나옵니다.

```text
(gdb) frame 10
(gdb) p *argv@argc
$2 = {0xfffff63a0e79 "./server", 0xfffff63a0e82 "/etc/hostname"}
```


타입 정보가 없는 raw 메모리에 타입을 씌워 해석합니다. 자체 자료 구조나 공용체를 볼 때 씁니다.

## 자주 만나는 패턴

여덟 패턴을 한 프로그램(`patterns.cpp`)의 인자로 재현했습니다. `g++ -g -O0 -pthread -fno-stack-protector`로 빌드했고, 패턴 3만 스택 보호를 켠 빌드와 비교합니다.

### 패턴 1 — NULL 역참조

```cpp
struct Request {
    virtual ~Request() = default;
    virtual int process() { return id; }
    long pad = 0;
    int id = 7;
};

int handle_null(Request *req) { return req->process(); }       // 1
int handle_member(Request *req) { return req->id; }            // 1b
```

두 함수에 `nullptr`를 넘겼습니다. 가상 함수 호출은 객체의 첫 8바이트(vptr)부터 읽으므로 `si_addr`가 0이고, 멤버 접근은 그 멤버의 offset이 `si_addr`가 됩니다.

```text
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x0000aaaad14518c0 in handle_null (req=0x0) at patterns.cpp:17
(gdb) p $_siginfo._sifields._sigfault.si_addr
$3 = (void *) 0x0
(gdb) x/i $pc
=> 0xaaaad14518c0 <_Z11handle_nullP7Request+16>:	ldr	x0, [x0]

#0  0x0000aaaac09f18e8 in handle_member (req=0x0) at patterns.cpp:18
(gdb) p $_siginfo._sifields._sigfault.si_addr
$3 = (void *) 0x10
(gdb) x/i $pc
=> 0xaaaac09f18e8 <_Z13handle_memberP7Request+12>:	ldr	w0, [x0, #16]
```

`ldr w0, [x0, #16]`에서 `x0`이 0이므로 0x10을 읽었습니다. `id`는 vptr(8바이트)과 `pad`(8바이트) 뒤 offset 16에 있습니다. `si_addr`, 명령의 offset, 구조체 배치가 서로 맞으면 NULL 포인터라고 결론을 내립니다.

### 패턴 2 — 손상된 포인터

`Session` 구조체 전체를 `'A'`로 채운 뒤 `s->req->id`를 읽었습니다.

```text
#0  handle_wild (s=0xffffd917b108) at patterns.cpp:21
21	int handle_wild(Session *s) { return s->req->id; }             // 2
(gdb) p $_siginfo._sifields._sigfault.si_addr
$3 = (void *) 0x4141414141414151
(gdb) info registers x0
x0             0x4141414141414141  4702111234474983745
```

`x0`이 `"AAAAAAAA"`이고 `si_addr`는 거기에 `id`의 offset 0x10을 더한 값입니다. 포인터 자리에 문자열이 들어갔으니 버퍼 오버플로나 use-after-free를 의심합니다. 어느 쪽인지는 core만으로 가려지지 않아서, [ASan](/blog/tools/debugging/sanitizers/chapter02-asan-ubsan) 빌드로 다시 돌려 덮어쓴 위치를 찾습니다.

### 패턴 3 — 스택 손상

16바이트 버퍼에 `'B'` 56개를 `strcpy()`했습니다.

```cpp
void copy_name(const char *src) {
    char buf[16];
    strcpy(buf, src);
    std::printf("%s\n", buf);
}
void handle_stack(const char *src) { copy_name(src); }
```

x86-64와 결과가 다릅니다. `copy_name`의 디스어셈블은 `stp x29, x30, [sp, #-48]!`로 프레임 레코드(x29, x30)를 `sp`에 두고, `buf`는 `sp+0x20`에 둡니다. 프레임 레코드가 지역 변수보다 낮은 주소에 있으므로, `buf`를 넘친 바이트는 `copy_name`의 복귀 주소가 아니라 호출한 `handle_stack`의 프레임 레코드를 덮습니다. 그래서 `copy_name`은 정상으로 돌아가고, `handle_stack`이 돌아갈 때 `0x4242424242424242`로 점프합니다.

```text
Program terminated with signal SIGBUS, Bus error.
#0  0x0042424242424242 in ?? ()
#1  0x4242424242424242 in ?? ()
Backtrace stopped: previous frame identical to this frame (corrupt stack?)
(gdb) p $_siginfo.si_code
$2 = 1
(gdb) info registers x29 x30 pc
x29            0x4242424242424242  4774451407313060418
x30            0x4242424242424242  4774451407313060418
pc             0x42424242424242    0x42424242424242
```

시그널은 SIGSEGV가 아니라 SIGBUS(`BUS_ADRALN`)였습니다. 0x…42는 4바이트 정렬이 아니어서 명령을 가져오기 전에 PC 정렬 fault가 났습니다. 스택을 보면 덮어쓴 범위가 보입니다.

```text
(gdb) x/12gx $sp-48
0xffffe1627d30:	0x4242424242424242	0x4242424242424242
0xffffe1627d40:	0x4242424242424242	0x4242424242424242
0xffffe1627d50:	0x4242424242424242	0x4242424242424242
0xffffe1627d60:	0x4242424242424242	0x0000ffffb9472200
0xffffe1627d70:	0x0000ffffe1627f68	0x0000ffffb9907000
```

0x…d60의 두 번째 칸 `0x0000ffffb9472200`에서 `'B'`가 끝납니다. 하위 바이트 0x00은 `strcpy()`가 붙인 NUL 종료 문자입니다. 길이 검사 없는 복사(`strcpy`, `gets`, `sprintf`)를 의심합니다.

같은 코드를 `-fstack-protector-strong -mbranch-protection=standard`로 빌드하면 덮어쓴 직후 `copy_name` 안에서 잡힙니다. 프로세스는 `*** stack smashing detected ***: terminated`를 찍고 SIGABRT로 죽었고, 콜스택에 덮어쓴 함수가 남았습니다.

```text
#4  0x0000ffffbc9a9e80 [PAC] in __fortify_fail () from /lib/aarch64-linux-gnu/libc.so.6
#5  0x0000ffffbc9aaf38 [PAC] in __stack_chk_fail () from /lib/aarch64-linux-gnu/libc.so.6
#6  0x0000aaaacc141c00 [PAC] in copy_name (src=0xaaaacc143570 'B' <repeats 56 times>) at patterns.cpp:27
#7  0x0000424242424242 [PAC] in ?? ()
```

스택 보호가 없으면 콜스택이 통째로 사라지고, 있으면 덮어쓴 함수(`#6`)와 입력(`src`)이 남습니다. 배포 빌드에서 이 옵션을 켜 두는 이유입니다.

### 패턴 4 — 데드락 (hung core)

세 스레드가 두 mutex를 서로 다른 순서로 잡도록 만들고, 멈춘 프로세스에 `gcore`를 걸었습니다.

```cpp
void cache_update() { std::lock_guard<std::mutex> a(cache_mu); usleep(100000); std::lock_guard<std::mutex> b(log_mu); }
void logger_write() { std::lock_guard<std::mutex> a(log_mu); usleep(100000); std::lock_guard<std::mutex> b(cache_mu); }
```

```text
(gdb) thread apply all bt 4
Thread 4 (Thread 0xffffab7af160 (LWP 7254)):
#1  0x0000ffffab8e9750 [PAC] in pthread_mutex_lock () from /lib/aarch64-linux-gnu/libc.so.6
#2  0x0000aaaac4511edc [PAC] in __gthread_mutex_lock (__mutex=0xaaaac4530180 <log_mu>) at ...
Thread 3 (Thread 0xffffaaf9f160 (LWP 7255)):
#1  0x0000ffffab8e9750 [PAC] in pthread_mutex_lock () from /lib/aarch64-linux-gnu/libc.so.6
#2  0x0000aaaac4511edc [PAC] in __gthread_mutex_lock (__mutex=0xaaaac4530150 <cache_mu>) at ...
Thread 2 (Thread 0xffffaa78f160 (LWP 7256)):
#1  0x0000ffffab8e9750 [PAC] in pthread_mutex_lock () from /lib/aarch64-linux-gnu/libc.so.6
#2  0x0000aaaac4511edc [PAC] in __gthread_mutex_lock (__mutex=0xaaaac4530150 <cache_mu>) at ...
(#0, #3 생략)
```

스레드 셋이 모두 `pthread_mutex_lock()`에서 기다립니다. 누가 무엇을 들고 있는지는 glibc mutex의 `__owner`(소유 스레드의 TID)가 알려 줍니다.

```text
(gdb) p cache_mu._M_mutex.__data
$3 = {__lock = 2, __count = 0, __owner = 7254, __nusers = 1, __kind = 0, __spins = 0, __list = {__prev = 0x0, __next = 0x0}}
(gdb) p log_mu._M_mutex.__data.__owner
$2 = 7255
```

| 스레드 (LWP) | 들고 있는 락 | 기다리는 락 |
| --- | --- | --- |
| 4 (7254) | `cache_mu` | `log_mu` |
| 3 (7255) | `log_mu` | `cache_mu` |
| 2 (7256) | 없음 | `cache_mu` |

7254와 7255가 서로를 기다리는 순환이 데드락이고, 7256은 그 뒤에 줄을 섰을 뿐입니다. `__lock = 2`는 기다리는 스레드가 있다는 표시입니다. `gcore`로 뜬 core라 `$_siginfo.si_signo`는 19(SIGSTOP), `si_code`는 128(SI_KERNEL)이었습니다.

### 패턴 5 — abort() / assert

`do_validate(-1)`이 `assert(x >= 0 && x < MAX_SIZE)`에 걸렸습니다. stderr에 남는 메시지가 실패한 조건을 그대로 알려 줍니다.

```text
patterns: patterns.cpp:35: void do_validate(int): Assertion `x >= 0 && x < MAX_SIZE' failed.
```

```text
(gdb) bt
#0  0x0000ffff878f8020 in ?? () from /lib/aarch64-linux-gnu/libc.so.6
#1  0x0000ffff878a6880 [PAC] in raise () from /lib/aarch64-linux-gnu/libc.so.6
#2  0x0000ffff87891a84 [PAC] in abort () from /lib/aarch64-linux-gnu/libc.so.6
#3  0x0000ffff8789f8bc [PAC] in ?? () from /lib/aarch64-linux-gnu/libc.so.6
#4  0x0000aaaae6071a88 [PAC] in do_validate (x=-1) at patterns.cpp:35
#5  0x0000aaaae6071da4 in main (argc=2, argv=0xffffe785c2d8) at patterns.cpp:56
(gdb) frame 4
(gdb) p x
$1 = -1
(gdb) p MAX_SIZE
$2 = 64
```

`#3`의 `??`는 debuginfo가 없어 이름이 빠진 glibc 내부 함수입니다([Ch 4](/blog/tools/debugging/postmortem/chapter04-debuginfod-minidump-automation)에서 debuginfod로 채웁니다). 실패한 조건과 변수 값이 함께 남으므로 SIGSEGV보다 진단이 빠릅니다. 단, 서비스 로그가 stderr를 버리면 조건 문자열은 core에서 찾기 어렵습니다.

### 패턴 6 — 가상 함수 호출 — vtable 손상

`Request`를 `delete`한 뒤 같은 크기를 `malloc()`해 `'A'`로 채우고, 해제된 포인터로 `process()`를 불렀습니다. glibc가 방금 해제한 청크를 그대로 돌려주므로 해제된 객체의 메모리가 덮입니다.

```text
#0  0x0000aaaaad6d1b18 in use_after_free () at patterns.cpp:42
42	    return r->process();
(gdb) x/i $pc
=> 0xaaaaad6d1b18 <_Z14use_after_freev+132>:	ldr	x1, [x0]
(gdb) p *r
$2 = {_vptr.Request = 0x4141414141414141, pad = 4702111234474983745, id = 1094795585}
(gdb) p $_siginfo._sifields._sigfault.si_addr
$3 = (void *) 0x4141414141414151
```

vptr가 `"AAAAAAAA"`이고, 프로그램은 vtable의 세 번째 칸(offset 0x10, `process`)을 읽으려다 죽었습니다. 소멸자 두 개(complete, deleting)가 앞의 두 칸을 차지합니다. 패턴 2와 `si_addr`가 같지만, 여기서는 `p *r`로 객체 전체가 덮였다는 것까지 보입니다. 객체가 해제된 시점과 장소는 core에 없으므로 ASan의 free 스택이 필요합니다.

### 패턴 7 — 무한 재귀

종료 조건이 없는 `recursive_fn()`이 스택 끝을 넘었습니다. core는 8,794,112바이트로, `ulimit -s` 8192(KiB) 스택이 거의 그대로 들어 있습니다.

```text
#0  recursive_fn (n=<error reading variable: Cannot access memory at address 0xffffd4781fcc>) at patterns.cpp:45
(gdb) p $_siginfo._sifields._sigfault.si_addr
$1 = (void *) 0xffffd4781fb0

$2 = (void *) 0xffffd4782010
(gdb) bt 3

#2  0x0000aaaae0f11b54 in recursive_fn (n=87356) at patterns.cpp:45
```

`si_addr`가 `$sp`보다 0x60 아래, 매핑되지 않은 guard 영역입니다. 프레임은 87,360개였고, 그냥 `bt`를 치면 전부 찍습니다. `bt N`은 안쪽 N개, `bt -N`은 바깥쪽 N개만 보여 줍니다. 바깥쪽 끝에서 재귀가 어디서 시작됐는지(`main`, `n=0`)를 봅니다.

### 패턴 8 — heap corruption

같은 포인터를 두 번 `free()`했습니다. glibc 2.41의 tcache 검사가 잡아 abort합니다.

```text
free(): double free detected in tcache 2
```

```text
(gdb) bt
#2  0x0000ffff9c7a1a84 [PAC] in abort () from /lib/aarch64-linux-gnu/libc.so.6
#3  0x0000ffff9c7fb5c8 [PAC] in ?? () from /lib/aarch64-linux-gnu/libc.so.6
#4  0x0000ffff9c81311c [PAC] in ?? () from /lib/aarch64-linux-gnu/libc.so.6
#5  0x0000ffff9c8131bc [PAC] in ?? () from /lib/aarch64-linux-gnu/libc.so.6
#6  0x0000ffff9c818324 [PAC] in free () from /lib/aarch64-linux-gnu/libc.so.6
#7  0x0000aaaac0311b90 [PAC] in double_free () at patterns.cpp:47
#8  0x0000aaaac0311e30 in main (argc=2, argv=0xffffe2fc08b8) at patterns.cpp:59
(#0, #1 생략)
```

`free()` 안에서 abort했다면 해제하려던 포인터가 이상하다는 뜻입니다. double free, 해제 후 쓰기로 깨진 청크 헤더, `malloc`이 돌려주지 않은 포인터 중 하나입니다. 이 경우 메시지가 원인을 알려 줬지만, glibc가 메시지를 내지 못하는 손상도 있습니다. 첫 번째 `free()`의 위치는 core에 없으므로 ASan으로 다시 돌려 할당·해제 두 스택을 모두 얻습니다.

```text
(gdb) set print pretty on              # 구조체를 줄 단위로 들여쓰기
(gdb) set print object on              # vptr로 실제 동적 타입 표시
(gdb) set print array on               # 배열을 원소별 줄로
(gdb) set print array-indexes on       # 원소 앞에 [i] 표시
(gdb) set print elements 100           # 문자열·배열 표시 한도 (기본 200)
(gdb) set print max-depth 5            # 중첩 구조체 표시 깊이

```

자주 쓰는 설정은 `~/.gdbinit`에 둡니다. 다만 스크립트에서 `-nx`로 부르면 이 파일을 읽지 않으므로, 자동화에는 필요한 설정을 `-ex`로 명시합니다.

## auto-load pretty-printer

Debian의 `libstdc++6`는 GDB용 pretty-printer 스크립트를 함께 설치합니다. 실행 파일이 그 라이브러리를 쓰면 GDB가 자동으로 읽습니다.

```text
(gdb) info auto-load python-scripts
Loaded  Script
Yes     /usr/share/gdb/auto-load/usr/lib/aarch64-linux-gnu/libstdc++.so.6.0.33-gdb.py
```

위에서 `items`가 `std::vector of length 0, capacity 0`으로 보인 것이 이 printer 덕분입니다. 경로 규칙은 `<auto-load 디렉터리>/<라이브러리의 실제 경로>-gdb.py`입니다. 자체 라이브러리도 `/usr/share/gdb/auto-load/usr/lib/libfoo.so.1-gdb.py`처럼 두면 같은 방식으로 적용됩니다. 출처를 모르는 스크립트가 실행되지 않도록 GDB는 `auto-load safe-path` 밖의 스크립트를 읽지 않습니다.

## Python 명령으로 자동화

여러 core에 같은 질문을 반복한다면 GDB Python API로 명령을 만듭니다. 시그널 정보와 스레드별 최상위 프레임을 찍는 `core-info` 명령입니다.

```python title="coreinfo.py"
import gdb

class CoreInfo(gdb.Command):
    """core dump 종합 정보."""
    def __init__(self):
        super().__init__("core-info", gdb.COMMAND_USER)

    def invoke(self, arg, from_tty):
        siginfo = gdb.parse_and_eval("$_siginfo")
        print("=== Death info ===")
        print(f"signal: {int(siginfo['si_signo'])}")
        print(f"si_code: {int(siginfo['si_code'])}")
        try:
            addr = int(siginfo['_sifields']['_sigfault']['si_addr'])
            print(f"si_addr: {addr:#x}")
        except gdb.error:
            pass

        print("=== Threads ===")
        for thread in gdb.selected_inferior().threads():
            thread.switch()
            frame = gdb.newest_frame()
            print(f"Thread {thread.num} (LWP {thread.ptid[1]}): {frame.name() or '??'}")

CoreInfo()
```

패턴 2와 패턴 4의 core에 돌린 결과입니다.

```text
$ gdb -q -nx -batch -ex "source coreinfo.py" -ex core-info ./patterns core.wild
=== Death info ===
signal: 11
si_code: 1
si_addr: 0x4141414141414151
=== Threads ===
Thread 1 (LWP 7116): handle_wild

$ gdb -q -nx -batch -ex "source coreinfo.py" -ex core-info ./patterns core.deadlock
=== Death info ===
signal: 19
si_code: 128
si_addr: 0x0
=== Threads ===
Thread 4 (LWP 7254): ??
Thread 3 (LWP 7255): ??
Thread 2 (LWP 7256): ??
Thread 1 (LWP 7252): ??
```

데드락 core에서 최상위 프레임이 모두 `??`인 것은 libc 내부에서 멈췄고 libc에 debuginfo가 없기 때문입니다. 최상위 프레임 하나로는 부족하므로, 실제로 쓸 명령이라면 우리 코드가 처음 나오는 프레임까지 `frame.older()`로 올라가도록 고칩니다.

## 정리

- `gdb <exe> <core>` 또는 `coredumpctl debug`로 열고, 자동화에는 `-q -nx -batch`를 씁니다.
- `bt`에서 라이브러리 프레임 위로 처음 나오는 우리 코드가 출발점입니다. `[PAC]`는 서명을 떼어 낸 복귀 주소입니다.
- `$_siginfo`의 `si_code`가 하드웨어 fault(양수)와 `abort()`·`kill`(0 이하)을 가릅니다.
- core에서는 함수를 호출할 수 없습니다(`You can't do that without a process to debug.`). 변수 읽기와 cast만 됩니다.
- arm64에서 NULL vptr 로드는 `si_addr` 0, 멤버 접근은 그 offset, 덮어쓴 복귀 주소는 SIGBUS `BUS_ADRALN`이었습니다.
- 데드락은 `thread apply all bt`와 mutex의 `__owner`로 누가 무엇을 쥐고 기다리는지 표를 만들어 찾습니다.
- 스택 보호(`-fstack-protector-strong`)가 있으면 덮어쓴 함수가 콜스택에 남습니다.
- use-after-free와 double free는 core가 "무엇이 깨졌는지"까지 알려 주고, "언제 깨졌는지"는 ASan이 알려 줍니다.
