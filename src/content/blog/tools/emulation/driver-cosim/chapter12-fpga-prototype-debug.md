Ch 10과 Ch 11은 시뮬레이션 안에서 버그를 찾는 이야기였습니다. 이 장은 RTL을 **FPGA**(프로그래밍으로 내부 회로를 바꿀 수 있는 칩)에 올려 실제 회로로 돌리는 **FPGA 프로토타입**으로 넘어갑니다. Ch 9에서 봤듯이 FPGA는 시뮬레이션보다 훨씬 빨라서 긴 스트레스 테스트와 실제 주변 장치 연결이 가능하지만, 내부 신호는 훨씬 보기 어렵습니다.

FPGA 디버깅에서 가장 흔하고 가장 답답한 상황은 **"시뮬레이션은 통과했는데 보드에서는 죽는다"**입니다. 이 장은 그 상황을 출발점으로 삼아, 시뮬레이션과 보드가 갈리는 이유를 정리하고 각 원인을 좁히는 도구를 소개합니다. FPGA 보드 위에서 드라이버를 처음 돌리는 SW 엔지니어와, 합성 결과를 들여다보는 HW 엔지니어가 함께 쓸 수 있는 체크리스트를 목표로 합니다.

## sim과 보드가 갈리는 이유

시뮬레이터는 RTL을 *이상적인 세계*에서 돌립니다. 모든 플립플롭이 정확히 같은 순간에 바뀌고, 신호는 지연 없이 전달되며, 두 클럭의 관계는 수학적으로 정확합니다. FPGA 보드는 *물리적인 세계*입니다. 신호가 배선을 지나는 데 시간이 걸리고, 클럭은 PLL(기준 클럭으로 원하는 주파수를 만드는 회로)에서 조금씩 흔들리며 나오고, 전원이 들어올 때의 상태도 시뮬레이션과 다릅니다.

연극에 비유하면, 시뮬레이션은 대본 리딩이고 FPGA는 실제 무대 리허설입니다. 대본상으로는 완벽한 장면도 무대에서는 소품이 제자리에 없거나 조명 전환이 반 박자 늦어 꼬일 수 있습니다. 같은 대본(RTL)이라도 무대(물리 회로)가 생기면 새로운 종류의 실수가 드러납니다.

![같은 RTL이 시뮬레이션과 FPGA 보드에서 갈리는 다섯 지점 — 초기값, 클럭, 메모리, 지연, 비동기 입력](/images/blog/driver-cosim/diagrams/ch12-sim-vs-board.svg)

다섯 지점을 SW 쪽 증상과 HW 쪽 확인 방법으로 나눠 정리하면 아래와 같습니다. 보드에서 이상한 증상이 보이면 이 표의 왼쪽 열부터 짚어 봅니다.

| 차이 | SW 쪽에서 보이는 증상 | HW 쪽에서 확인할 것 |
|---|---|---|
| 초기값 | 전원 직후 첫 동작만 실패, 리셋 버튼을 누르면 정상 | 리셋이 없는 레지스터, FPGA 초기값 설정 |
| 클럭 | 특정 주변 장치만 간헐적으로 오동작 | PLL lock, 클럭 도메인 경계 |
| 메모리 | 특정 주소나 크기에서만 데이터가 틀림 | ASIC 메모리를 대체한 BRAM·DDR 래퍼 |
| 지연 | 온도나 보드에 따라 결과가 달라짐 | 정적 타이밍 분석 보고서 |
| 비동기 입력 | 버튼, 외부 인터럽트, UART 수신이 가끔 이상함 | 동기화기 유무 |

## 내장 로직 분석기 — 트리거와 버퍼 깊이

보드 위 FPGA의 내부 신호를 보려면 **내장 로직 분석기**를 씁니다. 설계와 함께 FPGA 안에 작은 기록 회로를 넣어 두고, 지정한 조건이 되면 주변 신호를 FPGA 내부 메모리에 기록한 뒤 JTAG으로 꺼내 보는 방식입니다. AMD(Xilinx) FPGA에서는 Vivado의 **ILA**(Integrated Logic Analyzer), Intel(Altera) FPGA에서는 Quartus의 **Signal Tap**이 대표적입니다.

내장 로직 분석기는 비행기의 블랙박스와 닮았습니다. 블랙박스는 비행 전체를 기록하지 않고 마지막 일정 시간만 계속 덮어쓰며 보관합니다. 내장 로직 분석기도 FPGA 내부 메모리가 허락하는 만큼만, 트리거(기록을 멈추는 조건) 전후의 짧은 구간을 남깁니다. 그래서 두 가지를 미리 정해야 합니다.

- **무엇을 볼지:** 기록할 신호를 합성 전에 골라야 합니다. 신호를 바꾸려면 다시 합성해야 하고, 설계가 크면 합성에 몇 시간이 걸리기도 합니다.
- **언제 멈출지:** 트리거 조건을 잘 잡아야 원하는 순간이 버퍼에 들어옵니다. 증상이 나타난 순간보다 *원인이 의심되는 순간*을 트리거로 잡는 편이 좋습니다.

AMD FPGA에서는 RTL에 `mark_debug` 속성을 달아 기록 후보 신호를 표시할 수 있습니다. 아래 코드는 Ch 9의 DMA 인터럽트 경로에서 볼 신호를 표시한 예입니다.

```systemverilog
// 합성 뒤에도 이 신호들이 최적화로 사라지지 않고 ILA에 연결될 수 있게 표시
(* mark_debug = "true" *) logic        set_done;
(* mark_debug = "true" *) logic        clr_done;
(* mark_debug = "true" *) logic [3:0]  irq_stat;
(* mark_debug = "true" *) logic        irq_out;
```

이렇게 표시한 신호로 "set_done과 clr_done이 같은 cycle에 1"을 트리거로 잡으면, 3시간짜리 스트레스 테스트 중 충돌이 일어난 바로 그 순간 전후가 기록됩니다.

한 가지 주의할 점이 있습니다. 내장 로직 분석기를 넣으면 회로 배치와 배선이 바뀝니다. 그래서 타이밍이 빠듯한 설계에서는 분석기를 넣는 순간 증상이 사라지거나 다른 증상이 생기기도 합니다. 관찰하는 행위가 관찰 대상을 바꾸는 셈이라, 분석기를 넣고 증상이 사라졌다면 타이밍 문제를 먼저 의심합니다.

## CDC와 메타스테이빌리티

FPGA에서 시뮬레이션과 가장 다르게 동작하는 곳이 **CDC**(Clock Domain Crossing, 서로 다른 클럭으로 움직이는 두 영역 사이를 신호가 건너는 곳)입니다. 시뮬레이션에서는 신호가 깔끔하게 0이나 1로 바뀌지만, 실제 회로에서는 받는 쪽 클럭 에지가 신호가 바뀌는 순간과 겹치면 플립플롭이 잠깐 0도 1도 아닌 상태에 머물 수 있습니다. 이 현상을 **메타스테이빌리티**(metastability)라고 부릅니다.

동전을 세워서 튕기는 장면을 떠올리면 이해가 쉽습니다. 대부분은 바로 앞면이나 뒷면으로 떨어지지만, 가끔은 잠깐 모서리로 서서 흔들리다가 어느 쪽으로든 넘어집니다. 메타스테이블 상태의 플립플롭도 결국 0이나 1로 정해지지만, 그 전에 다음 회로가 값을 읽어 가면 회로마다 다른 값을 볼 수 있습니다.

이 문제를 막는 표준 방법이 **2단 동기화기**입니다. 받는 쪽 클럭으로 플립플롭을 두 개 연달아 두고, 두 번째 플립플롭의 출력만 사용합니다.

![2단 동기화기 — 도메인 A의 플립플롭에서 나온 req_a가 도메인 B의 FF1과 FF2를 차례로 지나며, FF1은 잠깐 불안정할 수 있지만 FF2가 한 cycle 동안 안정될 시간을 준다](/images/blog/driver-cosim/diagrams/ch12-cdc-sync.svg)

아래 코드는 동기화 없이 다른 도메인의 신호를 바로 쓰는 실수와, 2단 동기화기를 거친 올바른 형태를 나란히 보여 줍니다.

```systemverilog
// 회피: clk_a 도메인의 req_a를 clk_b 로직에서 바로 사용
always_ff @(posedge clk_b)
  if (req_a) state_b <= BUSY;

// Good: clk_b 플립플롭 두 개를 거친 뒤 사용
logic req_s1, req_s2;
always_ff @(posedge clk_b or negedge rst_b_n)
  if (!rst_b_n) {req_s2, req_s1} <= 2'b00;
  else          {req_s2, req_s1} <= {req_s1, req_a};

always_ff @(posedge clk_b)
  if (req_s2) state_b <= BUSY;
```

2단 동기화기는 *1비트* 신호에만 안전합니다. 여러 비트짜리 값(카운터, 주소)을 비트마다 따로 동기화하면, 비트마다 다른 cycle에 넘어와 중간에 엉뚱한 값이 보일 수 있습니다. 여러 비트는 Gray 코드(한 번에 한 비트만 바뀌는 숫자 표기), 핸드셰이크, 비동기 FIFO 같은 방법으로 넘깁니다.

시뮬레이터는 메타스테이빌리티를 재현하지 않습니다. 그래서 CDC 버그는 시뮬레이션에서 거의 잡히지 않고, FPGA나 실리콘에서 "가끔" 나타납니다. 상용 도구 중에는 RTL을 정적으로 분석해 동기화가 빠진 경계를 찾아 주는 CDC 검사 도구가 있으니, 프로젝트에서 쓸 수 있다면 FPGA에 올리기 전에 돌려 두는 편이 좋습니다.

## 타이밍 미충족이 만드는 간헐 오류

FPGA 합성 도구는 회로를 배치하고 배선한 뒤 **정적 타이밍 분석**(STA, 모든 신호 경로가 한 클럭 주기 안에 도착하는지 계산하는 것)을 합니다. 어떤 경로가 주어진 시간 안에 도착하지 못하면 *타이밍 미충족*이라고 보고합니다. 도구가 경고를 내도 비트스트림(FPGA에 올리는 설정 파일)은 만들어지는 경우가 많아서, 이 경고를 무시하고 보드에 올리는 일이 생깁니다.

타이밍이 미충족된 회로는 이어달리기에서 바통을 늦게 넘기는 주자와 같습니다. 대부분은 다음 주자가 조금 기다려 줘서 문제없이 넘어가지만, 어느 날 바통이 떨어집니다. 회로에서는 신호가 늦게 도착해 플립플롭이 이전 값을 잡거나 메타스테이블 상태에 빠집니다. 온도가 오르면 신호가 느려지므로, 보드를 오래 켜 둘수록 오류가 늘어나는 패턴이 자주 보입니다.

SW 쪽에서는 이런 문제가 "레지스터에 쓴 값이 가끔 다르게 읽힌다"로 보입니다. 아래 코드는 보드를 처음 올렸을 때 버스와 레지스터 경로가 안정적인지 확인하는 간단한 패턴 테스트입니다. 실패한 비트 위치가 항상 같다면 특정 경로의 타이밍 문제를 의심할 근거가 됩니다.

```c
/* scratch 레지스터에 패턴을 쓰고 읽어 비트 단위 오류를 센다 */
#define SCRATCH  ((volatile uint32_t *)(FPGA_BASE + 0x0FFC))   /* 예시 주소 */

uint32_t bus_pattern_test(uint32_t rounds)
{
    static const uint32_t pat[] = { 0x00000000u, 0xFFFFFFFFu, 0xAAAAAAAAu, 0x55555555u };
    uint32_t bad_bits = 0;
    for (uint32_t r = 0; r < rounds; r++) {
        for (unsigned i = 0; i < 4; i++) {
            *SCRATCH = pat[i];
            bad_bits |= (*SCRATCH ^ pat[i]);     /* 틀린 비트를 누적 */
        }
        for (unsigned b = 0; b < 32; b++) {       /* walking-one */
            *SCRATCH = 1u << b;
            bad_bits |= (*SCRATCH ^ (1u << b));
        }
    }
    return bad_bits;                              /* 0이면 이상 없음 */
}
```

HW 쪽에서는 STA 보고서에서 미충족 경로를 확인하는 것이 첫 단계입니다. 미충족이 남아 있는 비트스트림으로 얻은 디버깅 결과는 믿기 어렵기 때문에, 다른 원인을 찾기 전에 타이밍부터 맞추는 것이 원칙입니다.

## FPGA 전용 차이 — 초기값·메모리 모델·클럭 분주·IP 대체

FPGA 프로토타입은 실리콘과도 다릅니다. ASIC(특정 용도로 제조하는 칩)으로 만들 설계를 FPGA에 맞추느라 일부를 바꿔 넣기 때문입니다. 이 차이 때문에 *FPGA에서는 안 보이는데 실리콘에서 나타나는 버그*와 *FPGA에서만 보이는 가짜 버그*가 생깁니다.

- **초기값:** FPGA의 플립플롭은 비트스트림을 올릴 때 정해진 값으로 초기화됩니다. 그래서 리셋이 빠진 레지스터도 FPGA에서는 늘 같은 값으로 시작해 문제가 숨습니다. 실리콘에서는 전원이 들어올 때 무작위 값이 될 수 있습니다. Ch 10의 X-optimism과 같은 종류의 함정입니다.
- **메모리 모델:** ASIC용 SRAM은 FPGA의 블록 RAM으로 대체됩니다. 읽기 지연이나 동시 읽기·쓰기 동작이 원래 메모리와 다를 수 있어서, 래퍼(wrapper)가 그 차이를 정확히 흉내 내는지 확인해야 합니다.
- **클럭 분주:** FPGA는 실리콘보다 낮은 주파수로 돌아갑니다. 문제는 모든 클럭이 같은 비율로 느려지지 않는다는 점입니다. CPU는 10분의 1로 느려졌는데 외부 메모리나 UART는 원래 속도라면, 블록 사이의 *상대적 타이밍*이 실리콘과 달라져 경쟁 조건이 숨거나 새로 생깁니다.
- **IP 대체:** PLL, SerDes, 아날로그 블록 같은 IP는 FPGA 벤더의 비슷한 IP나 단순한 모델로 바꿔 넣습니다. 이 부분의 동작은 FPGA로 검증되지 않는다고 봐야 합니다.
- **분할:** 설계가 FPGA 한 개에 들어가지 않으면 여러 FPGA로 나눕니다. 이때 칩 사이 신호를 핀 수에 맞추느라 여러 신호를 시간을 나눠 한 핀으로 보내기도 합니다. 그러면 FPGA 사이 경로의 지연이 실리콘과 크게 달라집니다.

이 목록은 FPGA에서 *통과했다*는 결과를 얼마나 믿을지 판단하는 기준이기도 합니다. 위 항목에 걸리는 기능은 실리콘에서 다시 확인할 목록에 올려 둡니다.

## 작은 예시 — 리셋 버튼을 누르면 괜찮아지는 보드

FPGA 보드에 처음 리눅스 드라이버를 올렸더니, 전원을 켠 직후 첫 DMA만 실패하고 리셋 버튼을 누른 뒤에는 정상이라는 보고가 들어왔다고 합시다. 앞의 표에서 "초기값" 행과 증상이 정확히 맞습니다.

HW 엔지니어가 DMA 블록의 레지스터 중 리셋이 없는 것을 찾아봤더니 `desc_ptr_valid`라는 플래그가 리셋 없이 선언돼 있었습니다. FPGA에서 이 플래그는 비트스트림이 정한 초기값인 1로 시작했고, 드라이버가 디스크립터 주소를 쓰기 전에 DMA가 쓰레기 주소를 유효한 것으로 보고 읽어 버렸습니다. 첫 전송이 끝날 때 DMA가 이 플래그를 0으로 내렸고, 리셋 버튼은 FPGA를 다시 구성하지 않고 리셋 신호만 넣습니다. 리셋이 없는 플래그는 리셋 신호를 무시하니 0인 채로 남았고, 그래서 두 번째부터는 문제가 없었습니다.

수정은 플래그에 리셋을 추가하는 한 줄이지만, 교훈은 더 큽니다. 같은 버그가 실리콘에서는 *전원을 켤 때마다 무작위로* 나타났을 것이고, 원인을 찾기가 훨씬 어려웠을 것입니다. 이후 팀은 리셋 없는 플립플롭을 찾는 lint 규칙을 CI에 추가했습니다.

## 실제 사례 — 오픈소스 칩 프로젝트의 FPGA 흐름

공개 문서로 FPGA 프로토타입 흐름을 볼 수 있는 프로젝트로 OpenTitan이 있습니다. OpenTitan은 공개 문서에서 ChipWhisperer CW310 같은 FPGA 보드에 설계를 올리고, 시뮬레이션과 같은 소프트웨어 테스트를 FPGA에서도 돌리는 흐름을 설명합니다. 시뮬레이션에서 확인한 기능을 실제 속도와 실제 외부 연결로 다시 확인하는 단계를 프로젝트 차원에서 정해 둔 셈입니다.

Ch 9에서 소개한 FireSim도 다른 방향에서 같은 문제를 다룹니다. FPGA를 *보드 프로토타입*이 아닌 *빠른 시뮬레이터*로 써서, FPGA의 속도를 얻으면서도 시뮬레이션처럼 결정적으로 동작하게 만드는 것이 목표입니다. FPGA의 속도와 시뮬레이션의 재현성 사이에서 둘 다 얻으려는 시도입니다.

## 자주 하는 실수

- **타이밍 경고를 무시하고 디버깅합니다.** 미충족 경로가 남아 있으면 모든 관찰 결과가 의심스럽습니다. 타이밍부터 맞춥니다.
- **증상 신호만 기록합니다.** 내장 로직 분석기에 증상 신호만 넣으면 원인을 볼 수 없습니다. Ch 10의 역추적처럼 원인 후보 신호까지 넣습니다.
- **분석기를 넣었더니 증상이 사라져서 고쳐졌다고 판단합니다.** 배치가 바뀌어 타이밍이 우연히 맞았을 가능성이 큽니다.
- **FPGA 통과를 실리콘 통과로 여깁니다.** 초기값, 클럭 비율, IP 대체 때문에 FPGA에서 검증되지 않는 영역이 있습니다.
- **여러 비트 값을 2단 동기화기로 넘깁니다.** 비트마다 다른 cycle에 넘어와 중간값이 보입니다. Gray 코드나 비동기 FIFO를 씁니다.

## 정리

- 시뮬레이션은 이상적인 세계, FPGA는 물리적인 세계입니다. 초기값, 클럭, 메모리, 지연, 비동기 입력 다섯 지점에서 둘이 갈립니다.
- 내장 로직 분석기(ILA, Signal Tap 류)는 미리 고른 신호를 트리거 전후 짧은 구간만 기록합니다. 원인 후보 신호와 원인 쪽 트리거를 미리 정합니다.
- CDC에서 생기는 메타스테이빌리티는 시뮬레이션으로 재현되지 않습니다. 1비트는 2단 동기화기, 여러 비트는 Gray 코드·핸드셰이크·비동기 FIFO로 넘깁니다.
- 타이밍이 미충족된 비트스트림의 디버깅 결과는 믿기 어렵습니다. 온도에 따라 오류가 늘면 타이밍을 의심합니다.
- FPGA는 실리콘과도 다릅니다. 초기값, 메모리 래퍼, 클럭 비율, IP 대체, 다중 FPGA 분할 때문에 검증되지 않는 영역을 따로 기록합니다.
- "리셋 버튼을 누르면 괜찮다"는 증상은 리셋 없는 레지스터를 가리키는 강한 신호입니다.
