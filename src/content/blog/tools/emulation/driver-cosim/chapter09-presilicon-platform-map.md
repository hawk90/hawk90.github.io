Ch 1~8에서는 드라이버와 RTL을 한 프로세스에 묶는 co-simulation 환경을 만들었습니다. 이제부터 Ch 16까지는 그 환경 위에서 *실제로 버그를 잡는 일*을 다룹니다. 칩이 나오기 전에 버그를 찾아내고, 찾은 버그를 끝까지 추적하는 과정입니다.

그 출발점은 지도입니다. pre-silicon 단계에는 검증 플랫폼이 네 가지 있고, 플랫폼마다 잡히는 버그와 보이는 신호가 다릅니다. 이 장은 네 플랫폼을 한 장의 지도 위에 놓고, 버그 하나를 플랫폼 사이로 옮겨 가며 잡는 흐름을 보여 줍니다. SW 엔지니어와 HW 엔지니어가 같은 지도를 보고 이야기할 수 있게 만드는 것이 목표입니다.

## 어떤 문제를 푸는가

NPU 프로젝트의 회의 하나를 떠올려 보겠습니다. 드라이버 팀이 "DMA 완료 인터럽트가 가끔 안 옵니다"라고 보고합니다. 3시간짜리 스트레스 테스트를 돌리면 한두 번 일어나는 증상입니다. RTL 팀은 "시뮬레이션에서는 한 번도 본 적이 없다"고 답합니다. 둘 다 맞는 말입니다. 시뮬레이션으로는 3시간 분량의 트래픽을 돌릴 수 없고, 빠르게 돌릴 수 있는 플랫폼에서는 칩 내부가 보이지 않기 때문입니다.

이 상황이 pre-silicon 디버깅의 핵심 긴장을 보여 줍니다. **빠른 플랫폼은 버그를 *재현*하는 데 강하고, 느린 플랫폼은 버그를 *이해*하는 데 강합니다.** 한 플랫폼만으로는 둘 다 할 수 없습니다. 그래서 실전 디버깅은 버그를 빠른 플랫폼에서 발견하고, 재현 조건을 줄여서, 느리지만 잘 보이는 플랫폼으로 옮기는 일이 됩니다.

이 흐름을 따라가려면 먼저 각 플랫폼이 무엇을 보여 주고 무엇을 숨기는지 알아야 합니다.

## 네 플랫폼 한눈에

네 플랫폼을 경기 중계에 빗대어 보겠습니다. 경기는 칩 안에서 일어나는 일이고, 플랫폼은 그 경기를 보는 방법입니다.

| 플랫폼 | 한 문장 정의 | 비유 |
|---|---|---|
| **RTL 시뮬레이션** | RTL을 소프트웨어로 한 cycle씩 계산합니다 | 초고속 카메라로 찍은 슬로모션. 모든 프레임이 보이지만 1초를 보는 데 몇 시간이 걸립니다 |
| **에뮬레이터** | 전용 하드웨어가 RTL 전체를 병렬로 계산합니다 | 방송국 중계차. 카메라가 많고 실시간에 가깝지만 비싸고 예약해야 씁니다 |
| **FPGA 프로토타입** | RTL을 FPGA에 합성해 실제 회로로 돌립니다 | 경기장에 미리 달아 둔 CCTV. 빠르지만 카메라를 단 곳만 보입니다 |
| **Virtual Platform** | 칩의 동작을 C/C++ 모델로 흉내 냅니다 | 비행 시뮬레이터. 조종 연습은 충분히 되지만 엔진 내부의 금속 피로는 보이지 않습니다 |

여기서 **가시성**(visibility)은 "칩 안의 신호를 얼마나 많이, 얼마나 쉽게 볼 수 있는가"를 뜻합니다. 속도와 가시성을 두 축으로 놓으면 네 플랫폼과 실리콘이 거의 한 줄로 늘어섭니다.

![검증 플랫폼의 속도와 가시성 교환 — RTL 시뮬레이션은 느리지만 모든 신호가 보이고, 실리콘으로 갈수록 빨라지지만 안이 덜 보인다](/images/blog/driver-cosim/diagrams/ch09-speed-visibility.svg)

그림에서 virtual platform만 대각선에서 벗어나 있습니다. virtual platform은 *소프트웨어 상태*(레지스터 값, 메모리, 코어의 PC)는 전부 보여 주지만, 하드웨어 쪽은 모델이 흉내 낸 결과만 보여 줍니다. 그래서 SW 엔지니어에게는 가시성이 높고, HW 엔지니어에게는 가시성이 낮은 플랫폼입니다.

속도는 설계 규모와 장비에 따라 몇 자릿수씩 달라지므로 절대 수치보다 *순서*를 기억하는 편이 낫습니다. 느린 쪽부터 RTL 시뮬레이션, 에뮬레이터, FPGA 프로토타입, virtual platform 순이고, 실리콘이 가장 빠릅니다. Ch 1에서 RTL 시뮬레이션과 co-simulation이 Hz~kHz 영역이라고 했던 것을 떠올리면, 리눅스 부팅처럼 수십억 명령어가 필요한 일이 왜 시뮬레이션에서 비현실적인지 감이 옵니다.

## 플랫폼별로 들여다보기

같은 플랫폼이라도 SW 엔지니어와 HW 엔지니어는 다른 것을 봅니다. 각 플랫폼에서 양쪽이 무엇을 보는지, 어떤 버그에 강하고 어떤 버그에 약한지를 정리합니다.

### RTL 시뮬레이션

RTL 시뮬레이터는 Verilog/SystemVerilog 코드를 읽어 매 cycle 모든 신호의 값을 계산합니다. Ch 3의 Verilator, 상용 시뮬레이터가 여기에 속합니다. 이 시리즈의 co-simulation 환경도 RTL 시뮬레이션 위에서 돕니다.

- **HW 엔지니어가 보는 것:** 모든 신호, 모든 cycle의 waveform입니다. 버그가 어느 cycle에 어느 플립플롭에서 시작됐는지까지 거슬러 올라갈 수 있습니다.
- **SW 엔지니어가 보는 것:** 드라이버의 `writel()` 하나가 버스를 타고 레지스터에 도착하는 과정입니다. 드라이버 로그와 waveform의 시간축을 맞춰 볼 수 있습니다.
- **강한 버그:** 레지스터 인코딩 실수, 인터럽트 타이밍, 프로토콜 위반처럼 짧은 시나리오에서 드러나는 버그입니다.
- **약한 버그:** 몇 시간을 돌려야 한 번 나오는 버그, OS 전체가 돌아야 생기는 버그입니다.

### 에뮬레이터

에뮬레이터(emulator)는 RTL을 전용 하드웨어에 올려 병렬로 계산하는 장비입니다. 내부 구조는 벤더마다 다르지만, 칩 전체를 시뮬레이션보다 훨씬 빠르게 돌리면서 상당히 넓은 범위의 신호를 기록할 수 있다는 점이 공통입니다. 그래서 펌웨어와 OS 부팅을 RTL 위에서 처음 시도하는 곳이 보통 에뮬레이터입니다.

- **HW 엔지니어가 보는 것:** 정해 둔 시간 구간의 넓은 신호 덤프입니다. 시뮬레이션만큼 자유롭지는 않지만 FPGA보다 훨씬 많이 보입니다.
- **SW 엔지니어가 보는 것:** 부트로더와 커널 로그, 그리고 디버거 연결입니다. 실리콘보다 느릴 뿐 SW 입장에서는 진짜 칩에 가깝게 느껴집니다.
- **강한 버그:** 부팅 과정의 버그, 여러 IP가 동시에 움직일 때 생기는 버그입니다.
- **약한 버그:** 아주 긴 스트레스 테스트입니다. 장비가 비싼 공유 자원이라 오래 점유하기 어렵습니다.

에뮬레이터 위의 SW bring-up은 Ch 13에서 자세히 다룹니다.

### FPGA 프로토타입

FPGA 프로토타입은 RTL을 FPGA 보드에 합성해 실제 회로로 돌립니다. 속도는 실리콘보다 느리지만 앞의 두 플랫폼보다 빨라서, 몇 시간짜리 스트레스 테스트나 실제 주변 장치를 붙인 테스트가 가능합니다.

- **HW 엔지니어가 보는 것:** 합성할 때 미리 골라 둔 신호만 내장 로직 분석기로 볼 수 있습니다. 다른 신호를 보려면 다시 합성해야 하고, 합성에는 몇 시간이 걸리기도 합니다.
- **SW 엔지니어가 보는 것:** 실제 보드처럼 UART, JTAG, 네트워크가 붙은 환경입니다. 드라이버 개발자에게는 가장 편한 pre-silicon 환경입니다.
- **강한 버그:** 오래 돌려야 나오는 버그, 실제 외부 장치와 붙였을 때 나오는 버그입니다.
- **약한 버그:** 원인 분석입니다. 증상은 잡히는데 내부가 안 보여서 "어디서 틀렸는지"를 알기 어렵습니다.

FPGA에만 있는 함정(클럭 구조와 메모리 모델의 차이)은 Ch 12에서 다룹니다.

### Virtual Platform

virtual platform은 칩을 RTL이 아닌 C/C++ 모델로 흉내 냅니다. Ch 5의 SystemC TLM, QEMU 기반 모델이 여기에 속합니다. RTL이 완성되기 전부터 만들 수 있어서, 펌웨어 팀이 가장 먼저 손에 쥐는 플랫폼입니다.

- **HW 엔지니어가 보는 것:** 모델이 계산한 결과입니다. 모델을 만든 사람이 흉내 내기로 한 동작만 보입니다.
- **SW 엔지니어가 보는 것:** 코어 상태, 메모리, 레지스터 접근 기록입니다. 일반 디버거처럼 멈추고, 되감고, 들여다볼 수 있습니다.
- **강한 버그:** 펌웨어 로직, OS 통합, 드라이버 API 사용 실수입니다.
- **약한 버그:** 타이밍과 마이크로아키텍처에서 생기는 버그입니다. 모델에 그런 개념 자체가 없을 수 있습니다.

모델과 RTL이 서로 다르게 동작할 때 생기는 문제는 Ch 14의 주제입니다.

## 프로젝트 타임라인 위의 플랫폼

네 플랫폼은 언제든 고를 수 있는 것이 아닙니다. 프로젝트가 어느 단계에 있느냐에 따라 쓸 수 있는 플랫폼이 정해집니다.

![칩 프로젝트 타임라인과 플랫폼 — virtual platform은 스펙 단계부터, RTL 시뮬레이션은 RTL 착수부터, 에뮬레이터와 FPGA는 RTL이 안정된 뒤부터, 실리콘은 도착 이후에만 쓸 수 있다](/images/blog/driver-cosim/diagrams/ch09-platform-timeline.svg)

이 타임라인에서 두 가지를 읽어 낼 수 있습니다.

첫째, **에뮬레이터와 FPGA를 쓸 수 있는 기간은 생각보다 짧습니다.** RTL이 어느 정도 안정돼야 올릴 수 있고, 테이프아웃 뒤에는 RTL을 고칠 수 없으니 찾은 버그의 쓸모가 줄어듭니다. 그래서 이 기간에 무엇을 돌릴지는 미리 계획해야 합니다.

둘째, **RTL 시뮬레이션은 실리콘이 나온 뒤에도 계속 쓰입니다.** 실리콘에서 이상한 증상이 보이면 같은 시나리오를 시뮬레이션에서 재현해 원인을 찾습니다. 테이프아웃 선을 넘으면 RTL을 고치는 일은 곧 칩을 다시 만드는 일이 됩니다. 그 비용 때문에 시뮬레이션의 역할이 "고치기 전 확인"에서 "원인 설명"으로 바뀝니다.

## 버그 종류로 플랫폼 고르기

버그를 처음 발견한 곳과 원인을 찾을 곳은 다른 경우가 많습니다. 아래 표는 버그 종류별로 처음 잡힐 가능성이 높은 플랫폼과, 원인을 찾으러 옮겨 갈 플랫폼을 정리했습니다.

| 버그 종류 | 처음 잡히는 곳 | 원인을 찾는 곳 |
|---|---|---|
| 레지스터 비트 위치·리셋값 실수 | Virtual platform 또는 RTL 시뮬레이션 | RTL 시뮬레이션 |
| 인터럽트·DMA 타이밍 경쟁 | FPGA 프로토타입(장시간 스트레스) | RTL 시뮬레이션(재현 시나리오로) |
| 부팅 중 특정 단계에서 멈춤 | 에뮬레이터 | 에뮬레이터 덤프, 이후 RTL 시뮬레이션 |
| 펌웨어 로직·드라이버 API 오용 | Virtual platform | Virtual platform(일반 디버거) |
| 외부 장치와의 프로토콜 불일치 | FPGA 프로토타입 | 내장 로직 분석기, 이후 RTL 시뮬레이션 |
| 모델과 RTL의 동작 차이 | RTL 기반 플랫폼에 처음 올릴 때 | 두 플랫폼의 trace 비교 |

표의 오른쪽 열에 RTL 시뮬레이션이 자주 나오는 것은 우연이 아닙니다. 원인을 *설명*하려면 결국 모든 신호가 보이는 곳으로 가야 합니다. 디버깅의 기술 대부분은 빠른 플랫폼에서 본 증상을 느린 플랫폼으로 옮길 수 있을 만큼 작게 줄이는 데 있습니다.

## 작은 예시 — DMA 인터럽트 누락을 옮겨 가며 잡기

처음의 "DMA 완료 인터럽트가 가끔 안 온다" 사례를 끝까지 따라가 보겠습니다.

**1단계 — FPGA에서 재현합니다.** 스트레스 테스트에서 실패 빈도를 확인하고, 실패 직전에 어떤 DMA 요청이 있었는지 드라이버 로그로 남깁니다. 이 단계의 목표는 원인 찾기가 아니라 *재현 조건* 모으기입니다.

같은 테스트를 모든 플랫폼에서 돌리려면, 플랫폼마다 달라지는 부분을 함수 두 개로 가둬 두는 편이 좋습니다. 아래 코드는 레지스터 접근만 플랫폼별로 구현하고 나머지 테스트 로직은 그대로 공유하는 구조입니다.

```c
/* 플랫폼마다 이 두 함수만 다르게 구현한다:
 * FPGA·실리콘은 MMIO, co-sim은 DPI-C, virtual platform은 모델 API */
uint32_t plat_read32(uintptr_t addr);
void     plat_write32(uintptr_t addr, uint32_t val);

#define DMA_BASE      0x40010000u   /* 예시 주소 */
#define DMA_SRC       (DMA_BASE + 0x00)
#define DMA_LEN       (DMA_BASE + 0x08)
#define DMA_CTRL      (DMA_BASE + 0x0C)
#define DMA_IRQ_STAT  (DMA_BASE + 0x10)
#define DMA_START     (1u << 0)
#define DMA_DONE      (1u << 0)

int dma_irq_stress(uint32_t iterations, uint32_t seed)
{
    srand(seed);                                  /* seed를 남겨야 다른 플랫폼에서 재현된다 */
    for (uint32_t i = 0; i < iterations; i++) {
        uint32_t len = 64u + (uint32_t)(rand() % 4096);
        plat_write32(DMA_SRC, 0x80000000u);
        plat_write32(DMA_LEN, len);
        plat_write32(DMA_CTRL, DMA_START);
        if (!wait_irq(DMA_IRQ_STAT, DMA_DONE, /*timeout_us=*/1000)) {
            log_fail(i, len, seed);               /* 실패한 반복 번호와 길이를 기록 */
            return -1;
        }
        plat_write32(DMA_IRQ_STAT, DMA_DONE);     /* write-1-to-clear */
    }
    return 0;
}
```

**2단계 — 재현 조건을 줄입니다.** 로그를 모아 보니 실패는 항상 *길이가 4096 근처인 전송 직후에 짧은 전송이 바로 이어질 때* 일어났다고 합시다. 그러면 3시간짜리 테스트가 전송 두 번짜리 시나리오로 줄어듭니다. 이렇게 시나리오를 줄이는 기법은 Ch 15에서 자세히 다룹니다.

**3단계 — RTL 시뮬레이션으로 옮깁니다.** 전송 두 번짜리 시나리오는 시뮬레이션에서 몇 초면 끝납니다. 같은 `dma_irq_stress()`를 co-simulation 환경에서 실패 조건으로 돌리고 waveform을 남깁니다.

```bash
# 실패 조건만 골라 돌리고, 실패하면 waveform을 남긴다
pytest tests/test_dma.py -k "irq_back_to_back" --seed 4242 --dump-on-fail
```

**4단계 — waveform에서 원인을 찾습니다.** 첫 전송의 완료 인터럽트를 소프트웨어가 지우는 cycle과, 두 번째 전송의 완료가 인터럽트 상태 비트를 세우는 cycle이 겹치는 것이 보입니다. 같은 cycle에 "지우기"와 "세우기"가 부딪혀 지우기가 이긴 것입니다. 이건 RTL의 우선순위 버그입니다. 동시에 일어나면 세우기가 이겨야 합니다.

이 결론은 FPGA만으로는 낼 수 없었습니다. 반대로 시뮬레이션만으로는 이 시나리오를 떠올리지 못했을 것입니다. 두 플랫폼을 오가는 것이 pre-silicon 디버깅의 기본 동작입니다. 상태 비트의 지우기와 세우기 충돌을 찾아내는 waveform 읽기는 Ch 10에서, 이런 충돌을 assertion으로 미리 막는 법은 Ch 11에서 다룹니다.

## 실제 프로젝트에서는

오픈소스 하드웨어 프로젝트에서도 같은 분업을 볼 수 있습니다. UC Berkeley의 Chipyard 생태계에는 FireSim이 있습니다. FireSim은 RTL을 FPGA로 가속해 시뮬레이션처럼 쓰는 도구로, 소프트웨어 시뮬레이션으로는 오래 걸리는 긴 워크로드를 FPGA 위에서 돌리는 것이 목적입니다. 빠른 플랫폼에서 재현하고 느린 플랫폼에서 이해한다는 원칙을 도구 하나로 묶으려는 시도라고 볼 수 있습니다.

보안 칩 프로젝트인 OpenTitan도 Verilator 기반 시뮬레이션과 FPGA 보드를 함께 씁니다. 같은 소프트웨어 테스트를 여러 플랫폼에서 돌리는 구조를 갖춰서, 플랫폼마다 따로 테스트를 짜지 않아도 됩니다. 앞의 예시에서 `plat_read32()`/`plat_write32()`로 플랫폼 차이를 가둔 것과 같은 발상입니다.

## 자주 하는 오해

- **"빠른 플랫폼이 더 좋은 플랫폼이다."** 속도는 재현에 유리할 뿐입니다. 원인을 설명하는 데는 가시성이 필요하고, 가시성은 속도와 맞바꿔야 얻을 수 있습니다.
- **"시뮬레이션에서 통과했으니 RTL은 맞다."** 시뮬레이션은 돌린 시나리오만 검증합니다. 위 예시의 연속 전송처럼 아무도 짜지 않은 시나리오는 통과할 기회조차 없었습니다.
- **"virtual platform에서 되면 실리콘에서도 된다."** 모델은 만든 사람이 이해한 스펙을 흉내 냅니다. 모델과 RTL이 같은 스펙을 다르게 이해했을 수 있습니다.
- **"재현은 나중에 하고 일단 원인부터 찾자."** 재현 조건 없이 원인을 찾으면 고친 뒤에도 정말 고쳐졌는지 확인할 방법이 없습니다.

## 정리

- pre-silicon 검증 플랫폼은 RTL 시뮬레이션, 에뮬레이터, FPGA 프로토타입, virtual platform 네 가지입니다.
- 네 플랫폼은 **속도와 가시성을 맞바꾸는** 관계입니다. 빠를수록 재현에 강하고, 잘 보일수록 원인 분석에 강합니다.
- virtual platform은 SW 상태는 전부 보이지만 HW는 모델만 보입니다. SW와 HW 엔지니어에게 가시성이 다르게 느껴지는 플랫폼입니다.
- 에뮬레이터와 FPGA를 쓸 수 있는 기간은 RTL 안정 이후부터 테이프아웃까지로 짧습니다. RTL 시뮬레이션은 실리콘 이후에도 원인 설명용으로 계속 쓰입니다.
- 실전 디버깅은 **빠른 플랫폼에서 발견하고, 재현 조건을 줄이고, 잘 보이는 플랫폼으로 옮기는** 흐름입니다.
- 같은 테스트를 여러 플랫폼에서 돌리려면 플랫폼 의존 부분(레지스터 접근)을 작은 인터페이스로 가둡니다.
- seed와 실패 조건을 기록해 두어야 플랫폼을 옮겨도 버그가 따라옵니다.
