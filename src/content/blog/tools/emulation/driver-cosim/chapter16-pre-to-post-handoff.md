실리콘이 나온 뒤에 "이 신호를 볼 수 있었으면" 하고 후회해도 늦습니다. 테이프아웃(설계를 확정해 제조 공장에 넘기는 일) 이후에는 칩 안에 회로를 한 줄도 더할 수 없기 때문입니다. 이 장은 Co-simulation 시리즈 확장 파트의 마지막 장으로, pre-silicon 단계에서 post-silicon 디버깅을 위해 미리 심어 둘 장치를 다룹니다.

Ch 9~15가 "칩이 나오기 전에 버그를 잡는 법"이었다면, 이 장은 "잡지 못한 버그를 칩이 나온 뒤에 잡을 수 있게 준비하는 법"입니다. 디버그 훅(debug hook, 칩 내부 상태를 밖에서 관찰하거나 기록할 수 있게 넣어 두는 회로)을 설계하는 일은 HW 엔지니어의 몫이지만, 그 훅을 쓰는 사람은 대개 펌웨어·드라이버 엔지니어입니다. 그래서 두 팀이 테이프아웃 전에 같은 체크리스트를 보고 합의해야 합니다.

## 실리콘에서 후회하는 것들

post-silicon 디버깅 회의에서 반복해서 나오는 말이 몇 가지 있습니다. "어디서 멈췄는지만 알면 되는데", "리셋되면서 로그가 다 날아갔어요", "버스가 멈춰서 디버거도 안 붙어요" 같은 말입니다. 이 말들은 모두 같은 사실을 가리킵니다. 실리콘에서는 pre-silicon에서 당연했던 가시성(visibility, 칩 내부를 얼마나 볼 수 있는가)이 사라지고, 미리 만들어 둔 창문으로만 안을 들여다볼 수 있습니다.

집을 지을 때를 떠올려 보면 이해가 쉽습니다. 벽을 세우기 전에 점검구를 내 두면 나중에 배관이 새도 그 구멍으로 들여다볼 수 있습니다. 점검구 없이 마감한 집은 벽을 뜯어야 합니다. 칩에서 벽을 뜯는 일은 칩을 다시 만드는 일이고, 그 비용은 Ch 1에서 본 것처럼 몇 자릿수가 다릅니다.

아래 표는 실리콘에서 흔히 마주치는 증상과, 그 증상을 풀어 줄 훅을 짝지은 것입니다. 왼쪽은 SW 쪽에서 보이는 증상이고, 오른쪽은 HW가 미리 넣어 두었어야 할 장치입니다.

| SW 쪽에서 보이는 증상 | 필요했던 훅 | 이 장의 절 |
|---|---|---|
| 아무 출력 없이 멈춤, 어디서 멈췄는지 모름 | 리셋에도 유지되는 scratch 레지스터, postcode | DFD |
| 크래시 직후 리셋되어 원인이 사라짐 | 온칩 trace buffer, 리셋 후에도 읽을 수 있는 경로 | trace buffer |
| 버스 접근 하나에서 칩 전체가 멈춤 | 인터커넥트 timeout과 에러 기록 | 버스 모니터 |
| 특정 IP만 이상하게 동작 | IP 내부 상태·에러 레지스터 | DFD |
| 저전력 진입 후 깨어나지 않음 | 전원 도메인 상태 표시, 항상 켜진 영역의 기록 | 전원 인지 시뮬레이션 |
| sim에서는 되는데 실리콘에서는 안 됨 | 같은 테스트를 양쪽에서 돌릴 수 있는 구조 | 테스트 재사용 |

## DFD — 디버그 레지스터·scratch·postcode

DFD(Design for Debug, 디버깅을 위한 설계)는 칩을 처음부터 디버깅하기 쉽게 만드는 설계 관행을 가리킵니다. 양산 테스트를 위한 DFT(Design for Test)와 이름이 비슷하지만 목적이 다릅니다. DFT는 "이 칩이 제대로 만들어졌는가"를 공장에서 확인하는 회로이고, DFD는 "이 칩에서 왜 이런 일이 일어나는가"를 개발자가 알아내기 위한 회로입니다.

![테이프아웃 전에 심어 두는 디버그 훅 — scratch·postcode, 온칩 trace buffer, 디버그 포트, 버스 모니터, IP 상태 레지스터](/images/blog/driver-cosim/diagrams/ch16-dfd-hooks.svg)

가장 싸고 효과가 큰 DFD는 **scratch 레지스터**(값을 써 두었다가 나중에 읽어 보는 빈 레지스터)입니다. 기능은 단순하지만 두 가지 조건이 붙습니다. 첫째, 항상 켜진 전원 영역(always-on domain, 칩이 저전력 상태여도 전원이 유지되는 영역)에 있어야 합니다. 둘째, watchdog 리셋 같은 웜 리셋(warm reset, 전원은 유지한 채 칩만 다시 시작하는 리셋)에서 값이 지워지지 않아야 합니다. 이 두 조건을 갖춘 레지스터가 하나만 있어도 "어디서 멈췄나"라는 질문의 절반은 답할 수 있습니다.

**postcode**는 그 scratch 레지스터를 쓰는 관례입니다. 부팅이나 초기화 단계마다 정해진 번호를 레지스터에 써 두면, 멈춘 뒤에 마지막 번호를 읽어 어느 단계까지 갔는지 알 수 있습니다. PC에서는 오래전부터 BIOS가 부팅 단계마다 I/O 포트 0x80에 POST 코드를 써 왔고, 이 값을 보여 주는 POST 카드라는 진단 장비도 있습니다. 칩에 postcode 레지스터를 넣는 것은 이 관례를 SoC 안으로 가져오는 일입니다.

펌웨어 쪽에서는 아래처럼 단계 번호를 정의해 두고 초기화 코드 곳곳에서 씁니다. 번호 체계를 HW와 SW가 함께 정해 두면, 실리콘에서 읽은 값 하나로 양쪽이 같은 그림을 볼 수 있습니다.

```c
/* scratch 레지스터 주소와 단계 번호는 예시. 실제 값은 칩 스펙 문서를 따른다 */
#define DBG_POSTCODE   (*(volatile uint32_t *)0x4F000000u)  /* always-on, warm reset 유지 */

enum postcode {
    PC_ROM_HANDOFF   = 0x0100,   /* BootROM에서 첫 부트 코드로 넘어옴 */
    PC_CLK_INIT      = 0x0200,
    PC_DDR_INIT      = 0x0300,
    PC_DDR_TRAINING  = 0x0310,
    PC_LOAD_NEXT     = 0x0400,
};

static inline void postcode(enum postcode pc)
{
    DBG_POSTCODE = (DBG_POSTCODE & 0xFFFF0000u) | (uint32_t)pc;  /* 상위 16비트는 리셋 횟수용 */
}
```

이 밖에 IP마다 **상태·에러 레지스터**를 두는 것도 DFD에 속합니다. DMA 엔진이라면 마지막으로 처리한 descriptor 주소, 상태 머신의 현재 상태, 마지막 에러 원인 같은 값입니다. RTL 설계자에게는 몇 줄짜리 추가지만, 실리콘에서는 waveform 대신 이 값들이 유일한 단서가 되기도 합니다.

## 온칩 trace buffer와 버스 모니터

scratch 레지스터는 "어디서 멈췄나"를 알려 주지만 "어떻게 거기까지 갔나"는 알려 주지 못합니다. 그 질문에 답하는 장치가 **온칩 trace buffer**(칩 안의 작은 메모리에 실행 흐름이나 버스 트래픽을 계속 기록하는 회로)입니다. 비행기의 블랙박스가 사고 직전 몇십 분의 비행 기록을 남기듯, trace buffer는 크래시 직전의 기록을 남깁니다.

Arm 기반 SoC라면 CoreSight(Arm의 온칩 디버그·trace 아키텍처) 구성 요소인 ETM(코어의 실행 흐름을 기록하는 장치)과 ETB·ETR(그 기록을 담는 버퍼)을 넣을지, 버퍼를 얼마나 크게 잡을지를 이 단계에서 정합니다. 이 장치를 실리콘에서 실제로 쓰는 방법은 Embedded Debugging Ch 15에서 다룹니다. 설계 단계에서 확인할 것은 세 가지입니다.

- **리셋 뒤에도 버퍼를 읽을 수 있나:** 크래시가 watchdog 리셋으로 이어지면 버퍼 내용이 지워지거나 읽을 경로가 닫힐 수 있습니다.
- **정지 트리거를 걸 수 있나:** 에러나 watchdog 직전에 기록을 멈추게 하는 신호가 trace 회로까지 연결돼 있어야 합니다.
- **디버거 없이도 꺼낼 수 있나:** 양산 제품처럼 JTAG을 쓸 수 없는 환경에서 소프트웨어가 버퍼를 메모리로 복사할 수 있어야 합니다.

**버스 모니터**는 인터커넥트(칩 안의 여러 블록을 잇는 버스 네트워크)에 붙는 감시 장치입니다. 가장 중요한 기능은 timeout입니다. CPU가 전원이 꺼진 IP에 접근하면 응답이 영영 오지 않아 CPU가 멈춥니다. 이것이 버스 hang입니다. timeout 회로가 있으면 일정 시간 뒤 에러 응답을 돌려줘 CPU가 예외를 처리하고 로그를 남길 수 있습니다. 이 차이는 "칩이 그냥 멈췄다"와 "주소 0x4003_0000 접근이 timeout됐다"의 차이입니다. 실리콘에서 이 기능을 활용하는 법은 Embedded Debugging Ch 14에서 다룹니다.

## 테스트 재사용 — sim에서 실리콘까지

pre-silicon에서 수천 개의 테스트를 만들었다면, 그 테스트를 실리콘에서도 돌릴 수 있어야 합니다. 실리콘에서 증상이 나왔을 때 "같은 테스트가 시뮬레이션에서는 통과했다"는 사실은 범위를 좁히는 강력한 단서이기 때문입니다. 반대로 플랫폼마다 테스트를 따로 짰다면, 실리콘 결과와 시뮬레이션 결과를 비교할 기준 자체가 없습니다.

![한 벌의 테스트를 실리콘까지 — 테스트 시나리오는 하나, 플랫폼 계층만 RTL 시뮬레이션·에뮬레이터·FPGA·실리콘별로 바꾼다](/images/blog/driver-cosim/diagrams/ch16-test-reuse.svg)

Ch 9에서 본 `plat_read32()`/`plat_write32()` 구조가 바로 이 목적입니다. 테스트 시나리오는 한 벌만 두고, 레지스터 접근 방식만 플랫폼별로 바꿉니다. 여행용 멀티 어댑터를 떠올리면 됩니다. 기기는 그대로 두고 나라마다 다른 콘센트에 맞는 어댑터만 바꿔 끼웁니다.

업계에는 이 발상을 표준으로 만든 시도도 있습니다. Accellera의 Portable Test and Stimulus Standard(PSS)는 테스트의 *의도*를 한 번 기술하고, 도구가 그것을 시뮬레이션·에뮬레이션·실리콘용 테스트로 각각 생성하게 하는 표준입니다. 작은 팀이라면 표준 도구까지 갈 필요 없이, 위의 플랫폼 계층만 지켜도 효과의 상당 부분을 얻습니다.

테스트를 실리콘까지 가져가려면 몇 가지를 pre-silicon 단계부터 지켜야 합니다.

- **시간을 cycle 수로 기다리지 않습니다.** 시뮬레이션에서는 "100 cycle 뒤 완료"가 맞아도 실리콘에서는 클럭이 다를 수 있습니다. 상태 비트를 timeout과 함께 polling합니다.
- **결과를 로그 형식으로 통일합니다.** 플랫폼마다 출력이 다르면 비교가 어렵습니다. 테스트 이름, seed, 통과/실패, 실패 시 레지스터 값을 같은 형식으로 남깁니다.
- **seed를 항상 기록합니다.** 실리콘에서 실패한 seed를 시뮬레이션에서 그대로 재현하는 것이 Ch 15 triage의 출발점입니다.

## 전원 인지 시뮬레이션 — 전원 도메인 버그를 미리 잡기

현대 SoC는 쓰지 않는 블록의 전원을 끕니다. NPU가 놀고 있으면 NPU 영역의 전원을 끄고, 필요할 때 다시 켭니다. 그런데 일반 RTL 시뮬레이션은 전원이라는 개념이 없어서, 모든 블록이 항상 켜져 있다고 가정합니다. 그 결과 "전원을 껐다 켰을 때만 생기는 버그"는 시뮬레이션을 전부 통과하고 실리콘에서 처음 나타납니다. Embedded Debugging Ch 14의 "저전력 진입 후 안 깨어남"이 대표적인 증상입니다.

**전원 인지 시뮬레이션**(power-aware simulation)은 이 빈틈을 메웁니다. 전원 설계 정보를 별도 파일로 기술하고, 시뮬레이터가 그 정보에 따라 전원이 꺼진 영역의 신호를 알 수 없는 값(X)으로 바꿉니다. 꺼진 방의 전등 스위치를 눌러도 불이 켜지지 않는 것처럼, 꺼진 영역의 출력은 믿을 수 없는 값이 됩니다. 이 X가 켜져 있는 다른 영역으로 새어 들어가면 버그입니다.

전원 설계 정보는 보통 UPF(Unified Power Format, IEEE 1801로 표준화된 전원 의도 기술 형식)로 씁니다. 아래는 NPU 전원 도메인 하나와 그 경계에 둘 장치를 기술한 개념적 예시입니다. 실제 문법과 옵션은 사용하는 UPF 버전과 도구 문서를 따라야 합니다.

```tcl
# 개념적 예시: NPU 영역을 끌 수 있는 전원 도메인으로 정의한다
create_power_domain PD_NPU -elements {u_npu}
create_supply_net   VDD_NPU

# NPU가 꺼져 있을 때 출력이 X로 새지 않도록 경계에서 0으로 고정한다
set_isolation iso_npu -domain PD_NPU \
    -isolation_power_net VDD_AON -clamp_value 0 -applies_to outputs

# 전원을 껐다 켜도 일부 레지스터 값은 유지한다
set_retention ret_npu -domain PD_NPU -retention_power_net VDD_AON
```

이 정보를 넣고 시뮬레이션하면 세 종류의 버그가 드러납니다. 하나는 **isolation 누락**(꺼진 영역의 출력을 고정하는 장치가 빠진 경우)으로, 켜진 영역에 X가 퍼집니다. 다른 하나는 **retention 누락**(유지해야 할 상태가 전원을 껐다 켜며 사라지는 경우)으로, 깨어난 뒤 설정이 초기화돼 있습니다. 마지막은 **순서 오류**로, 펌웨어가 전원을 켜기 전에 레지스터에 접근하거나 isolation을 풀기 전에 신호를 쓰는 경우입니다. 마지막 종류는 펌웨어 버그이기도 해서, SW 엔지니어가 시나리오를 함께 짜야 잡힙니다.

## 테이프아웃 전 디버그 훅 체크리스트

마지막으로 위 내용을 체크리스트로 묶습니다. 테이프아웃 전 리뷰에서 HW와 SW가 함께 한 줄씩 확인하는 용도입니다. 항목마다 "누가 실리콘에서 이것을 쓰는가"를 함께 적어 두면, 훅이 실제로 쓰일지 판단하기 쉽습니다.

| 항목 | 확인할 것 | 실리콘에서 쓰는 사람 |
|---|---|---|
| scratch·postcode 레지스터 | always-on 영역인가, warm reset에 유지되나 | 펌웨어, bring-up 팀 |
| 리셋 원인 기록 | watchdog·전원·소프트웨어 리셋을 구분해 남기나 | 펌웨어 |
| 온칩 trace buffer | 크기, 정지 트리거 연결, 리셋 후 회수 경로 | 펌웨어, 성능·디버그 팀 |
| 버스 timeout | 모든 슬레이브 경로에 있나, 에러 주소를 기록하나 | 드라이버, 커널 |
| IP 상태·에러 레지스터 | 상태 머신·마지막 에러·마지막 요청을 읽을 수 있나 | 드라이버 |
| 디버그 포트 접근 | 디버그 전원 도메인, 인증 설정, 개발용 잠금 해제 방법 | bring-up 팀 |
| 전원 인지 시뮬레이션 | 모든 전원 전이 시나리오를 돌렸나 | 펌웨어(시나리오), HW(검증) |
| 테스트 재사용 | 실리콘용 플랫폼 계층이 준비됐나, 로그 형식이 같은가 | 검증, bring-up 팀 |

체크리스트에 "예"가 늘어날수록 칩 면적과 검증 일정은 조금씩 늘어납니다. 그래서 모든 항목을 최대로 넣기보다, 실리콘에서 가장 자주 막히는 지점(멈춘 위치, 리셋 원인, 버스 hang)부터 확실히 챙기는 편이 현실적입니다.

## 작은 예시 — postcode 하나로 끝난 하루

가상의 bring-up 첫 주를 따라가 보겠습니다. 보드가 부팅 중에 아무 출력 없이 멈추고, watchdog이 칩을 리셋합니다. 리셋 뒤 첫 부트 코드가 scratch 레지스터를 읽어 UART로 출력합니다.

부팅 직후 이전 부팅의 흔적을 출력하는 코드는 아래처럼 간단합니다. 하위 16비트는 마지막 단계 번호, 상위 16비트는 연속 리셋 횟수입니다.

```c
void report_previous_boot(void)
{
    uint32_t v = DBG_POSTCODE;
    uint32_t last = v & 0xFFFFu;
    uint32_t resets = (v >> 16) + 1u;

    printf("prev postcode=0x%04x resets=%u\n", last, resets);
    DBG_POSTCODE = resets << 16;          /* 이번 부팅을 위해 단계 번호만 지운다 */
}
```

출력은 `prev postcode=0x0310 resets=3`이었습니다. 세 번 연속 DDR training 단계에서 멈췄다는 뜻입니다. 이 값 하나로 팀은 클럭·전원 쪽 의심을 접고 DDR 담당자를 불렀습니다. postcode가 없었다면 "아무 출력 없이 멈춤"이라는 같은 증상을 두고 전원부터 다시 점검했을 것입니다. 이 레지스터를 넣는 데 든 비용은 RTL 몇 줄과 테이프아웃 전 리뷰 한 줄이었습니다.

## 자주 하는 실수

- **scratch 레지스터를 일반 전원 영역에 둡니다.** 저전력 진입이나 리셋에서 값이 지워지면, 정작 필요한 순간에 아무것도 남지 않습니다.
- **trace buffer를 넣고 회수 경로를 잊습니다.** 기록은 남았는데 리셋 뒤에 읽을 방법이 없으면 없는 것과 같습니다.
- **디버그 훅을 SW 팀과 상의하지 않습니다.** 레지스터 주소와 의미가 펌웨어 쪽 문서에 반영되지 않아, 실리콘이 나온 뒤에야 존재를 알게 됩니다.
- **전원 인지 시뮬레이션을 HW 혼자 돌립니다.** 실제 펌웨어의 전원 전이 순서를 넣지 않으면, 펌웨어 쪽 순서 버그는 잡히지 않습니다.
- **테스트를 cycle 수에 의존해 짭니다.** 실리콘으로 가져가는 순간 타이밍이 달라져 대부분의 테스트가 쓸모없어집니다.

## 정리

- 테이프아웃 뒤에는 회로를 더할 수 없으므로, post-silicon 디버깅에 필요한 훅은 pre-silicon 단계에서 미리 넣어야 합니다.
- DFD는 디버깅을 위한 설계이며, 가장 효과가 큰 것은 always-on 영역에서 warm reset에도 유지되는 **scratch·postcode 레지스터**입니다.
- 온칩 **trace buffer**는 크래시 직전의 흐름을 남기고, **버스 timeout**은 hang을 예외로 바꿔 로그를 남길 기회를 만듭니다.
- 같은 테스트를 시뮬레이션부터 실리콘까지 돌릴 수 있게 **플랫폼 계층**으로 분리하고, 로그 형식과 seed 기록을 통일합니다.
- **전원 인지 시뮬레이션**(UPF)은 isolation·retention 누락과 전원 전이 순서 버그를 실리콘 전에 드러냅니다.
- 테이프아웃 전 체크리스트는 HW와 SW가 함께 보고, 항목마다 실리콘에서 쓸 사람을 적어 둡니다.
