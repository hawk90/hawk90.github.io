Ch 9의 지도에서 **에뮬레이터**는 RTL 시뮬레이션과 FPGA 프로토타입 사이에 있었습니다. 칩 전체 RTL을 시뮬레이션보다 훨씬 빠르게 돌리면서, FPGA보다 넓은 범위의 신호를 기록할 수 있는 장비입니다. 그래서 펌웨어와 OS가 *RTL 위에서* 처음 부팅되는 곳이 대개 에뮬레이터입니다.

이 장은 에뮬레이터 위에서 소프트웨어를 처음 살리는 과정, 즉 pre-silicon **SW bring-up**을 다룹니다. 에뮬레이터는 회사마다 장비와 도구가 다르고 사용법도 벤더 문서에 달려 있으므로, 이 장은 특정 제품의 조작법보다 *어느 장비에서든 통하는 원리*에 집중합니다. 호스트와 RTL을 잇는 트랜잭터, 부팅 단계별로 무엇을 볼지, 넓은 가시성의 비용, 그리고 비싼 공유 자원을 쓰는 운영 방법입니다.

## 에뮬레이터가 채우는 자리

리눅스 커널 하나가 부팅되려면 수십억 개의 명령어가 실행돼야 합니다. Ch 1에서 RTL 시뮬레이션이 Hz~kHz 영역이라고 했으니, 시뮬레이션으로 리눅스를 부팅하면 몇 주에서 몇 달이 걸립니다. FPGA는 충분히 빠르지만 칩 전체가 FPGA에 들어가지 않거나, 내부 신호를 거의 볼 수 없습니다. 이 빈자리를 채우는 장비가 에뮬레이터입니다.

에뮬레이터(emulator)는 RTL을 전용 하드웨어에 올려 병렬로 계산합니다. 업계에는 Cadence Palladium, Synopsys ZeBu, Siemens Veloce 같은 제품군이 있고, 내부 구조는 벤더마다 다릅니다. 공통점은 세 가지입니다.

- 칩 전체 RTL을 한 번에 올릴 수 있을 만큼 용량이 큽니다.
- 시뮬레이션보다 훨씬 빨라서 부트로더와 OS를 실제로 부팅할 수 있습니다.
- 정해 둔 구간의 신호를 넓게 기록할 수 있습니다.

대신 장비가 매우 비싸서 대부분의 회사에서 여러 팀이 나눠 씁니다. 녹음 스튜디오를 대관하는 것과 비슷합니다. 장비는 최고급이지만 시간 단위로 예약해야 하고, 들어가기 전에 무엇을 녹음할지 준비하지 않으면 비싼 시간을 허비합니다.

SW와 HW 엔지니어가 에뮬레이터에 기대하는 것도 조금 다릅니다.

| 관점 | 에뮬레이터에서 하고 싶은 일 | 주로 보는 것 |
|---|---|---|
| SW 엔지니어 | 부트로더·커널·드라이버를 실리콘 전에 돌려 보기 | UART 로그, 디버거, postcode |
| HW 엔지니어 | 실제 소프트웨어 부하에서 RTL 버그 찾기 | 실패 구간의 넓은 waveform |

두 기대는 같은 실행에서 동시에 충족될 수 있습니다. SW가 부팅을 돌리는 동안 문제가 생기면, 그 구간의 waveform을 HW가 분석하는 식입니다.

## 트랜잭터 — 호스트와 RTL 사이의 다리

에뮬레이터 안의 RTL은 cycle 단위 신호로 움직이고, 테스트를 지휘하는 호스트 PC의 소프트웨어는 "UART로 한 글자 보내라" 같은 *메시지* 단위로 생각합니다. 둘 사이를 잇는 부품이 **트랜잭터**(transactor)입니다. 메시지 하나를 받아 여러 cycle에 걸친 핀 동작으로 풀어 RTL에 넣고, 반대로 RTL의 핀 동작을 모아 메시지로 만들어 호스트에 돌려줍니다.

![에뮬레이터 구성 — 호스트 PC가 빠른 링크로 트랜잭터와 메시지를 주고받고, 트랜잭터가 에뮬레이터 안의 SoC RTL 및 메모리·UART 모델과 신호 단위로 연결된 그림](/images/blog/driver-cosim/diagrams/ch13-emulator-setup.svg)

트랜잭터는 국제회의의 동시통역사와 비슷합니다. 호스트는 문장 단위로 말하고, RTL은 음절 단위로 알아듣습니다. 통역사가 문장을 받아 음절로 풀어 전달하는 동안 양쪽은 서로의 언어를 몰라도 됩니다. Ch 6의 BFM이 시뮬레이션 안에서 하던 일을, 트랜잭터는 에뮬레이터와 호스트 사이에서 합니다.

트랜잭터 설계에서 가장 중요한 원칙은 **호스트와 에뮬레이터가 맞춰 기다리는 횟수를 줄이는 것**입니다. 에뮬레이터는 빠르게 달리다가도 호스트의 응답을 기다려야 할 때마다 멈춥니다. 그래서 트랜잭터의 신호 처리 부분은 합성 가능한 회로로 만들어 에뮬레이터 안에 넣고, 호스트와는 메시지를 묶어서 가끔만 주고받는 구조가 일반적입니다. 이런 메시지 기반 연결을 표준화한 것이 Accellera의 **SCE-MI**(Standard Co-Emulation Modeling Interface)입니다.

## 부팅 단계별 디버그 포인트

에뮬레이터 위의 부팅은 실리콘 bring-up(Embedded Debugging Ch 10)과 같은 계단을 오릅니다. 차이는 각 단계에서 *볼 수 있는 것*이 훨씬 많다는 점입니다. 실리콘에서는 핀 몇 개만 보이지만, 에뮬레이터에서는 코어의 PC(프로그램 카운터, 지금 실행 중인 명령어 주소)부터 버스 트랜잭션까지 볼 수 있습니다.

![부팅 단계별 디버그 포인트 — 리셋 해제, BootROM, 첫 펌웨어, 메모리 초기화, 부트로더, 커널 각 단계에서 볼 것(리셋·클럭 신호, PC trace, postcode 레지스터, 백도어 로드, UART 트랜잭터 로그, 체크포인트)을 짝지은 그림](/images/blog/driver-cosim/diagrams/ch13-boot-debug.svg)

단계마다 쓸 만한 기법을 정리하면 이렇습니다.

- **리셋 해제·BootROM:** 리셋과 클럭 신호가 의도대로 풀리는지 waveform으로 확인하고, 코어의 PC 흐름을 기록해 BootROM이 어느 분기로 가는지 봅니다.
- **첫 펌웨어:** UART가 아직 준비되지 않았을 수 있으므로, 단계마다 번호를 특정 레지스터에 쓰는 **postcode**를 씁니다. 에뮬레이터의 모니터(특정 신호나 주소를 감시해 기록하는 기능)가 그 주소에 쓰기가 일어날 때마다 cycle 번호와 함께 기록합니다.
- **메모리 초기화:** DDR 초기화와 training(신호 타이밍을 보정하는 과정)은 에뮬레이터에서 오래 걸리고, 실제 DDR PHY는 모델로 대체돼 있는 경우가 많습니다. 그래서 메모리 모델에 이미지를 직접 써 넣는 **백도어 로드**로 이 단계를 건너뛰기도 합니다.
- **부트로더·커널:** UART 트랜잭터가 출력 문자를 호스트에 넘겨 주므로, 실리콘과 거의 같은 콘솔 로그를 볼 수 있습니다.
- **커널 이후:** 많은 에뮬레이터가 실행 상태를 저장했다가 그 지점부터 다시 시작하는 **체크포인트** 기능을 제공합니다. 커널 부팅이 끝난 상태를 저장해 두면, 드라이버 테스트를 할 때마다 부팅을 처음부터 다시 할 필요가 없습니다. 게임의 세이브 포인트와 같습니다.

postcode는 펌웨어 쪽에서 아주 간단하게 구현됩니다. 아래 코드는 부트 단계마다 번호를 남기는 펌웨어 조각입니다. 같은 코드가 나중에 실리콘에서도 그대로 쓰이도록 주소만 플랫폼별로 바꿉니다.

```c
/* 에뮬레이터 모니터가 이 주소의 쓰기를 감시한다 (예시 주소) */
#define POSTCODE_REG  (*(volatile uint32_t *)0x0FFF0000u)
static inline void postcode(uint32_t v) { POSTCODE_REG = v; }

void bl1_main(void)
{
    postcode(0x0100);              /* BL1 진입 */
    clocks_init();
    postcode(0x0110);              /* 클럭 설정 완료 */
    if (!platform_is_backdoor_loaded())
        ddr_init();                /* 백도어 로드면 건너뜀 */
    postcode(0x0120);              /* 메모리 준비 */
    load_bl2();
    postcode(0x0130);              /* BL2로 점프 직전 */
    jump_to_bl2();
}
```

에뮬레이터의 모니터가 남기는 로그는 아래와 같은 모양이 됩니다. 마지막 postcode가 어디서 멈췄는지 보면 계단의 어느 칸에서 막혔는지 바로 알 수 있습니다.

```text
[cyc   0000012040] POSTCODE 0x0100
[cyc   0000098312] POSTCODE 0x0110
[cyc   0000098977] POSTCODE 0x0120   (backdoor: ddr init skipped)
[cyc   0000412090] POSTCODE 0x0130
[cyc   0000412095] -- no further postcode, timeout --
```

## 전체 가시성이 필요할 때의 비용

에뮬레이터의 장점은 넓은 가시성이지만, 그 가시성은 공짜가 아닙니다. 신호를 많이 기록할수록 에뮬레이터가 느려지고, 기록한 데이터를 waveform으로 바꾸는 데도 시간이 걸립니다. 그래서 *항상 전부 기록*하지 않고, Ch 10의 원칙을 그대로 따릅니다. 실패 시각을 먼저 알아내고, 그 근처만 넓게 기록합니다.

방송 중계에 빗대면 이렇습니다. 중계차에 카메라가 수십 대 있어도 모든 카메라 영상을 고화질로 녹화하면 저장 장치와 편집 시간이 감당되지 않습니다. 그래서 평소에는 메인 카메라만 녹화하다가, 결정적 장면이 나오면 그 순간의 모든 각도를 다시 돌려 봅니다.

실무에서는 보통 두 단계로 나눕니다.

1. **빠른 실행:** 기록을 최소로 하고 소프트웨어 로그와 postcode만 남깁니다. 실패하면 마지막 postcode와 cycle 번호를 얻습니다.
2. **깊은 실행:** 같은 이미지, 같은 조건으로 다시 돌리면서 실패 직전 구간의 신호를 넓게 기록합니다. 체크포인트가 있다면 실패 직전 체크포인트에서 시작해 시간을 더 아낍니다.

이 흐름이 통하려면 실행이 **결정적**(같은 입력이면 같은 결과)이어야 합니다. 호스트 쪽 테스트가 실제 시각이나 난수에 의존하면 두 번째 실행에서 버그가 안 나타날 수 있습니다. 재현성을 지키는 방법은 Ch 15에서 자세히 다룹니다.

## 공유 자원 운영 — 예약·재현·캡처

에뮬레이터는 여러 팀이 나눠 쓰는 자원이라 기술만큼 운영이 중요합니다. 같은 장비라도 운영 습관에 따라 한 팀이 하루에 돌리는 실험 수가 크게 달라집니다.

- **들어가기 전에 준비합니다.** 이미지, 테스트 스크립트, 기록할 신호 목록, 트리거 조건을 예약 시간 전에 준비합니다. 장비 앞에서 코드를 고치기 시작하면 예약 시간이 금방 사라집니다.
- **실패를 재현 패키지로 남깁니다.** 실패한 실행의 RTL 버전, 펌웨어 이미지, 테스트 스크립트, seed, 체크포인트를 묶어 남깁니다. 다음 예약 때 그대로 다시 돌릴 수 있어야 합니다.
- **SW와 HW가 같은 실행을 봅니다.** SW 엔지니어가 로그로 실패 시각을 알아내면, HW 엔지니어가 같은 패키지로 깊은 실행을 돌립니다. 같은 실행을 두 관점에서 보는 구조를 미리 정해 둡니다.
- **긴 작업은 야간 배치로 돌립니다.** 사람이 붙어 있어야 하는 대화형 디버깅과, 회귀 테스트처럼 혼자 도는 작업을 나눠 예약합니다.

호스트 쪽 테스트 스크립트는 보통 아래와 같은 모양입니다. API 이름은 벤더와 사내 도구마다 다르므로, 흐름만 참고하는 개념적 예시입니다.

```python
# 개념적 예시: 실제 API는 에뮬레이터 벤더와 사내 트랜잭터마다 다르다
emu = Emulator.connect(job="soc_a0_boot", rtl="a0_rc7")
emu.mem_backdoor_load("ddr0", "build/u-boot.bin", addr=0x8000_0000)
emu.mem_backdoor_load("ddr0", "build/Image",      addr=0x8020_0000)
emu.monitor_postcode(addr=0x0FFF_0000)        # postcode 쓰기를 cycle과 함께 기록
emu.release_reset()

uart = emu.transactor("uart0")
log = uart.read_until(b"login:", timeout_cycles=2_000_000_000)
emu.save_checkpoint("after_login")             # 이후 드라이버 테스트의 시작점
emu.export_repro_bundle("runs/2026-10-05_boot")  # 재현 패키지
```

## 작은 예시 — 백도어 로드 직후 부트로더가 멈출 때

에뮬레이터에서 부트로더가 메모리 준비 단계 직후 멈췄다고 합시다. 실리콘이라면 원인 후보가 넓겠지만, 에뮬레이터에서는 범위를 빠르게 좁힐 수 있습니다.

첫 번째 빠른 실행에서 postcode를 보니 `0x0120`(메모리 준비)까지는 찍히고 `0x0130`이 나오지 않았습니다. 그 사이에는 `load_bl2()`가 있습니다. 두 번째 깊은 실행에서는 `0x0120`이 찍힌 cycle 직후부터 코어의 PC와 메모리 버스 트랜잭션을 기록했습니다. 그랬더니 코어가 DDR의 특정 주소를 읽는 요청을 보낸 뒤 응답을 받지 못하고 멈춰 있었습니다.

DDR 컨트롤러 쪽 신호를 보니, 백도어 로드로 DDR 초기화를 건너뛴 탓에 컨트롤러의 "초기화 완료" 플래그가 켜지지 않았고, 컨트롤러가 모든 읽기 요청을 보류하고 있었습니다. 원인은 RTL 버그가 아니라 *백도어 로드 흐름의 빈틈*이었습니다. 백도어로 메모리를 채울 때는 컨트롤러 상태도 함께 맞춰 줘야 했습니다. 팀은 백도어 로드 스크립트에 컨트롤러 상태 설정을 추가하고, "백도어 로드 시 실제 DDR 초기화 경로는 검증되지 않는다"는 사실을 검증 계획에 따로 적어 두었습니다.

이 예시는 에뮬레이터 디버깅의 흔한 함정을 보여 줍니다. 속도를 위해 건너뛴 단계가 새로운 문제를 만들 수 있고, 건너뛴 단계는 *검증되지 않은 단계*로 기록해 둬야 합니다.

## 실제 사례 — 표준 인터페이스와 하이브리드 구성

앞에서 소개한 SCE-MI는 트랜잭터를 특정 장비에 묶지 않으려는 업계 표준으로, "기다리는 횟수를 줄인다"는 원칙이 설계 동기 중 하나입니다. 표준 덕분에 같은 트랜잭터를 여러 벤더 장비에서 재사용할 길이 열렸습니다.

또 하나 널리 쓰이는 구성이 **하이브리드 에뮬레이션**입니다. CPU 코어처럼 검증이 끝난 IP는 빠른 소프트웨어 모델(virtual platform)로 돌리고, 새로 설계한 블록만 에뮬레이터의 RTL로 돌리는 방식입니다. 운영체제 부팅처럼 CPU가 대부분의 일을 하는 구간의 실행 시간을 크게 줄일 수 있어서, 주요 EDA 벤더가 이런 구성을 제공합니다. Cadence Palladium과 Synopsys ZeBu 계열도 에뮬레이터를 가상 CPU 모델과 짝지어 돌리는 하이브리드 흐름을 내세웁니다. 모델과 RTL을 섞을 때 생기는 불일치 문제는 다음 장의 주제입니다.

## 자주 하는 실수

- **장비 앞에서 준비를 시작합니다.** 이미지 빌드나 스크립트 수정은 예약 전에 끝냅니다.
- **처음부터 모든 신호를 기록합니다.** 실행이 느려지고 결과 파일이 다루기 어려워집니다. 빠른 실행으로 시각을 먼저 찾습니다.
- **건너뛴 단계를 잊습니다.** 백도어 로드나 모델 대체로 건너뛴 단계는 검증 계획에 "미검증"으로 남깁니다.
- **호스트와 너무 자주 동기화합니다.** 한 글자마다 호스트 응답을 기다리는 트랜잭터는 에뮬레이터의 속도를 다 깎아 먹습니다. 메시지를 묶어서 보냅니다.
- **재현 패키지 없이 실패를 보고합니다.** "어제 에뮬레이터에서 한 번 멈췄다"는 보고로는 아무도 다시 볼 수 없습니다.

## 정리

- 에뮬레이터는 칩 전체 RTL을 시뮬레이션보다 훨씬 빠르게 돌려, 실리콘 전에 펌웨어와 OS를 RTL 위에서 부팅하게 해 줍니다.
- 트랜잭터는 호스트의 메시지와 RTL의 cycle 단위 신호를 서로 바꿔 줍니다. 호스트와 동기화하는 횟수를 줄이는 것이 성능의 핵심이고, SCE-MI가 이 연결을 표준화합니다.
- 부팅 단계마다 PC trace, postcode, 백도어 로드, UART 트랜잭터, 체크포인트처럼 알맞은 디버그 수단이 있습니다.
- 넓은 가시성은 비쌉니다. 빠른 실행으로 실패 시각을 찾고, 깊은 실행으로 그 근처만 넓게 기록합니다. 이 흐름은 결정적인 실행을 전제로 합니다.
- 에뮬레이터는 공유 자원이라 준비, 재현 패키지, SW와 HW의 역할 분담 같은 운영이 생산성을 좌우합니다.
- 속도를 위해 건너뛴 단계는 검증되지 않은 단계로 기록합니다.
