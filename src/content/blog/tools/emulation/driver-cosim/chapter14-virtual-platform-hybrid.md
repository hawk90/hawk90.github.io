Ch 5에서 virtual platform으로 펌웨어를 먼저 돌리는 법을 봤습니다. 이 장은 그다음에 반드시 찾아오는 문제, 즉 모델에서는 되던 펌웨어가 RTL에서는 안 되는 상황을 다룹니다.

**virtual platform**은 칩을 C/C++ 모델로 흉내 내는 환경이고, 모델은 사람이 스펙을 읽고 만든 *해석*입니다. RTL도 다른 사람이 같은 스펙을 읽고 만든 또 하나의 해석입니다. 두 해석이 조금이라도 다르면, 한쪽에서 통과한 소프트웨어가 다른 쪽에서 실패합니다. 이 장은 그 불일치를 유형별로 정리하고, 체계적으로 찾아내고, 셋 중 누구를 고칠지 판정하는 방법을 다룹니다.

## 모델이 거짓말을 하는 순간

펌웨어 팀은 몇 달 동안 virtual platform 위에서 드라이버를 개발했습니다. 모든 테스트가 통과했고, RTL이 에뮬레이터에 올라오자마자 같은 드라이버를 올렸습니다. 그런데 부팅 초반부터 드라이버가 멈춥니다. 펌웨어 팀은 "RTL 버그"라고 보고하고, RTL 팀은 "스펙대로 만들었다"고 답합니다.

이런 대립은 pre-silicon 프로젝트에서 아주 흔합니다. 문제는 대개 어느 한쪽의 실수라기보다 *모델과 RTL이 스펙을 다르게 읽었다*는 데 있습니다. 지도와 실제 지형의 관계와 비슷합니다. 지도는 쓸모가 많지만, 지도를 만든 사람이 생략하거나 잘못 그린 길이 있으면 지도만 믿고 간 사람은 길을 잃습니다. 그리고 그 길이 지도와 다를 때, 틀린 쪽이 지도인지 지형 공사가 잘못된 것인지는 *원래 설계도(스펙)*를 봐야 알 수 있습니다.

SW와 HW 엔지니어는 이 불일치를 다른 모습으로 겪습니다.

| 관점 | 겪는 증상 | 흔한 첫 반응 |
|---|---|---|
| SW 엔지니어 | 모델에서 통과한 드라이버가 RTL에서 멈추거나 값이 다름 | "RTL이 틀렸다" |
| HW 엔지니어 | 드라이버가 스펙에 없는 순서나 타이밍을 가정함 | "드라이버가 틀렸다" |

둘 다 맞을 수도, 둘 다 틀릴 수도 있습니다. 판정에는 감이 아니라 절차가 필요합니다.

## 불일치 유형 — 리셋값·타이밍·부작용·미구현 기능

불일치는 무작위로 생기지 않고 몇 가지 유형으로 반복됩니다. 유형을 알면 어디부터 볼지 정할 수 있습니다.

| 유형 | 모델 쪽 동작 | RTL 쪽 동작 | SW에서 보이는 증상 |
|---|---|---|---|
| 리셋값 | 모든 레지스터가 0으로 시작 | 일부 비트가 1로 시작 | 초기화를 빠뜨린 설정이 RTL에서만 문제 |
| 타이밍 | 명령이 즉시 끝남 | 여러 cycle이 걸림 | 완료 확인 없이 결과를 쓰는 코드가 RTL에서 실패 |
| 부작용 | 상태 레지스터를 일반 저장소처럼 처리 | 읽으면 지워지거나, 1을 써야 지워짐 | 인터럽트가 안 지워지거나 두 번 처리됨 |
| 미구현 기능 | 오류 경로·특수 모드를 무시 | 오류 응답을 냄 | 모델에서 본 적 없는 오류 처리 코드가 처음 실행됨 |
| 순서·동시성 | 요청을 하나씩 순서대로 처리 | 여러 요청을 겹쳐 처리하거나 순서를 바꿈 | 순서를 가정한 드라이버가 가끔 틀린 데이터를 받음 |

이 중 SW 엔지니어를 가장 많이 괴롭히는 것은 **타이밍**과 **부작용**입니다. 모델은 보통 "기능만 맞으면 된다"는 목표로 만들어지기 때문에, DMA를 요청하면 그 자리에서 메모리 복사를 끝내 버립니다. 그러면 완료를 확인하지 않고 결과를 쓰는 드라이버도 모델에서는 늘 통과합니다. 아래 코드가 그런 드라이버의 전형입니다.

```c
/* 회피: 시작만 하고 완료를 확인하지 않은 채 결과를 사용 */
writel(DMA_START, base + DMA_CTRL);
memcpy(result, dma_buf, len);        /* 모델: 이미 끝나 있음 / RTL: 아직 진행 중 */

/* Good: 완료 비트를 확인한 뒤 사용 */
writel(DMA_START, base + DMA_CTRL);
if (readl_poll_timeout(base + DMA_IRQ_STAT, stat, stat & DMA_DONE, 10, 10000))
    return -ETIMEDOUT;
memcpy(result, dma_buf, len);
```

**부작용** 불일치는 모델 쪽 실수로 생기는 경우가 많습니다. 스펙에 "이 비트는 1을 써서 지운다(write-1-to-clear)"고 적혀 있어도, 모델 작성자가 바쁘면 일반 레지스터처럼 쓴 값을 그대로 저장해 버립니다. 아래는 그런 모델 코드와 올바른 코드를 나란히 놓은 예입니다.

```c
/* 모델의 레지스터 쓰기 처리 (QEMU 디바이스 모델 스타일) */
static void dma_write(void *opaque, hwaddr addr, uint64_t val, unsigned size)
{
    DmaState *s = opaque;
    switch (addr) {
    case DMA_IRQ_STAT:
        /* 회피: s->irq_stat = val;  쓴 값이 그대로 저장된다 */
        s->irq_stat &= ~val;         /* Good: 1을 쓴 비트만 지운다 */
        dma_update_irq(s);
        break;
    /* ... */
    }
}
```

## 불일치를 찾는 비교 테스트 — lockstep과 trace diff

불일치를 하나씩 우연히 발견하면 프로젝트 내내 같은 대립이 반복됩니다. 그래서 두 구현을 *기계적으로 대조*하는 방법을 씁니다. 회계에서 두 장부를 한 줄씩 맞춰 보며 처음으로 숫자가 어긋나는 줄을 찾는 것과 같은 원리입니다.

가장 강력한 방법은 **lockstep 비교**입니다. 같은 프로그램을 참조 모델과 RTL에서 동시에 돌리면서, 명령어 하나가 끝날 때마다 PC와 레지스터 쓰기 결과를 비교합니다. 첫 불일치가 나오는 명령어에서 바로 멈추므로, 원인과 증상 사이의 거리가 거의 0이 됩니다. Ch 11에서 assertion이 하던 일을 *모델 전체*가 하는 셈입니다.

![lockstep 비교 — 같은 테스트 프로그램을 참조 모델과 RTL에서 돌리고, 명령어마다 PC·레지스터·메모리 쓰기를 비교기로 대조해 첫 불일치에서 정지하는 구성](/images/blog/driver-cosim/diagrams/ch14-lockstep.svg)

lockstep에서 까다로운 부분은 **비결정적인 값**입니다. 인터럽트가 들어오는 시점, 타이머 값, 주변 장치 레지스터에서 읽은 값은 모델과 RTL에서 다를 수밖에 없습니다. 이런 값은 비교 대상에서 빼거나, RTL에서 읽은 값을 모델에 그대로 주입해 두 구현이 같은 길을 가도록 맞춥니다.

명령어 단위 lockstep이 어려운 경우(예: 주변 장치 블록처럼 CPU가 아닌 IP)에는 **trace diff**를 씁니다. 두 플랫폼에서 같은 테스트를 돌리며 레지스터 접근과 인터럽트 기록을 남기고, 시각 정보를 뺀 뒤 순서대로 비교합니다. 아래 스크립트는 두 trace를 비교해 첫 불일치를 찾습니다.

```python
# 형식: "<time> <R|W|IRQ> <addr> <value>" 한 줄에 접근 하나
def events(path):
    with open(path) as f:
        for line in f:
            _t, op, addr, val = line.split()
            yield op, addr, val                 # 시각은 비교에서 뺀다

def first_mismatch(model_trace, rtl_trace):
    for i, (m, r) in enumerate(zip(events(model_trace), events(rtl_trace))):
        if m != r:
            return i, m, r
    return None

hit = first_mismatch("model.trace", "rtl.trace")
print("identical" if hit is None else f"first mismatch #{hit[0]}: model={hit[1]} rtl={hit[2]}")
```

이렇게 찾은 첫 불일치는 "모델은 `IRQ_STAT`을 읽으면 0x1인데 RTL은 0x3"처럼 구체적인 형태로 나옵니다. 막연한 "RTL에서 드라이버가 멈춘다"보다 훨씬 다루기 쉬운 출발점입니다.

## 누구를 고칠까 — 모델이냐 RTL이냐 스펙이냐

불일치를 찾았다면 다음 질문은 *누구를 고칠 것인가*입니다. 이 질문에 감정 없이 답하는 방법은 순서를 정해 두는 것입니다. 기준은 늘 **스펙**입니다.

![누구를 고칠까 — 모델과 RTL의 불일치를 발견하면 먼저 스펙에 동작이 분명히 적혀 있는지 묻고, 없으면 스펙을 보완하고, 있으면 RTL이 스펙대로인지 물어 RTL 또는 모델을 고치는 흐름](/images/blog/driver-cosim/diagrams/ch14-who-to-fix.svg)

1. **스펙에 이 동작이 분명히 적혀 있나?** 적혀 있지 않거나 두 가지로 읽힌다면, 모델도 RTL도 틀린 것이 아닙니다. 스펙의 빈틈입니다. 아키텍트가 먼저 동작을 정하고 스펙을 고친 뒤, 그 결정에 맞춰 나머지를 고칩니다.
2. **RTL이 스펙대로 동작하나?** 아니라면 RTL 버그입니다. 테이프아웃 전이라면 RTL을 고치는 것이 가장 싸게 끝나는 길입니다.
3. **RTL이 스펙대로라면** 모델이 스펙을 잘못 이해한 것입니다. 모델을 고치고, 그 모델에서만 통과하던 드라이버 코드도 함께 점검합니다.

번역본과 원서의 관계로 생각하면 쉽습니다. 두 번역본이 서로 다르면 원서를 펼쳐 봅니다. 원서가 모호하면 원저자에게 묻고, 원서가 분명하면 틀린 번역본을 고칩니다.

실무에서 한 가지 더 따져야 할 것은 **일정**입니다. 테이프아웃이 임박했는데 RTL을 고치는 비용이 크다면, 스펙을 RTL 동작에 맞춰 바꾸고 드라이버가 그 동작을 따르도록 결정하기도 합니다. 이 결정은 기술 판단이면서 동시에 프로젝트 판단이라, 결정 이유를 문서로 남겨 두어야 나중에 같은 논쟁이 반복되지 않습니다.

## 모델을 RTL에 맞춰 유지하는 운영

모델과 RTL의 불일치는 한 번 고쳐서 끝나지 않습니다. RTL은 프로젝트 내내 바뀌고, 모델은 별도 팀이 관리하는 경우가 많아서 시간이 지날수록 둘이 벌어집니다. 그래서 불일치를 *계속* 잡는 구조를 만들어 둡니다.

- **스펙을 한 곳에서 생성합니다.** 레지스터 맵을 IP-XACT나 SystemRDL 같은 기계가 읽는 형식으로 관리하고, 거기서 RTL 레지스터 블록, 모델의 레지스터 정의, 드라이버 헤더를 함께 생성하면 리셋값과 비트 위치 불일치가 원천적으로 줄어듭니다.
- **비교 테스트를 회귀에 넣습니다.** lockstep이나 trace diff를 야간 회귀에 넣어 두면, RTL이나 모델이 바뀔 때 새 불일치가 다음 날 아침 바로 드러납니다.
- **모델의 한계를 문서로 남깁니다.** 모델이 일부러 흉내 내지 않는 기능(정확한 타이밍, 특정 오류 경로)을 목록으로 관리합니다. 그 목록은 곧 "모델에서 통과해도 믿으면 안 되는 영역"입니다.
- **불일치를 버그 트래커에서 별도로 분류합니다.** "모델 버그", "RTL 버그", "스펙 빈틈"을 따로 세면, 어느 쪽이 자주 틀리는지가 보이고 다음 프로젝트의 계획에 반영할 수 있습니다.

## 작은 예시 — 인터럽트가 두 번 처리되는 드라이버

virtual platform에서는 문제없던 드라이버가 RTL에서 DMA 완료 인터럽트를 두 번씩 처리한다는 보고가 들어왔다고 합시다. 두 번째 처리에서 이미 해제한 버퍼를 다시 해제하려다 커널 경고가 납니다.

trace diff를 돌려 보니 첫 불일치는 ISR 안에서 나왔습니다. 드라이버가 ISR에서 `IRQ_STAT`을 한 번 읽은 뒤 다시 읽으면, 모델에서는 0x0인데 RTL에서는 여전히 0x1이었습니다. 앞의 판정 순서를 따라 스펙을 펼쳐 보니 `IRQ_STAT`은 "1을 써서 지우는(write-1-to-clear)" 레지스터로 분명히 적혀 있었고, RTL도 그대로 구현돼 있었습니다.

문제는 모델이었습니다. 모델은 이 레지스터를 "읽으면 지워지는(read-to-clear)" 레지스터로 잘못 구현했고, 드라이버는 그 모델에 맞춰 작성돼 상태를 읽기만 하고 1을 쓰지 않았습니다. 모델에서는 읽는 순간 비트가 지워졌으니 문제가 없었습니다. RTL에서는 비트가 그대로 남아 인터럽트가 계속 걸려 있었고, ISR이 끝나자마자 같은 인터럽트로 다시 불려 이미 처리한 완료를 한 번 더 처리했습니다.

판정은 "스펙은 분명하고, RTL은 스펙대로이며, 모델이 틀렸다"입니다. 모델의 레지스터 의미를 write-1-to-clear로 고치자, 모델에서도 드라이버가 똑같이 실패했습니다. 이제 드라이버를 스펙에 맞게 고치고(읽은 값을 그대로 다시 써서 지우기) 모델에서 바로 검증할 수 있는 환경이 생겼습니다. 팀은 이 레지스터 맵을 SystemRDL로 옮겨 레지스터 의미까지 한 곳에서 생성하기로 했습니다.

## 실제 사례 — RISC-V 생태계의 참조 모델

lockstep 비교가 가장 잘 정착된 곳 중 하나가 RISC-V 생태계입니다. RISC-V 재단이 관리하는 **Spike**는 RISC-V ISA의 참조 시뮬레이터로, 많은 RISC-V 코어 프로젝트가 자기 RTL의 실행 결과를 Spike와 비교하는 데 씁니다. Spike가 "스펙을 코드로 옮긴 기준"에 가까운 역할을 하기 때문에, RTL과 결과가 다르면 일단 RTL을 의심할 근거가 됩니다.

Esperanto Technologies가 공개하고 지금은 CHIPS Alliance에서 관리하는 **Dromajo**도 같은 목적의 RISC-V 참조 모델입니다. RTL 시뮬레이션과 함께 돌면서 명령어마다 결과를 대조하는 co-simulation을 염두에 두고 만들어졌습니다. 앞에서 말한 비결정적인 값(인터럽트 등)을 RTL과 맞추는 문제를 다뤄야 한다는 점도 이런 도구들이 공통으로 고민하는 지점입니다.

## 자주 하는 실수

- **모델 통과를 기능 검증 완료로 봅니다.** 모델은 스펙의 한 해석일 뿐입니다. 타이밍과 부작용은 모델에서 검증되지 않았을 가능성이 큽니다.
- **불일치를 감으로 판정합니다.** "보통 RTL이 맞겠지", "모델이 단순하니까 맞겠지" 같은 판단은 매번 틀릴 수 있습니다. 스펙을 기준으로 순서대로 묻습니다.
- **비결정적인 값까지 비교합니다.** 타이머나 인터럽트 시점까지 비교하면 의미 없는 불일치가 쏟아집니다. 비교에서 빼거나 RTL 값을 모델에 주입합니다.
- **모델에 맞춰 짠 드라이버를 그대로 둡니다.** 모델을 고쳤다면, 그 모델에서만 통과하던 드라이버 코드가 있는지도 함께 찾아봅니다.
- **레지스터 정의를 손으로 세 번 씁니다.** RTL, 모델, 드라이버 헤더를 따로 손으로 쓰면 리셋값과 비트 위치가 반드시 어긋납니다.

## 정리

- 모델과 RTL은 같은 스펙의 서로 다른 해석입니다. 해석이 어긋나면 한쪽에서 통과한 소프트웨어가 다른 쪽에서 실패합니다.
- 불일치는 리셋값, 타이밍, 부작용, 미구현 기능, 순서·동시성 다섯 유형으로 반복됩니다. SW를 가장 괴롭히는 것은 타이밍과 부작용입니다.
- lockstep 비교는 명령어마다 두 구현을 대조해 첫 불일치에서 멈추고, trace diff는 레지스터 접근 기록을 순서대로 비교합니다. 비결정적인 값은 빼거나 맞춥니다.
- 누구를 고칠지는 스펙을 기준으로 정합니다. 스펙이 모호하면 스펙을, RTL이 스펙과 다르면 RTL을, 그렇지 않으면 모델을 고칩니다.
- 레지스터 맵을 한 곳에서 생성하고, 비교 테스트를 회귀에 넣고, 모델의 한계를 문서로 남기면 불일치가 계속 관리됩니다.
- RISC-V의 Spike와 Dromajo처럼 참조 모델과 RTL을 대조하는 흐름은 이미 오픈소스 생태계에 자리 잡았습니다.
