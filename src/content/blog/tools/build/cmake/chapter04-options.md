## 왜 캐시 변수가 필요한가

`cmake -B build`를 부를 때마다 *모든 설정*을 다시 입력해야 한다면 빌드 사이클이 견디기 힘들어집니다.

```bash
# 매번 이걸 칠 수는 없다
cmake -B build -DCMAKE_BUILD_TYPE=Debug -DENABLE_TESTS=ON -DUSE_SYSTEM_ZLIB=OFF
```

CMake의 답은 *캐시*입니다. 캐시 항목은 `build/CMakeCache.txt`에 저장되어 다음 구성 호출에서도 유지됩니다. 일반 변수와 타겟 속성은 이 파일에 저장되지 않습니다. 캐시 값을 바꾸는 쪽은 사용자의 `-D`, 프로젝트의 `set(... CACHE ... FORCE)`, 그리고 `find_*` 같은 탐색 명령입니다.

실행 기준은 CMake 4.5.0·Ninja 1.13.2·macOS 27.2·AppleClang 21입니다. 예제의 최소 정책 기준은 3.25이고, 이 글의 출력은 모두 4.5.0에서 실행한 결과입니다. 이전 버전이나 Windows에서 실행한 결과는 아닙니다.

```bash
# 처음 — 모든 설정 명시
cmake -B build -DCMAKE_BUILD_TYPE=Debug -DENABLE_TESTS=ON

# 이후 — 캐시 자동 사용
cmake -B build                           # 이전 설정 그대로
cmake -B build -DENABLE_TESTS=OFF        # 변경할 것만
```

이게 *캐시 변수*의 첫 용도입니다. 그 외에도 캐시는 두 가지 역할을 더 합니다.

- **사용자 옵션**: 프로젝트가 사용자에게 노출하는 설정(`ENABLE_TESTS`, `BUILD_SHARED_LIBS` 등). `cmake-gui`나 `ccmake`에 보이는 모든 항목이 캐시 변수입니다.
- **탐지 결과 저장**: `find_library`·`find_path` 같은 탐색 명령은 찾은 경로를 캐시에 적고, 다음 구성에서 그 값이 있으면 다시 찾지 않습니다. `find_package(ZLIB REQUIRED)`를 macOS에서 구성하면 캐시에 `ZLIB_INCLUDE_DIR:PATH=.../MacOSX.sdk/usr/include`와 `ZLIB_LIBRARY_RELEASE:FILEPATH=.../MacOSX.sdk/usr/lib/libz.tbd`가 남습니다. 다만 캐시되는 것은 이 경로들이고 `find_package()` 호출 자체는 매번 실행됩니다. 두 번째 구성에서 `-- Found ZLIB: ...` 줄은 다시 찍히지 않았지만, 모듈이 채우는 `ZLIB_VERSION`(`1.2.12`)은 그대로 설정되어 있었습니다.

캐시 파일은 *그냥 텍스트*입니다. 직접 열어 보면 CMake가 무엇을 알고 있는지 한눈에 보입니다.

```text
$ head -3 build/CMakeCache.txt
# This is the CMakeCache file.
# For build in directory: .../cc/build
# It was generated by CMake: /opt/homebrew/bin/cmake
$ grep -E '^(BACKEND|CMAKE_BUILD_TYPE|CMAKE_CXX_COMPILER|ENABLE_FEATURE_Y):' build/CMakeCache.txt
BACKEND:STRING=gpu
CMAKE_BUILD_TYPE:STRING=
CMAKE_CXX_COMPILER:FILEPATH=/usr/bin/c++
ENABLE_FEATURE_Y:BOOL=ON
```

이 글 끝의 실전 예제를 두 번 구성한 뒤의 캐시입니다(경로는 줄였습니다). 항목은 `이름:타입=값` 형식이고, 파일 머리의 주석에도 `KEY:TYPE=VALUE`라고 적혀 있습니다. "왜 이 값으로 빌드됐지?"를 추적할 때 가장 먼저 열어 볼 파일입니다.

## 캐시 변수

### 설정 방법

```cmake
set(MY_VAR "default" CACHE STRING "변수 설명")
```

| 타입 | 설명 | GUI 표시 |
|------|------|----------|
| `STRING` | 문자열 | 텍스트 입력 |
| `BOOL` | 불리언 (ON/OFF) | 체크박스 |
| `PATH` | 디렉터리 경로 | 디렉터리 선택기 |
| `FILEPATH` | 파일 경로 | 파일 선택기 |
| `INTERNAL` | 내부 사용 | 표시 안 됨 |

```cmake
# 예시
set(MY_INSTALL_PREFIX "/usr/local" CACHE PATH "Installation prefix")
set(ENABLE_TESTS ON CACHE BOOL "Enable unit tests")
set(VERSION_STRING "1.0.0" CACHE STRING "Version string")
set(DETECTED_COMPILER_PATH "/usr/bin/gcc" CACHE INTERNAL "")
```

### 명령줄에서 설정

`-D변수=값` 형식으로 캐시 변수를 설정합니다.

```bash
cmake -B build -DENABLE_TESTS=OFF -DCMAKE_INSTALL_PREFIX=/opt/myapp
```

### 이미 존재하는 캐시 변수

캐시 변수는 **이미 존재하면 덮어쓰지 않습니다**. 이 동작 덕분에 사용자 설정이 보존됩니다.

```cmake
# 첫 번째 cmake 실행: MY_VAR = "default"가 캐시에 저장됨
set(MY_VAR "default" CACHE STRING "")

# 사용자가 cmake -DMY_VAR=custom 으로 실행
# MY_VAR = "custom"

# 두 번째 cmake 실행: 캐시에 이미 있으므로 "default"로 덮어쓰지 않음
set(MY_VAR "default" CACHE STRING "")
# MY_VAR = "custom" 유지
```

### FORCE 옵션

강제로 덮어쓰려면 `FORCE`를 사용합니다.

```cmake
set(MY_VAR "new_value" CACHE STRING "설명" FORCE)
```

**주의**: `FORCE`는 사용자가 `-D`로 준 값도 덮어씁니다. 아래 "FORCE 남용" 절에서 `-DENABLE_TESTS=OFF`가 실제로 사라지는 것을 봅니다. 그래서 CMakeLists.txt가 계산한 값을 저장할 때만 씁니다.

## `option()` 명령 — 불리언 캐시의 단축 문법

```cmake
option(ENABLE_TESTS "Enable unit tests" ON)

# 캐시가 없는 상태에서 BOOL 기본값을 제공하는 비슷한 예
set(ENABLE_TESTS ON CACHE BOOL "Enable unit tests")
```

`option()`은 켜기/끄기 설정을 제공하며, 새 캐시 항목을 만들 때 BOOL 타입을 사용합니다. `option(X "" yes)`도 유효한데, 4.5.0에서 구성하면 캐시에는 `yes`가 아니라 `X:BOOL=ON`으로 기록됐습니다. 다중 선택 문자열은 `set(... CACHE STRING ...)`으로 구분합니다.

일반 변수가 이미 존재할 때는 [`CMP0077`](https://cmake.org/cmake/help/v4.4/policy/CMP0077.html)(3.13 도입)의 상태가 중요합니다. 최소 버전 3.25에서는 NEW이므로, `set(X OFF)` 뒤의 `option(X "" ON)`은 일반 변수 OFF를 보존하고 캐시 항목을 만들지 않습니다(4.5.0에서 `X=OFF`, 캐시에 `X:` 항목 0개). 같은 파일을 `cmake_minimum_required(VERSION 3.12)`로 바꾸면 정책이 미설정이라 OLD 동작이 나옵니다.

```text
CMake Warning (policy) at CMakeLists.txt:4 (option):
  Policy CMP0077 is not set: option() honors normal variables.  Run "cmake
  --help-policy CMP0077" for policy details.  Use the cmake_policy command to
  set the policy and suppress this warning.

  For compatibility with older versions of CMake, option is clearing the
  normal variable 'X'.
...
-- X=ON
```

실행 중인 CMake가 4.5.0이어도 결과를 정하는 것은 최소 버전 선언입니다. [option() 문서](https://cmake.org/cmake/help/v4.4/command/option.html)를 기준으로 캐시와 일반 변수를 구분합니다.

### `option()` vs `set(... CACHE STRING ...)` — 언제 무엇을

| 상황 | 권장 |
|------|------|
| *켜기/끄기 토글* (true/false) | `option(NAME "doc" ON)` |
| *여러 값 중 하나* (예: "Debug" / "Release") | `set(NAME "Debug" CACHE STRING "doc")` + `set_property(CACHE NAME PROPERTY STRINGS Debug Release ...)` |
| *경로*  | `set(NAME "/path" CACHE PATH "doc")` |
| *파일 경로* | `set(NAME "/path/file" CACHE FILEPATH "doc")` |
| *사용자가 보면 안 되는 내부* | `set(NAME val CACHE INTERNAL "doc")` |

`set_property(CACHE ... PROPERTY STRINGS ...)`는 GUI에 선택 목록을 제공하는 메타데이터입니다. 명령줄 값은 검증하지 않습니다. 아래 예제에서 `IN_LIST` 검사를 빼고 `-DMYAPP_BACKEND=Metal`로 구성하면 아무 경고 없이 `B=Metal`로 진행됐습니다. [STRINGS 속성](https://cmake.org/cmake/help/v4.4/prop_cache/STRINGS.html)으로 후보를 안내하고, 허용 여부는 직접 검사합니다.

```cmake
set(MYAPP_BACKEND "OpenGL" CACHE STRING "Rendering backend")
set_property(CACHE MYAPP_BACKEND PROPERTY STRINGS OpenGL Vulkan DirectX)
set(SUPPORTED_BACKENDS OpenGL Vulkan DirectX)
if(NOT MYAPP_BACKEND IN_LIST SUPPORTED_BACKENDS)
    message(FATAL_ERROR "Unsupported backend: ${MYAPP_BACKEND}")
endif()
```

### 일반적인 옵션 패턴

```cmake
# 기능 토글
option(ENABLE_TESTING "Enable unit tests" ON)
option(ENABLE_COVERAGE "Enable code coverage" OFF)
option(ENABLE_SANITIZERS "Enable sanitizers in Debug" ON)

# 빌드 방식
option(BUILD_SHARED_LIBS "Build shared libraries" OFF)
option(BUILD_DOCS "Build documentation" OFF)

# 의존성 선택
option(USE_SYSTEM_ZLIB "Use system zlib instead of bundled" OFF)
option(USE_SYSTEM_JSON "Use system nlohmann_json" OFF)
```

### 옵션 사용

```cmake
option(ENABLE_TESTING "Enable testing" ON)
option(USE_SYSTEM_ZLIB "Use system zlib" OFF)

if(ENABLE_TESTING)
    enable_testing()
    add_subdirectory(tests)
endif()

if(USE_SYSTEM_ZLIB)
    find_package(ZLIB REQUIRED)
    target_link_libraries(myapp PRIVATE ZLIB::ZLIB)
else()
    add_subdirectory(third_party/zlib)
    target_link_libraries(myapp PRIVATE zlib)
endif()
```

## 캐시 변수와 일반 변수

같은 이름의 캐시 변수와 일반 변수가 있으면, **일반 변수가 우선**합니다.

```cmake
set(MY_VAR "cache_value" CACHE STRING "")
set(MY_VAR "normal_value")

message("${MY_VAR}")  # normal_value
```

캐시 값을 직접 참조하려면 `$CACHE{...}`를 사용합니다.

```cmake
set(MY_VAR "cache_value" CACHE STRING "")
set(MY_VAR "normal_value")

message("Cache: $CACHE{MY_VAR}")   # cache_value
message("Current: ${MY_VAR}")      # normal_value
```

일반 변수가 캐시를 가리면 `message("${MY_VAR}")`만으로는 캐시에 무엇이 남았는지 알 수 없습니다. 위처럼 `$CACHE{MY_VAR}`를 함께 찍으면 두 저장소의 값을 나란히 볼 수 있습니다(4.5.0 출력: `Cache: cache_value`, `Current: normal_value`).

## 조건부 옵션

### CMakeDependentOption

다른 옵션에 의존하는 옵션을 만듭니다.

```cmake
include(CMakeDependentOption)

option(BUILD_TOOLS "Build tools" ON)

# BUILD_TOOLS가 ON일 때만 BUILD_TOOL_A를 선택할 수 있음
# BUILD_TOOLS가 OFF이면 BUILD_TOOL_A는 강제로 OFF
cmake_dependent_option(
    BUILD_TOOL_A "Build tool A" ON
    "BUILD_TOOLS" OFF
)

cmake_dependent_option(
    BUILD_TOOL_B "Build tool B" ON
    "BUILD_TOOLS" OFF
)
```

조건이 거짓일 때 무슨 일이 일어나는지는 캐시를 보면 드러납니다. 4.5.0에서 `-DBUILD_TOOLS=OFF`로 구성하면 `BUILD_TOOL_A`의 캐시 항목이 `BUILD_TOOL_A:INTERNAL=...`로 바뀌어 GUI에서 숨겨지고, 일반 변수 `BUILD_TOOL_A`가 `OFF`로 설정됩니다. 이 상태에서 `-DBUILD_TOOL_A=ON`을 줘도 캐시 값만 `ON`이 되고 실제 값은 `OFF`였습니다. `-DBUILD_TOOLS=ON`으로 되돌리자 `BUILD_TOOL_A`가 `ON`이 됐습니다. 사용자가 고른 값은 캐시에 보존되고, 조건이 참일 때만 쓰입니다.

세미콜론으로 조건을 여러 개 줄 수도 있습니다.

```cmake
# ENABLE_TESTING이 ON이고 BUILD_SHARED_LIBS가 OFF일 때만 사용 가능
cmake_dependent_option(
    ENABLE_STATIC_TESTS "Static test builds" ON
    "ENABLE_TESTING;NOT BUILD_SHARED_LIBS" OFF
)
```

### FeatureSummary

설정된 기능을 요약 출력합니다.

```cmake
include(FeatureSummary)

option(ENABLE_FOO "Enable foo feature" ON)
option(ENABLE_BAR "Enable bar feature" OFF)
option(ENABLE_BAZ "Enable baz feature" ON)

add_feature_info(Foo ENABLE_FOO "The foo feature for X")
add_feature_info(Bar ENABLE_BAR "The bar feature for Y")
add_feature_info(Baz ENABLE_BAZ "The baz feature for Z")

feature_summary(WHAT ALL)
```

4.5.0의 구성 출력에는 다음 요약이 찍힙니다.

```text
-- The following features have been enabled:

 * Foo, The foo feature for X
 * Baz, The baz feature for Z

-- The following features have been disabled:

 * Bar, The bar feature for Y

```

구성 로그 끝에 켜진 기능과 꺼진 기능이 이렇게 모여 있으면, CI 로그나 이슈에 붙은 로그만 보고도 어떤 옵션으로 빌드했는지 알 수 있습니다.

## 빌드 타입 처리

### 기본 빌드 타입 설정

단일 구성 생성기의 빌드 타입은 캐시·환경·toolchain의 영향을 받습니다. 아래는 기존 값이 없을 때 Release 기본값을 제공하는 패턴입니다.

```cmake
# 단일 설정 생성기(Make, Ninja)에서만 유효
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    message(STATUS "Setting build type to 'Release' as none was specified.")
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Choose the type of build." FORCE)

    # GUI에서 선택 가능한 값 설정
    set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
        "Debug" "Release" "MinSizeRel" "RelWithDebInfo"
    )
endif()
```

`CMAKE_CONFIGURATION_TYPES`는 multi-config 생성기(Visual Studio, Xcode, Ninja Multi-Config)에서 설정됩니다. `Ninja Multi-Config`로 구성한 캐시에는 `CMAKE_CONFIGURATION_TYPES:STRING=Debug;Release;RelWithDebInfo`가 들어 있었습니다. 이 변수가 있으면 위 블록은 `CMAKE_BUILD_TYPE`을 건드리지 않습니다.

### 빌드 타입별 설정

아래 sanitizer 옵션은 GCC·Clang 계열을 전제로 합니다. MSVC의 옵션이나 지원 범위와 동일하지 않습니다. 실제 사용 시 두 방식 모두 해당 컴파일러인지 먼저 검사합니다.

**if문 방식** (단일 설정 생성기):

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug" AND
   CMAKE_CXX_COMPILER_ID MATCHES "^(GNU|Clang|AppleClang)$")
    target_compile_options(myapp PRIVATE -fsanitize=address)
    target_link_options(myapp PRIVATE -fsanitize=address)
endif()
```

**제너레이터 표현식 방식** (구성 선택에 독립적):

```cmake
if(CMAKE_CXX_COMPILER_ID MATCHES "^(GNU|Clang|AppleClang)$")
target_compile_options(myapp PRIVATE
    $<$<CONFIG:Debug>:-fsanitize=address,undefined>
)
target_link_options(myapp PRIVATE
    $<$<CONFIG:Debug>:-fsanitize=address,undefined>
)
endif()
```

제너레이터 표현식 쪽을 `Ninja Multi-Config`·AppleClang 21로 확인했습니다. 배열 `int a[2]`의 `a[2]`를 읽는 `main.cpp`를 빌드하면, `--config Debug`의 컴파일·링크 명령 두 줄에만 `-fsanitize`가 들어가고 `--config Release`에는 하나도 없었습니다. Debug 실행 파일은 이렇게 멈췄고, Release 실행 파일은 쓰레기 값을 찍고 종료 코드 0으로 끝났습니다.

```text
<src>/main.cpp:2:66: runtime error: index 2 out of bounds for type 'int[2]'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior <src>/main.cpp:2:66
=================================================================
==8747==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x00016b6a20c8 ...
```

MSVC에서 돌린 결과는 이 글에 없습니다.

## 설정 파일 생성

### configure_file

CMake 변수를 C/C++ 헤더로 내보냅니다.

**템플릿 파일** (`config.h.in`):

```c
#ifndef CONFIG_H
#define CONFIG_H

#define PROJECT_NAME "@PROJECT_NAME@"
#define VERSION_MAJOR @PROJECT_VERSION_MAJOR@
#define VERSION_MINOR @PROJECT_VERSION_MINOR@
#define VERSION_PATCH @PROJECT_VERSION_PATCH@

#cmakedefine ENABLE_FEATURE_X
#cmakedefine01 ENABLE_FEATURE_Y

#endif
```

**CMakeLists.txt**:

```cmake
set(ENABLE_FEATURE_X ON)
set(ENABLE_FEATURE_Y OFF)

configure_file(
    ${CMAKE_CURRENT_SOURCE_DIR}/config.h.in
    ${CMAKE_CURRENT_BINARY_DIR}/config.h
)

target_include_directories(myapp PRIVATE ${CMAKE_CURRENT_BINARY_DIR})
```

**생성된 파일** (`build/config.h`, 4.5.0에서 `project(MyApp VERSION 1.0.0)`로 구성한 실제 결과):

```c
#ifndef CONFIG_H
#define CONFIG_H

#define PROJECT_NAME "MyApp"
#define VERSION_MAJOR 1
#define VERSION_MINOR 0
#define VERSION_PATCH 0

#define ENABLE_FEATURE_X
#define ENABLE_FEATURE_Y 0

#endif
```

### 치환 규칙 — 네 가지 패턴

| 템플릿 | 결과 (값이 참) | 결과 (값이 거짓/미정의) |
|--------|---------------|----------------------|
| `@VAR@` | 변수 값 그대로 | OFF·0도 그대로, 미정의이면 빈 문자열 |
| `${VAR}` | 변수 값 그대로 | OFF·0도 그대로, 미정의이면 빈 문자열 (기본 모드) |
| `#cmakedefine VAR` | `#define VAR` | `/* #undef VAR */` |
| `#cmakedefine01 VAR` | `#define VAR 1` | `#define VAR 0` |

표는 `V_ON=ON`, `V_OFF=OFF`, `V_UNDEF` 미정의로 템플릿을 구성해 4.5.0에서 확인한 결과입니다. `@VAR@`과 `${VAR}`은 기본 모드에서 같은 결과를 냅니다. 문제는 템플릿이 셸 스크립트처럼 `${...}`를 자기 문법으로 쓰는 경우입니다. 기본 모드는 그 `${HOME}`까지 CMake 변수로 치환해 버립니다. `configure_file(... @ONLY)`을 주면 같은 템플릿의 `${V_ON}`이 치환되지 않고 그대로 남고, `@V_ON@`만 `ON`이 됐습니다.

일반 `#cmakedefine`은 변수의 값을 뒤에 자동으로 붙이지 않습니다. `V_STR=hello`일 때 `#cmakedefine V_STR`은 `#define V_STR`, `#cmakedefine V_STR "@V_STR@"`은 `#define V_STR "hello"`가 됐습니다. 반면 `#cmakedefine01`은 정의를 항상 만들고 값만 0/1로 바꾸므로 C/C++에서는 `#ifdef` 대신 `#if VAR`로 검사합니다. [configure_file 변환 규칙](https://cmake.org/cmake/help/v4.4/command/configure_file.html#transformations)을 기준으로 읽습니다.

```cmake
configure_file(
    script.sh.in
    script.sh
    @ONLY    # ${} 형태는 그대로 두고, @...@만 치환
)
```

### `configure_file()` vs `file(GENERATE ...)`

비슷해 보이는 두 명령이 *언제 평가되느냐*에서 갈립니다.

| | `configure_file()` | `file(GENERATE ...)` |
|---|---|---|
| 평가 시점 | *CMake 구성 시점* | *빌드 시스템 생성 시점* |
| 제너레이터 식 (`$<...>`) | *지원 안 함* (템플릿의 `$<CONFIG>`가 출력에 그대로 남음) | *지원* — 생성 시점에 풀림 |
| 입력 | 첫 위치 인자로 입력 파일 지정 | `CONTENT` 인라인 또는 `INPUT` |
| 구성당 출력 | 1개 | 구성마다 *다른 파일*도 가능 |

`configure_file()`은 *컴파일 시점에 고정될 정보*(버전 번호, 빌드 타입과 무관한 매크로)에 씁니다. 빌드 구성에 따라 *내용이 달라야 할 파일*은 `file(GENERATE ...)`을 씁니다.

```cmake
# configure_file() — 한 번만 결정
configure_file(version.h.in version.h)

# file(GENERATE) — 각 구성마다 결정 (예: pkg-config 파일)
file(GENERATE
    OUTPUT mylib-$<CONFIG>.pc
    INPUT mylib.pc.in
)
```

## CMakePresets.json

`CMakePresets.json`은 CMake 3.19 릴리스 노트에 처음 나옵니다. 아래 JSON은 스키마 version 6을 쓰는데, [cmake-presets(7)](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)은 version 6을 3.25에 추가된 형식으로 적습니다. 그래서 3.19~3.24의 CMake는 이 파일을 읽지 못합니다. [프리셋 형식 버전](https://cmake.org/cmake/help/v4.4/manual/cmake-presets.7.html#format)을 참고합니다.

### 기본 구조

```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "debug",
            "displayName": "Debug Build",
            "generator": "Ninja",
            "binaryDir": "${sourceDir}/build/debug",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Debug",
                "ENABLE_TESTING": "ON",
                "ENABLE_SANITIZERS": "ON"
            }
        },
        {
            "name": "release",
            "displayName": "Release Build",
            "generator": "Ninja",
            "binaryDir": "${sourceDir}/build/release",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Release",
                "ENABLE_TESTING": "OFF"
            }
        }
    ],
    "buildPresets": [
        {
            "name": "debug",
            "configurePreset": "debug"
        },
        {
            "name": "release",
            "configurePreset": "release"
        }
    ]
}
```

### 사용

```bash
# 프리셋 목록 확인
cmake --list-presets

# 프리셋으로 구성
cmake --preset debug

# 프리셋으로 빌드
cmake --build --preset debug
```

위 JSON과 `option(ENABLE_TESTING ...)`·`option(ENABLE_SANITIZERS ...)`을 둔 프로젝트에서 4.5.0으로 실행한 결과입니다.

```text
$ cmake --list-presets
Available configure presets:

  "debug"   - Debug Build
  "release" - Release Build
$ cmake --preset debug
...
-- Build files have been written to: .../pre/build/debug
$ cmake --build --preset debug
[1/2] Building CXX object CMakeFiles/app.dir/main.cpp.o
[2/2] Linking CXX executable app
$ grep -E '^(CMAKE_BUILD_TYPE|ENABLE_TESTING|ENABLE_SANITIZERS):' build/debug/CMakeCache.txt
CMAKE_BUILD_TYPE:STRING=Debug
ENABLE_SANITIZERS:BOOL=ON
ENABLE_TESTING:BOOL=ON
```

프리셋의 `cacheVariables` 세 개가 캐시에 그대로 들어갔고, 빌드 디렉터리는 `binaryDir`의 `build/debug`입니다.

### 상속

프리셋을 상속하여 공통 설정을 재사용합니다.

```json
{
    "version": 6,
    "configurePresets": [
        {
            "name": "base",
            "hidden": true,
            "generator": "Ninja",
            "cacheVariables": {
                "CMAKE_CXX_STANDARD": "17"
            }
        },
        {
            "name": "debug",
            "inherits": "base",
            "binaryDir": "${sourceDir}/build/debug",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Debug"
            }
        },
        {
            "name": "release",
            "inherits": "base",
            "binaryDir": "${sourceDir}/build/release",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Release"
            }
        }
    ]
}
```

`hidden: true`인 프리셋은 `--list-presets`에 나타나지 않지만 상속용으로 사용됩니다. 위 파일로 `--list-presets`를 실행하면 `"debug"`, `"release"`만 나오고, `cmake --preset base`는 `CMake Error: Cannot use hidden configure preset in ...: "base"`로 거부됐습니다.

## 캐시 관리

### 캐시 확인

```bash
# 텍스트로 확인
cat build/CMakeCache.txt

# 변수 검색
grep ENABLE build/CMakeCache.txt

# TUI (Terminal UI)
ccmake build

# GUI
cmake-gui build
```

### 캐시 초기화

문제가 생기면 캐시를 초기화합니다.

```bash
# 캐시 파일만 삭제
rm build/CMakeCache.txt
cmake -B build

# 3.24+: 캐시를 버리고 새 빌드 트리처럼 구성
cmake -B build --fresh

# 빌드 디렉터리 전체 삭제 (빌드 산물까지)
rm -rf build
cmake -B build
```

`--fresh`는 CMake 3.24 릴리스 노트에 "freshly created" 빌드 트리처럼 구성하는 옵션으로 나옵니다. 아래 "option 기본값이 적용 안 됨" 절에서 실제로 캐시 값을 버리는 것을 봅니다.

## 실전 예시 — OFF가 생성 헤더까지 전달되는지 확인하기

옵션 값이 CMakeCache.txt에만 있고 프로그램에 전달되지 않으면 사용자 설정은 효과가 없습니다. 다음 세 파일은 옵션·생성 헤더·실행 결과를 함께 확인하는 최소 프로젝트입니다.

```cmake title="CMakeLists.txt"
cmake_minimum_required(VERSION 3.25)
project(CacheCheck VERSION 1.0.0 LANGUAGES CXX)
option(ENABLE_FEATURE_X "Enable feature X" ON)
option(ENABLE_FEATURE_Y "Enable feature Y" OFF)
set(BACKEND "cpu" CACHE STRING "Execution backend")
set_property(CACHE BACKEND PROPERTY STRINGS cpu gpu)
set(SUPPORTED_BACKENDS cpu gpu)
if(NOT BACKEND IN_LIST SUPPORTED_BACKENDS)
    message(FATAL_ERROR "Unsupported backend: ${BACKEND}")
endif()
configure_file(config.h.in config.h @ONLY)
add_executable(app main.cpp)
target_include_directories(app PRIVATE "${CMAKE_CURRENT_BINARY_DIR}")
```

두 매크로의 생성 규칙을 같은 헤더에서 비교합니다.

```c title="config.h.in"
#pragma once
#cmakedefine ENABLE_FEATURE_X
#cmakedefine01 ENABLE_FEATURE_Y
#define APP_BACKEND "@BACKEND@"
```

`ENABLE_FEATURE_Y`는 OFF일 때도 정의되어 있으므로 값으로 분기합니다.

```cpp title="main.cpp"
#include "config.h"
#include <iostream>
int main() {
#if ENABLE_FEATURE_Y
    std::cout << "Y=ON\n";
#else
    std::cout << "Y=OFF\n";
#endif
    std::cout << "backend=" << APP_BACKEND << '\n';
}
```

Ninja가 있는 macOS·Linux 셸에서 같은 빌드 디렉터리를 재사용합니다.

```bash
cmake -S . -B build -G Ninja -DENABLE_FEATURE_Y=OFF -DBACKEND=cpu
cmake --build build
./build/app
cmake -S . -B build -DENABLE_FEATURE_Y=ON -DBACKEND=gpu
cmake --build build
./build/app
cmake -S . -B build
```

4.5.0에서 첫 실행은 `Y=OFF`, `backend=cpu`를, 두 번째는 `Y=ON`, `backend=gpu`를 출력했습니다. 각 시점의 `build/config.h`입니다.

```c
// 첫 구성
#pragma once
#define ENABLE_FEATURE_X
#define ENABLE_FEATURE_Y 0
#define APP_BACKEND "cpu"

// 두 번째 구성
#pragma once
#define ENABLE_FEATURE_X
#define ENABLE_FEATURE_Y 1
#define APP_BACKEND "gpu"
```

마지막 `cmake -S . -B build`는 옵션 없이 구성했는데도 캐시에 `BACKEND:STRING=gpu`, `ENABLE_FEATURE_Y:BOOL=ON`이 남아 있었습니다. `-DBACKEND=typo`로 구성하면 직접 작성한 검사가 멈춥니다.

```text
CMake Error at CMakeLists.txt:9 (message):
  Unsupported backend: typo
```

주의할 점은 구성이 실패해도 캐시에는 `BACKEND:STRING=typo`가 이미 기록된다는 것입니다. 다음 `cmake -S . -B build`도 같은 오류로 멈추므로, `-DBACKEND=cpu`로 값을 다시 줘야 합니다.

## 흔한 실수

### option 기본값이 적용 안 됨

처음에 `option(ENABLE_TESTS "..." OFF)`로 구성한 빌드 디렉터리에서, 나중에 CMakeLists.txt의 기본값을 `ON`으로 바꾼 경우입니다. 4.5.0에서 각 명령이 찍은 `ENABLE_TESTS` 값을 주석에 적었습니다.

```bash
cmake -B build -DENABLE_TESTS=OFF  # 처음 실행: OFF
# CMakeLists.txt를 option(ENABLE_TESTS "..." ON)으로 수정
cmake -B build                     # 여전히 OFF (캐시에 남아 있음)

# 해결: 명시적으로 변경하거나 캐시를 버림
cmake -B build -DENABLE_TESTS=ON   # 명시적 설정
cmake -B build --fresh             # 새 기본값 ON
```

### if(CMAKE_BUILD_TYPE)가 multi-config에서 동작 안 함

```cmake
# 회피: multi-config의 실제 구성 선택을 제어하지 못함
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    target_compile_definitions(app PRIVATE DEBUG_MODE)
endif()
# 값이 있어 참이 되더라도 모든 구성에 정의를 붙이는 문제가 있음

# Good: 제너레이터 표현식 사용
target_compile_definitions(app PRIVATE
    $<$<CONFIG:Debug>:DEBUG_MODE>
)
```

### FORCE 남용

```cmake
# 회피: 사용자 설정을 무시함
option(ENABLE_TESTS "..." ON)
# 사용자가 cmake -DENABLE_TESTS=OFF 로 실행해도...
set(ENABLE_TESTS ON CACHE BOOL "" FORCE)  # 강제로 ON
# 4.5.0 결과: ENABLE_TESTS=ON, 캐시도 ENABLE_TESTS:BOOL=ON

# Good: FORCE는 계산된 값에만 사용
set(DETECTED_INCLUDE_PATH "${FOUND_PATH}/include" CACHE PATH "" FORCE)
```

### 일반 변수와 캐시 변수 혼동

```cmake
# 회피: 일반 변수 설정이 캐시에 반영 안 됨
option(ENABLE_TESTS "..." ON)
set(ENABLE_TESTS OFF)  # 일반 변수
# 4.5.0 결과: ${ENABLE_TESTS}=OFF, $CACHE{ENABLE_TESTS}=ON

# Good: 캐시 변수 사용
set(ENABLE_TESTS OFF CACHE BOOL "" FORCE)
# 또는 명령줄에서
# cmake -B build -DENABLE_TESTS=OFF
```

## 정리

- **캐시 변수**는 `CMakeCache.txt`에 저장되어 재설정 시 유지됩니다.
- `option()`은 불리언 캐시 변수의 단축 문법입니다.
- 명령줄에서 `-DVAR=value`로 캐시 변수를 설정합니다.
- 캐시 변수는 **이미 존재하면 덮어쓰지 않습니다**.
- **일반 변수가 같은 이름의 캐시 변수보다 우선**합니다.
- `configure_file()`로 CMake 변수를 C/C++ 헤더로 내보냅니다.
- **CMakePresets.json**으로 빌드 설정을 미리 정의합니다.
- 빌드 타입별 설정은 **제너레이터 표현식**을 사용하세요.
