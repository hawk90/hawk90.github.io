# 6. 개선 우선순위

모든 문제를 한 번에 고치면 프로젝트가 또 커진다. 따라서 우선순위를 엄격하게 나누는 게 좋다.

---

## P0. 방향 결정

가장 먼저 해야 한다.

### 1. 저장소 목적 선언

```text
hawk90.github.io의 1차 목적은
개인 기술 지식베이스 운영이다.

범용 블로그 테마 개발은 2차 목적이다.
```

이 한 문장이 이후 기능 판단 기준이 된다.

### 2. 핵심 독자 정의

추천 독자는 다음 정도다.

```text
중급 이상의 C++·시스템·임베디드 개발자
저수준 소프트웨어와 하드웨어 경계를 공부하는 개발자
실제 장애 분석과 내부 동작을 찾는 엔지니어
```

모든 초보자를 대상으로 할 필요는 없다.

### 3. 핵심 분야 제한

홈에서 보여줄 핵심 분야를 5~6개로 제한한다.

```text
C++
Systems Programming
Firmware & Bootloader
GPU & CUDA
PCIe
CXL
```

태그는 많아도 되지만 최상위 주제는 적어야 한다.

---

## P1. 사용자에게 바로 보이는 구조 개선

### 1. 홈 개편

현재:

```text
Hero
Latest Posts
```

목표:

```text
Hero
Core Topics
Start Here
Featured Guides
Latest Posts
```

### 2. Topic Hub 5개 생성

초기에 추천하는 허브는 다음이다.

```text
C++
Systems Programming
Firmware & Bootloader
GPU & CUDA
PCIe & CXL
```

처음부터 PCIe와 CXL을 분리하지 않고 한 허브로 시작해도 된다.

### 3. 대표 문서 20개 선정

기준:

- 직접 경험이 들어감
- 검색 가치가 있음
- 내용이 여전히 유효함
- 다른 글의 기반이 됨
- 네 전문성을 잘 보여줌

이 20개가 사이트의 중심 문서가 된다.

### 4. 내부 링크 재설계

대표 문서마다 다음을 추가한다.

```text
상위 Topic
선행 지식
관련 개념
다음 글
```

## P1. 콘텐츠 가치 강화

### 1. 콘텐츠 타입 지정

최소 다음 6개면 충분하다.

```text
Guide
Concept
Debug Note
Experiment
Source Walkthrough
Reference
```

### 2. 핵심 글 구조 보완

대표 글부터 다음을 확인한다.

- 글의 목적
- 대상 독자
- 테스트 환경
- 버전
- 관찰
- 근거
- 해석
- 한계
- 결론
- 관련 글

### 3. 신뢰 정보 추가

특히 기술 변화가 빠른 글에는 다음을 표시한다.

```text
Published
Updated
Last Verified
Status
Tested Environment
```

### 4. 짧고 중복된 글 통합

다음 조건을 동시에 만족하는 글을 우선 검토한다.

- 동일한 검색 의도
- 배경 설명 중복
- 고유 실험이나 경험 없음
- 각각 너무 짧음
- 서로 강하게 의존

## P2. 기술 구조 개선

### 1. 빌드 프로파일링

측정할 항목:

```text
전체 빌드 시간
peak memory
Markdown 처리
Shiki 처리
검색 인덱스 생성
OG 생성
최종 출력 크기
```

### 2. 빠른 빌드와 배포 빌드 분리

```text
dev/fast
release
audit
```

를 분리한다.

### 3. 검색 인덱스 재설계

전체 본문 복사 대신:

- title
- description
- headings
- topics
- type
- keywords
- 핵심 excerpt

를 사용한다.

코드와 로그는 기본 검색에서 제외하거나 낮은 가중치를 준다.

### 4. 콘텐츠 manifest

모든 감사 스크립트가 각자 Markdown을 해석하지 않고, 공통 manifest를 사용하게 한다.

```json
{
  "slug": "...",
  "title": "...",
  "topics": [],
  "type": "...",
  "status": "...",
  "links": []
}
```

## P2. 유지보수 구조

### 1. 콘텐츠 스키마 정리

현재 필요한 최소 스키마:

```yaml
title:
description:
published:
updated:
type:
topics:
status:
```

모든 필드를 필수로 만들지는 않는다.

### 2. 오래된 글 상태 모델

```text
current
needs-review
historical
superseded
archived
```

### 3. 문서와 구현 일치

README에서:

- 현재 기능
- 실험 기능
- 계획 기능
- 제거된 기능

을 구분한다.

### 4. 관리자 기능 경계

공개 블로그의 static 구조를 깨는 관리자·OAuth 기능은 별도 앱 또는 명확히 분리된 package로 관리한다.

## P3. 나중에 해도 되는 것

다음은 우선순위가 낮다.

- 프레임워크 교체
- Astro 제거
- Tailwind 제거
- 전면적인 URL 변경
- 전체 글 metadata 일괄 수정
- 모든 페이지 디자인 재작성
- 검색엔진 서버 구축
- 복잡한 지식 그래프 시각화
- 모든 콘텐츠를 MDX로 변환
- 별도 CMS 구축

이런 작업은 흥미롭지만 현재 핵심 문제를 직접 해결하지 않는다.
