# 3. 세 번째 핵심 안티패턴

## Configuration as Architecture  
### 설정 파일이 아키텍처를 대신함

현재 README는 거의 모든 설정이 `src/consts/config.ts`에 있고, `defineSite`, `defineBranding`, `defineNav`, `defineComments`, `defineAnalytics`, `defineNewsletter` 같은 helper를 통해 관리된다고 설명한다. 런타임 비용은 거의 없고 타입 자동완성을 제공한다는 점은 좋다. citeturn214183view0

그러나 설정 항목이 계속 늘어나면 다음처럼 된다.

```text
defineSite
defineBranding
defineNav
defineSocial
defineComments
defineAnalytics
defineNewsletter
defineSearch
defineSeries
defineTheme
defineAdmin
defineResume
defineAbout
defineAds
defineSEO
```

이 상태에서는 설정이 단순 값 모음이 아니라 **작은 애플리케이션 프레임워크의 공개 API**가 된다.

### 문제

- 설정 조합 수가 폭증
- 실제 사용하지 않는 조합도 존재
- `enabled: false`가 계속 늘어남
- 컴포넌트가 설정 스키마에 종속
- 설정 변경이 여러 화면에 영향을 줌
- 어느 설정이 필수인지 불명확
- 개인 사이트인데 범용 제품 수준의 호환성을 고민함

### 개선 원칙

설정을 세 층으로 제한하는 게 좋다.

```text
1. Identity
2. Content behavior
3. External integrations
```

예:

```ts
site = {
  title,
  description,
  author,
  url,
  locale,
};

content = {
  pagination,
  search,
  series,
};

integrations = {
  analytics,
  comments,
  newsletter,
};
```

나머지는 코드의 고정 정책으로 두는 편이 단순할 수 있다.

> 모든 것을 설정 가능하게 만드는 것은 유연성이 아니라 책임 회피가 될 수 있다.
