# 콘텐츠 수정 안티패턴 카탈로그

AdSense 개선 루프에서 글을 고치다가 나온 안티패턴을 모은 목록이다. 수정자(fixer), 평가자(evaluator), 이중 확인자(double-checker)는 라운드를 시작할 때마다 이 파일을 읽는다.

- **추가 방식.** 루프마다 이중 확인 결과를 이 파일에 합친다. 새 항목은 다음 번호를 받고, 기존 항목에 해당하면 그 항목의 `예`에 사례를 덧붙인다. 어느 쪽이든 루프 번호와 날짜를 적는다. 항목당 `예`는 5개까지 두고, 넘치면 가장 배울 것이 많은 사례를 남긴다.
- **rubric과의 관계.** `docs/adsense-audit/rubric.md`는 글에 점수를 매긴다. 이 파일은 수정 과정에서 같은 실수가 되풀이되지 않게 막는다. 규칙이 rubric 상한·안전 규칙을 가리키면 rubric이 정본이다.
- **ID.** `AP-C-NN`(C = content). 방법론 배치의 `AP-D` ID와 겹치지 않는다. 항목은 주제별 절에 두므로 절 안의 ID가 번호순이 아닐 수 있다.
- **파일 경로.** `예`의 파일은 따로 적지 않으면 `src/content/blog/embedded/modern-recipes/` 아래에 있다. 다른 시리즈 글은 `src/content/blog/embedded/` 기준 경로로 적고, 그림 소스 `.tex`는 `public/images/blog/modern-recipes/diagrams/` 아래에 있다. 줄 번호는 관찰 당시 기준이다. 루프 표시가 없는 예는 파일럿 1이다.
- **출처.** 파일럿 루프 1(2026-10-11, 글 3편, 관찰 73건), 파일럿 루프 2(2026-10-11, 같은 글 3편, 관찰 37건), 묶음 2(2026-10-11, 글 9편, 관찰 110건)에서 정리했다.

## 1. 사실·수치

### AP-C-01 파생 수치를 다시 유도하지 않음
- **문제.** 수정자가 새로 쓴 분수·개수·클럭·최악값 같은 파생 값을 표를 만든 스크립트나 같은 출처의 다른 값으로 다시 확인하지 않는다. 결론이 맞더라도 유도가 틀리면 다른 숫자까지 의심받는다.
- **예.** `part1-10-can-electrical.md` L160 (14/16 → 16 TQ, 7/8로 약분 안 함) · `part12-01-edge-inference.md` L135-140 (역산한 NPU 180 MHz가 같은 페이지의 160 MHz와 충돌) · `part1-12-lvds-differential.md` L65-70 ('최악값(VOD 최소…)'이라 했지만 VIC 창 식에서는 VOD 최대가 최악, 대표 판정 '0.90 V'가 틀린 코너 위에 섬) (묶음 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L47 ('IRQ가 82개(FPU_IRQn = 81)', 최대 번호는 슬롯 수이고 F407 헤더는 79를 건너뜀) (묶음 2, 2026-10-11) · `part1-12-lvds-differential.md` L59 (1.91%를 '2% 남짓', 근사어 방향이 자기 계산과 반대) (묶음 2, 2026-10-11)
- **규칙.** 새로 쓴 파생 수치는 표를 만든 스크립트나 열거로 전제까지 다시 계산한다. 분수는 기약분수로 쓴다. 업체 수치에서 역산했으면 같은 출처가 직접 공개한 관련 값을 옆에 두고, 맞지 않으면 그렇다고 적는다. '최악' 라벨은 한계 식에 들어가는 변수의 코너(min/max 조합)를 모두 스크립트로 열거해 실제로 최소가 되는 코너에만 붙인다. 개수는 최대 인덱스가 아니라 출처 항목을 세어 구하고, 최대 인덱스에서 왔으면 '슬롯'이라고 쓴다. 한 출처의 두 수치를 한 문장에 두면 곱해 보아 명시된 율이 재현되는지 보고, 괄호 라벨(예: '22 DCLOCK')은 표 머리 조건과 각주를 읽은 뒤에 운용값으로 쓴다. 근사어(남짓·약·이상)는 다시 계산해 방향을 맞추고, 되도록 소수 한 자리 계산값을 쓴다.
- **확인.** diff에서 새로 생긴 숫자를 뽑아 스크립트 출력이나 출처 값과 하나씩 대조한다. '최악·최소·최대' 라벨마다 코너 열거가 있는지 본다.

### AP-C-02 선언한 조건 밖의 값을 같은 결론에 섞음
- **문제.** 앞에서 임의로 고른 파라미터나 선언한 가정 밖의 값이 뒤의 '한계'에 몰래 들어간다. 조건마다 따로 맞는 데이터시트 값을 합쳐 존재할 수 없는 동작점을 만들기도 한다. 그 조건에서도 결론이 거짓이 된다.
- **예.** `part1-10-can-electrical.md` L199 → L218-226·L267·L282 (76.2% 선택이 '한계 약 19 m'로 굳음) · 같은 글 L210 vs L238 (PS2 ≥ 2라고 해 놓고 PS2 = 1로 계산) · `part1-07-adc-principles.md` L68-78 (R_ADC max @ VDD 1.8 V와 f_ADC 30 MHz @ VDDA ≥ 2.4 V를 한 계산에 씀, VDDA = VDD라 불가능한 점에서 '0 Ω에서도 실패') (묶음 2, 2026-10-11) · `part1-05-spi-hardware.md` L55 vs L70·L76 (VDD 2.7-3.6 V로 고정해 놓고 tw(SCKL) min은 1.7-3.6 V 행, typ와 공칭값이 섞여 선언 조건의 답 −1.1 ns가 나오지 않음) (묶음 2, 2026-10-11) · `part2-08-arm-mmu.md` L85 vs L59 (52-bit가 기본이라 해 놓고 PTE_SHARED 행은 non-LPA2 배치, 인용한 mmap.c의 LPA2 분기는 PTE_SHARED를 지움) (묶음 2, 2026-10-11)
- **규칙.** '조건 X에서의 한계'는 X가 허용하는 구성을 모두 열거해서 구하거나, 추가로 고정한 값을 숫자가 반복되는 모든 곳(Q 답변·함정·정리)의 X에 적는다. 가정 밖에서 구한 값은 같은 문장에 '가정 X 밖의 상한'이라고 붙인다. 데이터시트 값을 식에 넣기 전에 값마다 조건을 적고 함께 성립하는지(VDDA = VDD 같은 전원 묶음 규칙 포함) 확인한다. 타이밍 예산은 모든 항을 선언한 조건 행 하나와 같은 통계(min 또는 max)에서 가져오고, 다른 행·typ 값은 행을 밝힌 민감도 문장 하나로 준다. 기본 구성을 선언했으면 표의 모든 행을 그 기본값에서 다시 확인한다.
- **확인.** 한계 수치가 나오는 모든 문장에서 조건 목록을 대조하고, 계산에 쓴 값이 선언한 가정 범위 안에 있는지 본다. 계산에 들어간 데이터시트 값마다 조건 행을 적어 서로 모순이 없는지 본다.

### AP-C-03 완전히 열거하지 않고 완전성을 주장함
- **문제.** '경계 표', 'N가지', 'X 중 가장 낮은 값', 'CAN 2.0 준수', '일어나지 않는다' 같은 표현은 빠진 것이 없다는 뜻인데, 실제 열거나 확인은 빠진 행·분기·조항·경로·레지스터가 있다.
- **예.** `part7-13-irq-affinity.md` L92 ('조건은 네 가지', `no_irq_affinity` 분기 누락) · 같은 글 L348-355 (hotplug 뒤 affinity 손실 대책으로 udev KOBJ_ONLINE 규칙만 제시, uevent가 없는 suspend/resume 경로는 빠짐) (파일럿 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L119-146 (부트로더 점프가 오래된 핸들러에 들어가지 않는다고 보장했지만 NVIC enable·pending만 지움, ICSR의 SysTick·PendSV pending, SHCSR, CONTROL, BASEPRI가 넘어감) (묶음 2, 2026-10-11) · `part1-05-spi-hardware.md` L15·L63 vs L75 ('세 값 중 가장 낮은 값'으로 정의한 뒤 판정 문장에 '보드 배선'을 넷째 조건으로 더함, 그 값을 줄 tCLQV는 쓰지 않음) (묶음 2, 2026-10-11) · `part1-04-uart-hardware.md` L117 (FIFO 문턱으로 줄인 인터럽트 간격은 정상 상태만, 문턱 아래 버스트 꼬리를 처리할 RTO/IDLE 경로가 없어 CR3 조각을 따라 하면 마지막 바이트를 잃음) (묶음 2, 2026-10-11)
- **규칙.** 열거 표는 스크립트로 만들고, 정의역과 필터를 본문에 적고, 출력과 diff한다. 'N가지'·'X 중 가장 낮은 값'은 인용 출처가 주는 항을 모두 나열한 뒤에만 쓰고(SPI라면 분주비, 컨트롤러 fSCK, 슬레이브 fR/FR, tCLQV와 마스터 setup에서 나온 MISO 타이밍), 뒤 문장이 조건을 더하지 않는지 grep한다. 아니면 개수 없이 나열하거나 범위를 붙인다('전압 기준 세 가지'). 준수 라벨은 이름 댄 규칙의 조항을 모두 확인했을 때만 붙이고, 아니면 확인한 조항을 적는다. 커널 상태 변화에 대한 대책은 그 변화를 일으키는 함수의 호출자를 모두 grep해 경로를 열거하고, 덮는 경로와 덮지 못하는 경로를 적는다. 상태를 넘기는 시퀀스(부트로더 점프, 문맥 전환)는 UG 레지스터 요약 표에서 pending·enable·mask 상태를 가진 레지스터(ICSR, SHCSR, NVIC ISER/ISPR, PRIMASK, BASEPRI, FAULTMASK, CONTROL)를 모두 나열하고, 각각 처리했는지 가정을 두고 그대로 뒀는지 적은 뒤에 'X는 일어나지 않는다'를 쓴다. 코드 경로를 설명할 때는 인용 함수에서 이름 댄 단계 사이의 호출을 모두 나열한다(dup_mmap의 `flush_tlb_mm`). 정상 상태의 처리량·간격 수치에는 나머지를 처리하는 경로를 이름 대거나 그 절을 링크한다.
- **확인.** 'N가지', '모든', '경계', '전부', '중 가장', '않습니다'를 grep해서 근거 열거와 개수를 대조한다. 준수 라벨이 붙은 열마다 규칙의 조항 목록과 대조한다. 대책·보장 문장마다 원인 경로·레지스터 목록이 있는지 본다.

### AP-C-04 코드 경로를 끝까지 따라가지 않은 동작 주장
- **문제.** 함수 조각이나 문서 문장을 읽고 동작을 추론해, 출처를 단 채 틀린 예시나 메커니즘을 쓴다. 필드나 함수 이름만 대고 효과를 쓰지 않거나, 인용한 함수의 본문을 읽지 않고 코드를 쓰거나, 보호 코드가 무엇을 덮는지 따라가지 않는다. 고쳐 쓴 문장이 새로운 오류가 되기도 한다.
- **예.** `part7-13-irq-affinity.md` L221 (taskset 덮어쓰기, 실제로는 `sched_setaffinity`가 EINVAL) · 같은 글 L77 ('첫 CPU를 redirect 대상으로 저장'만 쓰고, 그 값을 읽는 `demux_redirect_remote`가 핸들러를 어디서 돌리는지는 안 씀) (파일럿 2, 2026-10-11) · `part2-07-arm-mpu.md` L182-183 (`__set_CONTROL` 뒤에 `__ISB`를 더함, 인용한 CMSIS 5.9.0 `cmsis_gcc.h` L1001-1005의 `__set_CONTROL`은 이미 `__ISB()`로 끝남) (묶음 2, 2026-10-11) · 같은 글 L102-125·L155-160 (32 B stack guard와 MMFSR 결과 표, 예외 진입 스태킹·핸들러 push·guard를 건너뛰는 큰 프레임을 따라가지 않음) (묶음 2, 2026-10-11) · `part2-08-arm-mmu.md` L30 vs L71 (memory.rst의 'global only'는 non-KPTI 경우, 글이 다루는 KPTI·KASLR에서는 거짓) (묶음 2, 2026-10-11)
- **규칙.** 코드에서 끌어낸 예시는 단계마다 구체 값(어느 마스크를, 언제, 어떤 호출 순서로)을 추적하고 각 단계를 인용한다. 사용자 공간 명령에 대한 주장은 시스콜 진입점과 커널 쪽 처리를 모두 확인한다. 문서와 코드가 다르면 코드 동작을 쓴다. Documentation 문장이 코드 성질을 말하면 그 성질을 구현한 매크로·플래그(예: `PTE_MAYBE_NG`)를 태그 트리에서 grep하고, 글이 언급한 구성 중 그 성질을 바꾸는 것이 있으면 조건을 문장에 넣는다. 이름을 댄 커널 필드·함수는 관찰 가능한 효과를 한 문장으로 함께 쓰고, 저장되는 값은 그 값을 읽는 쪽까지 따라간 뒤 동작을 쓴다(`vm_page_prot` → `mk_pte` → `pte_mkwrite`). 인용한 헤더의 intrinsic은 고정 태그에서 본문을 읽고 코드를 그 동작에 맞춘다. 보호 코드(guard, watchdog, MPU 영역)는 커버리지 조건(guard 크기 ≥ 가장 큰 프레임 + 예외 프레임)을 쓰고, 예외 진입과 핸들러 자신의 스택 사용까지 fault 경로를 따라가며, 예측한 상태 비트마다 출처를 단다. 단계를 없애는 주장('maintenance가 필요 없다')은 경로 끝(DMA 시작)까지 따라가 남은 요구(배리어, 정렬)를 함께 적는다. 트리거는 '처음·한 번' 같은 서수어가 아니라 코드의 조건으로 쓴다. 고쳐 쓴 문장은 새 주장으로 보고 따로 출처를 단다.
- **확인.** 출처 링크가 그 문장 자체를 뒷받침하는지(옆 함수가 아닌지) 본다. 열거한 경우마다 조기 반환을 포함한 제어 흐름을 따라간다. 글의 코드가 부르는 intrinsic·함수마다 인용 태그의 본문을 열어 본다.

### AP-C-05 근거 범위와 주장 범위가 다름
- **문제.** 드라이버 하나, 기본 플래그 하나, 브랜치 하나, 코어 하나에서 본 사실을 하드웨어군·파라미터군·릴리스·부품 전체로 넓힌다. 거꾸로 일반 값을 특정 부품의 결과처럼 붙이거나, 일부 출처만 보고 '어느 자료에도 없다'고 쓴다.
- **예.** `part7-13-irq-affinity.md` L67 (GICv3 ITS 동작을 'arm64 SoC 전체'로) · 같은 글 L245 (master grep을 '1.9.5 소스에는 없다'로) · `part1-10-can-electrical.md` L5·L101·L287 (SLLA270의 일반 CAN 컨트롤러 지연으로 구한 결과를 title·description에서 STM32 bxCAN 결과로 제시) (파일럿 2, 2026-10-11) · `part1-05-spi-hardware.md` L51 (드라이버 헤더는 '74Hx164'지만 매치 표는 74hc595/74lvc594만 묶음, 래치 없는 부품을 이름 대 공유 CS 체인이 성립하지 않음) (묶음 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L132-138 (zero-wait-state에서만 맞는 코어 사이클 수를 STM32F407 시나리오 표에 넣음, 조건은 표 위 한 번뿐) (묶음 2, 2026-10-11)
- **규칙.** 한 드라이버에서 읽은 주장은 그 드라이버가 다루는 하드웨어로 한정하고, 하드웨어 이름은 파일 이름이나 헤더 주석이 아니라 고정 태그의 `of_device_id`·`spi_device_id`·ACPI 매치 표에서 가져온다. 드라이버의 구현 선택은 그 드라이버의 선택으로 쓰고, 모든 장치에 대한 주장은 여러 부품군을 다루는 출처나 메커니즘 유도(유도라고 표시)로 뒷받침한다. 코어 수준 수치를 특정 부품 예에 넣으면 조건을 같은 칸이나 열 머리에 두거나 수치 없이 순서만 준다. 부재 주장에는 검색 범위를 적고 태그된 릴리스 트리에서 검색한다. 일반 값은 표에 일반 값이라고 적고, 그 부품 자료를 쓰지 않은 결과에 부품 이름을 붙이지 않는다. '어느 자료에도 없다'는 인용한 출처를 모두 다시 검색한 뒤에만 쓴다.
- **확인.** '모든/전체/없다' 주장마다 검색하거나 읽은 범위가 주장 범위와 같은지 대조한다. title·description·표의 부품 이름마다 그 부품 자료가 계산에 들어갔는지 본다.

## 2. 출처·인용

### AP-C-06 출처가 정한 양·규칙·절차에서 말없이 벗어남
- **문제.** 출처를 인용해 놓고 기준량을 비슷한 다른 양으로 바꾸거나, 공식만 가져오고 절차와 범위 규칙은 버린다. 출처가 붙어 있어 맞아 보이지만 출처와 어긋난다.
- **예.** `part1-10-can-electrical.md` L99-108 (PROP_SEG 대신 sample point) · 같은 글 L100 (지배 엣지 LOOP1 대신 큰 LOOP2) · 같은 글 L114 vs L204·L199 vs L221-227 (PROP_SEG 1..8 TQ, PS2 = max(PS1, IPT) 위반)
- **규칙.** 판정 기준은 출처가 지목한 양 그대로 쓴다. 단순화하거나 여유값을 쓰면 그렇다고 밝히고 오차 방향과 원래 기준의 결과를 함께 적는다. 인용한 절의 수치 제약은 글의 모든 예제와 대조하고, 벗어난 예제는 사용하는 자리에서 밝히고 근거를 단다. 출처가 공식과 절차를 함께 주면 절차를 따르거나 이탈 이유를 적는다.
- **확인.** 인용한 절을 다시 열어 정의·범위·권장 절차를 뽑고, 본문 계산과 예제가 그 안에 있는지 확인한다.

### AP-C-07 출처의 조건·한정어·범위를 잘라냄
- **문제.** 데이터시트 조건, 표의 일부 행, 조건 목록 일부, 부등호의 엄격함, max·min 한정어, 함수의 부수 효과를 잘라 옮겨 원문과 다른 뜻이 된다. 따옴표 안 인용을 글의 예시에 맞게 줄이기도 한다. 정리에서 조건부 메커니즘을 무조건 문장으로 줄이기도 한다. 묶음 2에서는 9편 모두에서 나왔다.
- **예.** `part1-10-can-electrical.md` L43-44·L148·L248 (±20 V 행만 옮기고 요약에서 VCM 조건 삭제) · `part12-01-edge-inference.md` L177 (TensorRT sparsity 조건 중 2:4 zero와 `kSPARSE_WEIGHTS`만 옮기고 정밀도·레이어 종류·GPU 세대 조건은 뺌) (파일럿 2, 2026-10-11) · `part1-05-spi-hardware.md` L51 (Linux 문서의 'in/out on rising edges'를 따옴표 안에서 '받기'로 줄여 하강 엣지 출력인 W25Q32JV를 예로 맞춤, 출처를 연 독자는 다른 문장을 봄) (묶음 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L69·L174 (TRM 3.9.1의 '최대 12 cycle'에서 6을 빼 '18 cycle이 줄어든다'는 고정 절감으로 씀, 고친 문장이 원래 오류 유형을 되풀이) (묶음 2, 2026-10-11) · `part2-07-arm-mpu.md` L74 ('Table 4-45 중 TEX = 000·001 행'이라 했지만 TEX=001 C=1 B=0 행이 빠져 없는 인코딩처럼 읽힘) (묶음 2, 2026-10-11)
- **규칙.** 표는 조건 헤더를 그대로 옮기고, 글이 다루는 경우에 걸리는 행·조건 값은 모두 포함하거나 그 경우가 밖에 있다고 쓴다. 빠진 행이 있으면 '중 일부'라고 하고 무엇을 뺐는지 적는다. 소스 표의 행을 고르는 레지스터 조건(M=10이면 PCE, HSIDIV=00)은 그 값을 쓰는 문장에 함께 옮기고, 모든 파생 수치가 기대는 클록 가정은 '이 글의 기준' 목록에 설정 필드와 함께 둔다. 따옴표 안 문장은 출처의 뜻을 모두 담아야 하고, 글의 예가 출처와 다르면 출처를 다 인용한 뒤 차이를 한 문장으로 적는다. 부등호는 출처의 엄격함을 유지하거나 같을 때 무슨 일이 생기는지 쓴다. 출처의 max·min·typ 값을 산술로 합치면 가장 강한 한정어를 결과와 그 결과가 반복되는 모든 곳(수정 이력 포함)에 붙인다. 인용 함수의 동작을 요약할 때는 독자에게 보이는 부수 효과(`ARM_MPU_Enable`의 `__DMB`, SHCSR MemManage 활성화)를 모두 적거나 '등'을 쓰고 줄 범위를 링크한다. 조건을 나열하는 절(승격 조건 네 개, 커널 함수의 모든 return 분기)을 인용하면 주장에 걸리는 조건을 모두 옮기거나 주장을 코드가 바꾸는 한 조건으로 좁힌다. 인용 문장은 그 쪽의 절 제목과 예외 문장까지 읽고 한정어(preview, deprecated, 버전, 'parallel clock SerDes 한정')를 남긴다. 정리 불릿은 1차 자료로 따로 다시 확인하고, 분기 조건을 남기거나 그 항목을 뺀다. 목록 항목을 인용하기 전에 그 문자열이 어느 대상의 제목인지 확인한다.
- **확인.** 인용 표·목록을 출처와 행 단위로 diff한다. 따옴표 안 문장을 출처 원문과 대조한다. 요약·정리 문장의 값과 메커니즘에 본문의 조건과 한정어가 남아 있는지 본다.

### AP-C-08 판·버전이 고정되지 않은 출처

### AP-C-27 출처끼리, 또는 출처와 자기 계산이 어긋나는데 맞추지 않음
- **문제.** 예산은 출처 X에서, 판정 기준은 출처 Y에서 가져오면서 두 출처가 같은 항을 다르게 센다는 것을 말하지 않는다. 앱 노트와 데이터시트가 같은 파라미터에 다른 값을 주는데 한쪽만 쓰거나, 다른 지점에서 정의된 두 양을 바로 비교한다. 자기 계산이 인용 출처의 대표 수치를 뒤집는데 그 수치를 언급하지 않거나, 글의 모델과 맞지 않는 upstream 예시를 인용한다. 출처를 연 독자는 설명 없는 모순을 본다.
- **예.** `part1-10-can-electrical.md` L108 vs L128 (SLLA270 예산은 컨트롤러 지연을 한 번, Hartwich 조건은 노드마다 세어 길이가 5-7.5 m 낙관적일 수 있음) (파일럿 2, 2026-10-11) · 같은 글 L86-96·L225·L287 (SLLA270은 ISO 11898이 40 m에서 1 Mbps를 규정한다고 하는데, 글은 그 문장을 인용하지 않고 40 m 불가로 결론) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L99 vs L83 (IO-APIC 문서 예시는 IRQ 하나를 CPU 4개에 분산, 본문은 x86이 CPU 하나를 고른다고 함) (파일럿 2, 2026-10-11) · `part1-07-adc-principles.md` L137 (AN2834의 VREF+ 2.4 V min을 씀, 글이 다른 모든 수치에 인용하는 DS8626 Table 67은 1.8 V min) (묶음 2, 2026-10-11) · `part1-12-lvds-differential.md` L61·L139 (드라이버 쪽으로 되돌아가는 반사파를 수신기 147 mV 예산에서 그대로 빼서 비교, 글의 모델에서는 그런 손실이 생기지 않음) (묶음 2, 2026-10-11)
- **규칙.** X의 예산과 Y의 기준을 합치면 각 항이 Y의 정의에 어떻게 대응하는지 한 문장으로 적고, 다르면 결과가 얼마나 바뀌는지 준다. 인용한 1차 자료 둘이 같은 파라미터에 다른 규칙을 주면 둘 다 보이고 각 행을 양쪽 규칙에 대해 표시한다. 앱 노트와 디바이스 데이터시트가 다르면 데이터시트 값을 먼저 인용하고 앱 노트 값과 어느 쪽이 지배하는지 적는다. 메커니즘 X의 양을 예산 Y와 비교하기 전에 X가 Y의 측정 지점에 어떻게 도달하는지(시점, 크기) 한 문장으로 쓰고, 아니면 같은 지점에서 정의된 양끼리만 비교한다. 판정 기준 부품과 예시 조건(데이터율, 링크)이 다르면 두 조건을 같은 문단에 밝히고 기준 부품의 정격에서 다시 계산한 값을 함께 준다(150 Mbps면 PRBS31 주기 ≈ 14.3 s). 인용 문장의 한정어는 그 문장이 이름 댄 출처에 있어야 한다. 자기 계산이 인용 출처의 수치를 뒤집으면 그 수치를 판정 옆에 인용하고 달라진 입력을 적는다. upstream 예시는 출력이 글의 메커니즘과 맞을 때만 쓴다.
- **확인.** 출처가 둘 이상 들어간 계산마다 항별 출처를 적어 대조한다. 판정 수치를 인용 출처의 대표 수치(제목·요약·표 값)와 비교한다. 같은 파라미터를 다른 출처가 주는지 데이터시트에서 찾아본다.

### AP-C-31 특정 코어에 대한 새 권고를 errata 확인 없이 더함
- **문제.** TRM·UG 표만 보고 특정 코어의 메모리 속성·모드를 대안으로 권한다. 문서에 있는 인코딩이라도 출시된 실리콘 리비전에서 errata로 안전하지 않을 수 있다.
- **예.** `part2-06-arm-cache.md` L167 (write-through를 '중간 선택지'로 새로 권함, Cortex-M7 errata notice는 확인하지 않음) (묶음 2, 2026-10-11)
- **규칙.** 이름 댄 코어의 메모리 속성·캐시 정책·동작 모드를 권하는 문장을 더하면 그 코어의 errata notice를 확인하고 영향을 받는 리비전 범위를 적는다. 확인하지 못했으면 권고를 넣지 않는다.
- **확인.** 수정 diff에서 새 권고 문장('-를 쓰면 된다', '대안', '선택지')마다 수정 보고에 errata 문서와 판이 있는지 본다.

### AP-C-11 권고·추론을 단정 사실로 승격

- **확인.** 정리·한 줄 요약·description의 문장마다 본문 출처 문장으로 거슬러 올라가 양상이 같은지, 파생 수치가 출처에 없는 가정에 기대지 않는지 대조한다. '-므로/-때문에' 문장마다 인용 절에 인과 표현이 있는지 본다.

### AP-C-12 출처 없는 한정·빈도·불가능 부사

- **예.** `part12-01-edge-inference.md` L99-104·L568 ('흔히 새는 것') · `part7-13-irq-affinity.md` L195·L360 (`irq_startup` → `irq_setup_affinity` 하나만 따라가 기본 마스크를 거기서만 읽는다고 씀, `desc_smp_init`도 `irq_default_affinity`를 읽음) (파일럿 2, 2026-10-11) · `part2-07-arm-mpu.md` L211 ('모두'로 단정, 인용한 DUI 0553A 4.5.2에 SCS와 벡터 표는 항상 허용된다는 예외가 있음) (묶음 2, 2026-10-11) · `part2-08-arm-mmu.md` L55 ('때만', 같은 memory.rst 절이 언급하는 `CONFIG_ARM64_FORCE_52BIT`를 빠뜨림) (묶음 2, 2026-10-11) · `part1-09-pwm-signal.md` L70·L85 ('만들 수 없습니다', 고해상도 타이머와 dithering이 반례) (묶음 2, 2026-10-11)
- **규칙.** 빈도 부사는 지우거나 사례·보고서를 인용한다. '만·뿐·항상·모든·없다'는 그 자체에 출처가 있어야 한다. 이런 문장이 절을 인용하면 그 절 전체에서 예외 문구('always permitted', 'except', 'regardless')와 분기를 다시 찾아, 다른 분기를 이름 대거나 주장을 좁힌다. 코드에 대해 '만·뿐·없다·한 번'을 쓰려면 고정한 태그 트리 전체에서 심볼의 참조를 모두 grep하고, 그 동작을 바꾸는 Kconfig 심볼과 `#ifdef`도 grep하고, 읽는 쪽을 모두 인용하고, 검색 범위를 본문에 적는다. '없다·불가'는 범위('일반 counter-compare PWM에서')를 붙이거나 전체 공간을 덮는 출처를 단다. 수학적 귀결은 엄격함을 증명하지 않았으면 비엄격 부등호('낮아지지 않는다')로 쓴다.

### AP-C-15 글이 약속한 것을 본문·코드가 하지 않음

- **규칙.** 'X를 보인다'는 문장과 '어떤 상황에서 쓰나' 불릿마다 X를 완전히 답하는 절(코드 포함)을 가리킬 수 있어야 하고, 없으면 불릿을 좁히거나 지운다. 본문·표·코드 주석에 이름이 나오는 절차 단계는 코드에 있거나 '독자 확장'으로 표시한다. 산문이 코드 예에 대해 계산하는 클록·타이밍 수치는 그 코드가 설정하는 값(프리스케일러, PCLK)이거나 명시한 전제여야 하고, 코드가 만드는 값을 데이터시트 한계(f_ADC max)와 대조한다.

### AP-C-16 수정한 뒤 요약·설명·같은 주장의 다른 문장을 맞추지 않음
- **문제.** 표나 본문 한 곳만 고치고, 같은 숫자나 주장을 반복하는 산문·함정·정리·한 줄 요약·description은 옛 내용 그대로 둔다. 숫자뿐 아니라 주장의 출처·라벨·범위를 바꿨을 때도 같은 일이 생긴다. 글이 스스로 모순되고, rubric 3-1은 내부 모순을 오류 확인으로 보아 점수와 관계없이 우선 조치로 보낸다. 그림은 AP-C-29, 다른 글의 링크 라벨은 AP-C-30을 본다.

- **규칙.** 결론·수치·구조·출처 귀속·라벨·범위를 바꿨으면 같은 라운드에서 옛 숫자와 옛 표현을 글 전체에서 grep하고, 한 줄 요약·함정·정리·수정 이력·description·title을 다시 읽어 맞춘 뒤에 보고한다.
- **확인.** 수정 diff에서 바뀐 숫자·용어·출처 이름 목록을 만들어 수정 후 본문 전체를 grep한다.

### AP-C-17 편집이 문단 맥락과 참조를 흐림
- **문제.** 본문의 절 번호와 인용 문서의 절 번호가 한 문단에 섞이거나, 인용을 고치면서 문장을 상관없는 문단에 끼워 넣는다.

### AP-C-29 산문만 고치고 글에 넣은 그림은 그대로 둠
- **문제.** 산문을 1차 자료에 맞게 고치면서 그 글이 넣은 그림(`.tex` → SVG)은 옛 메커니즘이나 출처 없는 라벨을 그대로 둔다. `.md`만 고치는 범위라며 blocker로 미루거나, alt text를 좁히거나, 그림의 모순을 설명하는 본문 문단을 더해 덮는다. 독자는 그림을 믿고, 게이트는 SVG 안 텍스트를 보지 못한다.
- **예.** `part1-04-uart-hardware.md` L36 · `part1-04-uart-oversampling.tex` L37-38 (RM에 맞게 시작 비트 규칙을 고쳤는데 그림은 옛 8/9/10 단일 검사를 가르침, `.md`만 고칠 범위라 blocker로 남김) (묶음 2, 2026-10-11) · 같은 글 L44 vs `part1-04-uart-oversampling.tex` L29-52 (그림을 고치는 대신 alt text를 '두 번째 검사를 보인다'로 좁힘, 그림은 3/5/7 검사가 없고 '다수결'이라 부르며 글과 관계없는 9600 baud 비트 시간을 표시) (묶음 2, 2026-10-11) · `part1-05-spi-topologies.tex` L33·L40 (산문에서는 빈도 부사를 지웠는데 그림에 '(드물게 사용)'과 잘못 배선한 daisy chain이 남음) (묶음 2, 2026-10-11) · `part1-09-pwm-signal.md` L37-42 vs `part1-09-pwm-alignment.tex` (그림과 충돌하는 극성을 산문에서 빼자 그림이 서로 맞지 않는 극성 주장 둘을 그대로 가짐) (묶음 2, 2026-10-11) · 같은 글 L41-43 vs `part1-09-pwm-alignment.tex` L59-66 (PWM mode 1·2를 섞은 그림을 고치지 않고 그 불일치를 설명하는 문단을 본문에 더함) (묶음 2, 2026-10-11)
- **규칙.** 글이 넣은 그림의 `.tex` 텍스트·라벨과 alt text는 글의 일부다. 수정이 그림이 그리는 메커니즘을 바꾸거나 그림에 1차 자료와 다른 주장이 있으면, 같은 라운드에 `.tex`를 고치고 `npm run diagrams`로 다시 빌드한다. 작업 범위가 `.md`로 묶여 있으면 그림을 빼거나 빠진 내용을 캡션 한 줄로 밝혀, 글이 자기 그림과 모순되지 않게 한다. alt text를 좁혀 차이를 덮거나, 그림의 오류를 설명하는 본문 문단을 더하지 않는다.
- **확인.** 글이 참조하는 SVG마다 `.tex` 소스의 텍스트(라벨, 주석, 수치)를 수정 diff의 메커니즘·수치와 대조한다. `npm run check:diagrams`로 stamp가 맞는지 본다. 수정 보고 blocker에 `.tex`가 남아 있으면 라운드를 닫지 않는다.

### AP-C-30 제목·범위를 바꾼 뒤 제목과 들어오는 링크 라벨을 맞추지 않음
- **문제.** 제목을 고치면서 본문이 실제로 다루는 범위(코어, 부품)로 좁히지 않거나, 범위를 좁힌 뒤 다른 글에서 들어오는 링크 라벨과 관련 항목 라벨은 옛 제목 그대로 둔다. 지적받은 라벨 하나만 고치고 같은 slug의 다른 라벨은 남기기도 한다. rubric E는 제목·본문 범위 불일치를, F는 라벨 불일치를 잘못된 링크로 보아 크게 깎는다(F ≤ 5).
- **예.** `part2-06-arm-cache.md` L2 vs L5 ('Inclusive'만 빼고 일반 'ARM'을 남김, 모든 절차가 Cortex-M7 전용) (묶음 2, 2026-10-11) · `part1-12-lvds-differential.md` (범위를 SN65LVDS31/32 마진 분석으로 좁혔는데 `part1-01` L128, `part1-11` L166·L172, `part2-01` L153의 라벨은 여전히 '차동 신호 일반', blocker로만 남김) (묶음 2, 2026-10-11) · `part2-07-arm-mpu.md` L217 (2-06 제목을 바꾼 뒤 2-05의 라벨은 찾았지만 2-07의 'ARM 캐시 (L1/L2)'는 놓침) (묶음 2, 2026-10-11) · `part2-08-arm-mmu.md` L229 (같은 묶음에서 'Cortex-M7 캐시와 DMA'로 바뀐 형제 글을 옛 일반 제목으로 가리킴) (묶음 2, 2026-10-11)
- **규칙.** 제목을 고치면 모든 코드 블록과 절차가 대상으로 하는 아키텍처나 코어를 이름 댄다. 제목을 넓게 두려면 절차가 그 제목이 이름 댄 모든 계열을 다뤄야 한다. 제목·범위·판정 기준을 바꾸면 같은 라운드에 사이트 전체(`src/content`)에서 그 글의 slug를 grep해 들어오는 링크 라벨을 모두 새 제목에 맞춘다. 같은 묶음에서 제목이 바뀐 글을 가리키는 `- [N-NN: …]` 라벨도 모두 맞추고, 대상이 더는 글의 질문과 관계없으면 관련 링크에서 뺀다. 범위 밖이라 고치지 못하면 파일과 줄을 다음 루프 대상 목록에 올린다. 보고서 메모로 닫지 않는다.
- **확인.** 제목이 바뀐 글마다 `grep -rn <slug> src/content`의 라벨을 대상 글의 현재 title과 대조한다. title의 아키텍처·부품 이름을 본문 코드 블록의 대상과 비교한다.

## 6. 중복·범위

### AP-C-18 형제 글의 모순을 그대로 둠
- **문제.** 한 글에서 사실을 고쳤는데 같은 주장이 형제 글, 선수 글, 다른 시리즈에 남는다. 두 글을 '충돌'로만 적고 어느 쪽이 맞는지 판정하지 않거나, 형제 글을 '다음 패스'나 수정 보고의 blocker 메모로 미루면 틀린 쪽이 계속 발행되고 게이트도 막지 못한다. 묶음 2에서는 9편 중 7편이 blocker 메모만 남기고 `known-falsehoods.yaml`에 아무것도 등록하지 않았다. 반대로 대상 부품군이 다른 형제 글을 오류로 몰아 맞는 문장을 차단 목록에 올릴 뻔하기도 했다.
- **예.** `part1-10-can-electrical.md` L107 vs `part5-10-can-communication.md` L61·L287·L297 (part1-10은 Linux CiA 표의 '800 kbit/s 초과 75%'로 고쳤는데, 형제 글은 '87.5% 권장'을 '별도 패스'로 미뤄 발행 상태로 남음) (파일럿 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L71 vs `rtos/practical-internals/part1-05-interrupts-rtos.md` L138 (TRM 3.9.1로 판정이 끝난 '6-12 cycle을 절약'을 blocker로만 보고, 등록 없음) (묶음 2, 2026-10-11) · `part2-06-arm-cache.md` vs `part2-05-arm-memory-map.md` L112·`part2-10-memory-barrier.md` L196-201·`performance-engineering/part2-05-cache-basics.md` L246-254 (2-05만 찾고 2-10과 다른 시리즈는 놓침, 2-10의 RX 시퀀스는 DMA 전 clean이 없어 dirty line 축출이 DMA 데이터를 덮음) (묶음 2, 2026-10-11) · `part2-07-arm-mpu.md` L137 vs `rtos/practical-internals/part4-06-stack-overflow.md` L150 (문자열 grep이 다른 시리즈의 '1 byte라도 넘기는 순간' guard 주장을 놓침) (묶음 2, 2026-10-11) · `part1-04-uart-hardware.md` 수정 보고 blocker 2 vs `part10-05-uart-not-printing.md` L98-99 (H7에서 틀린 BRR 식을 이유로 84 MHz F4 설정인 10-05의 맞는 USARTDIV 식을 오류라 함, 등록했다면 맞는 문장이 차단됨) (묶음 2, 2026-10-11)
- **규칙.** 사실을 고친 뒤 같은 주장을 사이트 전체에서 grep한다. 문자열만이 아니라 메커니즘 키워드(guard, MemManage, tlbi, ASID, 클린·무효화 순서)와 절차·코드까지, 같은 시리즈만이 아니라 모든 시리즈에서 찾는다. 바꾼 헤드라인 수치를 인용하는 다른 글의 라벨('1-04의 오차 3%')도 찾는다. 모순이라고 부르기 전에 형제 글이 대상으로 하는 부품군과 관례를 확인한다. 부품군이 다르면 '대상 미기재', 관례 차이(/4095 정규화)면 주석으로 처리하고, 그런 문자열은 `known-falsehoods.yaml`에 넣지 않는다. 확인된 오류이면 1차 자료로 판정하고, 라운드 완료를 보고하기 전에 다음 중 하나가 diff에 있어야 한다. (a) 형제 글 수정, (b) 오류 문자열과 1차 자료 정정을 `data/known-falsehoods.yaml`에 등록하고 `npm run audit:falsehoods` 실행, 그리고 형제 글을 파일·줄과 함께 다음 루프 대상에 올림. 수정 보고의 blocker 메모나 '다음 라운드 대기', `시리즈 공통 문제` 기록만으로는 닫히지 않는다. 형제 코드가 내지 않는 값을 독자에게 형제 코드로 재현하라고 하지 않는다.
- **확인.** 수정 보고에 grep 범위(문자열, 메커니즘 키워드, 시리즈)와 결과가 있는지 본다. 보고의 blocker 목록에 형제 글이 있으면 라운드 diff에 형제 글 변경이나 `known-falsehoods.yaml` 변경이 있는지 보고, 없으면 라운드를 미완료로 돌린다. 등록한 문자열마다 형제 글의 대상 부품군이 정정의 범위와 같은지 본다.

### AP-C-19 지적된 한 건만 고침
- **문제.** 평가자가 이름을 댄 사례 하나만 고치고, 같은 유형의 다른 사례(넓은 표, 완곡 표현, 형제 글과 겹치는 함정 항목)는 남긴다. 한 행의 수치를 다시 출처 잡으면서 같은 행의 분류 라벨은 두기도 한다. 다음 라운드에서 같은 지적이 다시 나온다.
- **예.** `part12-01-edge-inference.md` L43·L151·L545 (넓은 표 하나만 분할) · `part1-10-can-electrical.md` L238-240 vs `part5-10-can-communication.md` L270 (중복 함정 하나만 제거) · `part12-01-edge-inference.md` L131·L173 (Alif 페이지로 수치는 모두 다시 잡았지만, 같은 페이지가 반박하는 'MCU' 분류는 그대로. E7은 MMU가 있는 Cortex-A32 두 개를 가짐) (파일럿 2, 2026-10-11)
- **규칙.** 지적을 유형으로 읽는다. 같은 유형을 글 전체에서 찾아 같은 라운드에 모두 고치고, 형제 글과 중복을 정리할 때는 함정·주의 항목을 전부 대조해 겹치는 것을 링크로 바꾼다. 표의 행을 다시 출처 잡을 때는 수치만이 아니라 범주 라벨까지 같은 1차 자료로 확인한다.
- **확인.** 지적 유형별로 수정 전후 개수를 센다(예: 열이 5개 이상인 표의 수). 다시 출처 잡은 행마다 라벨 칸도 출처와 대조했는지 본다.

## 7. 분량·질

### AP-C-20 단일 출처를 바꿔 써서 절을 채움
- **문제.** 절 전체가 한 앱 노트나 매뉴얼을 단락별로 다시 쓴 것이다. 출처 이름으로 시작해 출처를 바꿔 쓰는 문단, 글의 질문에 쓰이지 않는 표 열·행, 출처는 맞지만 뒤에서 쓰지 않는 사실이 쌓인다. 정확도는 오르지만 원래 가치(A)는 그대로이고, 글이 출처 요약처럼 읽힌다. 내용을 잘라낸 뒤 연결이 끊긴 템플릿 절도 남는다. 묶음 2에서는 9편 모두에서 나왔다.
- **예.** `part1-10-can-electrical.md` L55-59·L77-82·L141·L143-161 (라운드마다 줄였지만 앱 노트·데이터시트 재진술 절이 남음) (파일럿 2, 2026-10-11) · `part1-05-spi-hardware.md` L30·L34-38·L57·L59·L136·L140 (출처 없는 주장을 출처 이름으로 시작하는 바꿔 쓰기로 대체, 정확도만 오름) (묶음 2, 2026-10-11) · `part1-04-uart-hardware.md` L77-84 (BRR·DQUANT 표에 글이 묻지 않는 '1 KiB 전송' 열과 공식 재진술) (묶음 2, 2026-10-11) · `part2-06-arm-cache.md` L25-34·L95 (출처는 맞지만 M7 DMA 질문에 쓰이지 않는 Cortex-A53 행과 Linux arm64 메모가 제목 범위 불일치를 키움) (묶음 2, 2026-10-11) · `part2-08-arm-mmu.md` L147-169 (MMU 질문 밖의 DMA·kmalloc 함정에 출처를 더해 키움, part8-04·part7-09와 겹침) (묶음 2, 2026-10-11)
- **규칙.** 한 출처로 만든 절에는 글의 예(부품, 예산)에 연결된, 출처에 없는 계산이나 판단을 하나 이상 넣는다(예: 고른 SCK에서 MISO 타이밍 예산). 넣지 않을 거라면 링크 한 줄로 줄인다. 단일 출처 표는 글의 유도에 쓰는 행만 남기고 원표 포인터 한 줄을 둔다. 표의 열·행과 출처를 단 문단은 뒤 문장이 쓰는 결정에 연결될 때만 둔다. 출처가 맞아도 쓰이지 않으면 지운다. 절에 출처를 더하기 전에 그 절이 제목 질문에 답하는지 보고, 아니고 형제 글이 다루면 한 줄 링크로 바꾼다. 문단은 독자가 실행할 결론으로 시작하고 출처는 괄호에 둔다. 함정은 본문에 없는 증상이나 결정이 글의 질문과 이어질 때만 둔다. 라운드를 닫기 전에 H2·H3마다 '이 글이 답하는 질문' 불릿 하나에 대응시키고, 대응이 없는 절(내용을 잘라낸 뒤 남은 용례 목록, 슬로건 포함)은 지운다.
- **확인.** 절마다 인용 출처가 하나뿐인지, 출처에 없는 계산·결정이 있는지 본다. H2·H3 목록과 질문 목록의 대응을 적어 본다. 표의 열마다 그 값을 쓰는 뒤 문장을 찾는다. 출처 이름으로 시작하는 문단 수를 센다.

### AP-C-21 점수를 올리려고 분량을 늘림
- **문제.** 루브릭 점수를 올리려고 문단·표·예시를 덧붙이거나, 두 질문을 한 글에 몰아 글을 키운다. 질이 아니라 길이가 늘어난다.
- **예.** 파일럿 루프 1·2와 묶음 2에서 이 항목 그대로의 사례는 없다. 운영자 결정으로 미리 둔 규칙이다. 지적에 답하며 늘어난 경우는 AP-C-25, 반복으로 늘어난 경우는 AP-C-26, 출처를 더해 범위 밖 절이 커진 경우는 AP-C-20을 본다.
- **규칙.** **운영자 결정 2026-10-11 (b):** 길이보다 질이다. 고정된 길이 상한은 없고, 점수를 올리려고 내용을 덧붙이지 않는다. 한 글이 두 질문을 다뤄야 하면 늘리지 말고 분할을 제안한다. 분할 여부는 운영자가 정한다.
- **확인.** 수정 diff에서 줄이 크게 늘었으면 새 문단마다 독자 질문에 답하는지 본다. 한 줄 요약이 질문 두 개를 담으면 분할 제안으로 돌린다.

### AP-C-25 출처·검증 과정을 독자용 산문으로 풀어 씀
- **문제.** 평가자의 출처 지적에 답하려고 어느 규칙·문서·판이 무엇을 말하는지 해설하는 문단을 본문에 더하거나, 커널 함수 호출 사슬을 한 단계씩 서술하거나, 편집 과정을 수정 이력에 적는다. 수정 이력을 배포본이 아니라 앞 라운드의 미커밋 초안과 비교해 쓰기도 한다. G는 조금 오르지만 군더더기가 늘어 A·B·F가 내려가고 결론이 묻힌다.
- **예.** `part1-10-can-electrical.md` L199·L231·L326 (출처 해설 문단, L231은 AP-C-16 모순을 만듦) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L125·L145·L180·L244·L327·L338 (중간 커널 함수를 모두 나열한 호출 사슬) (파일럿 2, 2026-10-11) · `part12-01-edge-inference.md` L711-712 ('개발 머신 출력 삭제', 'TRM을 다시 열 수 없음' 같은 작업 메모가 수정 이력에 있음) (파일럿 2, 2026-10-11) · `part1-12-lvds-differential.md` L143 (수정 이력이 발행된 적 없는 값을 고쳤다고 적고, 배포본에서 실제로 바뀐 것은 빠짐) (묶음 2, 2026-10-11) · `part1-04-uart-hardware.md` L89 ('rev Y Table 37과 rev V Table 134가 같다', 독자에게 필요 없는 대조 과정) (묶음 2, 2026-10-11)
- **규칙.** 출처는 인용 괄호, 표의 열, 참고 자료에 둔다. 표 하나(필요하면 실리콘 리비전과 함께)를 인용하고, 두 표·두 판을 대조한 과정은 커밋 본문에 쓴다. 출처 해설 문단은 독자의 결정이 그 출처 차이에 달려 있을 때만 쓴다. 본문에는 관찰 가능한 결론과 그것을 정하는 함수·파일 하나의 링크를 두고, 전체 호출 사슬은 커밋 본문이나 팩트체크 보고에 둔다. 수정 이력에는 주장을 바꾼 내용 수정만 적고, 배포본(`git show HEAD:<file>`)과 비교해 쓴다. 'old → new' 값마다 HEAD 판에서 grep해 옛 값이 실제로 발행됐는지 확인한다. 과정 메모는 커밋 본문에 쓴다.
- **확인.** 수정 diff의 새 문단이 출처 이름이나 함수 이름으로 시작하는지, 한 문장에 함수 이름이 셋 이상 나오는지 본다. 수정 이력에 '삭제·다시 열 수 없음·검증·대조' 같은 과정 단어가 있는지 grep하고, 이력의 옛 값을 `git show HEAD:<file>`에서 찾는다.

### AP-C-26 같은 결론·수치를 본문·함정·정리에 되풀이함
- **문제.** 라운드마다 바뀐 본문 수치와 판정을 함정·정리에도 덧붙이고, 지적받은 자리에 판정을 다시 쓰면서 앞의 사본은 지우지 않는다. 함정이 본문 절을 거울처럼 따라가고 정리가 절 목록이 된다. 사본을 다른 조건으로 바꿔 쓰다 거짓이 되기도 한다. 길이만 늘고, 사본마다 맞춰야 할 자리가 생기며(AP-C-16), 글마다 같은 골격이 반복돼 rubric 3절의 scaled content 신호와 A·B·D 감점이 된다.
- **예.** `part1-10-can-electrical.md` L116·L192-196·L228·L254 (같은 판정이 네 절에) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L298-323 vs L59·L65·L79·L133·L156·L178 (함정이 본문 절을 되풀이) (파일럿 2, 2026-10-11) · `part1-09-pwm-signal.md` L44 vs L78 (본문의 '같은 단계 수 N에서 정확히 절반'을 함정에서 'counter 범위를 그대로 두고'로 바꿔 써 거짓이 됨) (묶음 2, 2026-10-11) · `part2-04-cortex-m-exceptions.md` L15·L62·L68-71·L136-137·L145-149·L181 (같은 사이클 수가 모든 절에, 측정·비교 없는 '측정 / 비교' 절을 데이터시트 표로 채움) (묶음 2, 2026-10-11) · `part1-07-adc-principles.md` L50·L135·L137·L155 (ENOB의 SINAD·잡음 기준 단서가 네 곳에) (묶음 2, 2026-10-11)
- **규칙.** 결론 하나는 한 절에만 둔다. 다른 자리에서는 그 절을 이름으로 가리키거나 그 자리의 국소 수치만 쓰고 다시 판정하지 않는다. 다시 말해야 하면 조건을 그대로 옮기고, 바꿔 쓴 문장은 새 주장으로 보고 글의 정의에서 다시 계산한다. 측정이나 비교가 없는 '측정 / 비교' 절은 표 재진술로 채우지 말고 지운다. 함정은 본문이 다루지 않은 증상이나 메커니즘이 있을 때만 두고, 아니면 한 줄 증상과 본문 절 포인터로 줄인다. 정리는 독자가 가져갈 결정 3-4개로 쓰고, 불릿마다 핵심 수치는 하나까지, 새 조건은 넣지 않는다.
- **확인.** 정리 불릿 수와 불릿별 숫자 수를 센다. 함정 항목마다 본문에 같은 메커니즘이 있는지 찾고, 있으면 조건이 본문과 같은지 대조한다. 판정 문장(만족·불가·통과)과 핵심 수치를 grep해서 같은 것이 몇 곳에 있는지 센다.

### AP-C-28 기준을 고르지 않고 변형을 모두 나열함
- **문제.** 해석이 갈리는 선택마다 모든 조합을 남겨 고르는 일을 독자에게 넘긴다. 독자는 같은 양의 수치를 열 개쯤 받고, 판정을 말하려면 분기 나무가 필요하다. 글이 스스로 틀린 파라미터라고 한 변형이 기준이 되기도 한다.
- **예.** `part1-10-can-electrical.md` L91-99·L116·L178·L190-196·L228 (LOOP1/LOOP2 × 컨트롤러 지연 한 번/두 번 × typ/max × PHASE_SEG2 ≥ 1/≥ 2를 모두 유지해 왕복 지연 수치가 약 10개) (파일럿 2, 2026-10-11)
- **규칙.** 인용한 1차 자료가 뒷받침하는 변형을 기준으로 쓴다(여기서는 엣지에 맞는 LOOP1과 Hartwich의 두 노드 공식). 나머지 변형은 길이가 얼마나 바뀌는지 민감도 문장 하나로 준다. 글이 틀렸다고 한 파라미터를 기준으로 삼지 않는다.
- **확인.** 같은 양(왕복 지연, 최대 길이)에 서로 다른 값이 몇 개 나오는지 센다. 셋 이상이면 기준 하나와 민감도 문장 하나로 줄일 수 있는지 본다.

### AP-C-22 요약형 fetch나 텍스트 추출로 표·그림 수치를 확인함

### AP-C-23 재현할 수 없거나 실제보다 강한 검증 기록
- **문제.** 존재하지 않는 clone 경로, 브라우저에서만 읽은 JS 렌더 문서, `cc -c`뿐인 '컴파일됨', 커밋하지 않은 수정, 절 시작 쪽을 가리키는 쪽 인용, 수정 전 줄 번호처럼 검증 기록을 다시 따라갈 수 없거나 실제보다 강하게 적는다. 다시 쓴 물리 주장을 출처 목록의 '순수 산술' 항목 아래 묶어 검증자가 건너뛰게 하기도 한다. 묶음 2에서는 9편 중 5편이 미커밋 상태로 평가를 받았다.
- **예.** `part1-10-can-electrical.md` 수정 보고 ('로컬 clone에서 git show', 경로 없음) · `part12-01-edge-inference.md` 수정 보고 (pthread 파이프라인 'compiles'는 `-c`만) · `part2-08-arm-mmu.md` L18 (본문에 v6.12와 2026-10-11에 대조했다고 쓰는데, 수정과 출처는 다른 글 8편과 섞인 미커밋 작업 트리에만 있음) (묶음 2, 2026-10-11) · `part1-09-pwm-signal.md` L33·L52 (유도성 부하·dead-time 기준을 새로 썼는데 출처 목록 1번 '순수 산술' 아래 묶음) (묶음 2, 2026-10-11) · 같은 글 L17 ('§7.2(216쪽)'은 절 시작 쪽, 인용한 사실은 218쪽) (묶음 2, 2026-10-11)
- **규칙.** 검증은 고정 태그·sha URL이나 실제로 쓴 로컬 경로로 커밋 본문에 남긴다(`06-remediation-evidence`). 검증한 글은 글마다 따로, 출처를 커밋 본문에 적어 평가·이중 확인 요청 전에 커밋한다. 관계없는 글을 한 미커밋 작업 트리에 묶지 않는다. 본문의 '대조했다'·`lastVerified`는 그 커밋이 있을 때만 쓴다. 출처 목록에는 다시 쓴 산술 아닌 문장마다 1차 자료 항목을 두고, 없으면 보고에 unsupported로 적는다. 쪽 인용은 인용 문장이 실제로 있는 쪽(또는 쪽 범위)을 인용한 판의 PDF로 확인한다. JS 렌더 문서는 인용 문구나 스크린샷 경로를 저장하고, 재현할 수 없으면 TBD로 둔다. 컴파일 검증은 모드(`-c` / 링크 후 실행)를 적는다. 수정 보고의 줄 번호는 수정 후 파일에서 다시 뽑거나, 바꾼 문장을 인용한다.
- **확인.** 기록된 경로·URL을 다시 열어 본다. `git status`로 미커밋 수정이 없는지, 커밋 하나가 글 하나만 바꾸는지 본다. 출처 목록의 항목 수를 diff에서 새로 쓴 주장 문장 수와 비교한다. 쪽 인용 몇 개를 PDF에서 열어 문장이 그 쪽에 있는지 본다.

### AP-C-24 평가자가 rubric 상한을 넘겨 점수를 줌
- **문제.** 평가자가 rubric 3-1의 명시 상한이나 대역 문구의 조건을 적용하지 않고 기준 글(anchor) 점수를 따라간다. 합계가 80 경계를 넘고 상위 anchor 후보로 잘못 제안된다. 묶음 2에서는 9편 중 8편에서 나왔고, 그중 7편이 관찰 결과 없는 글에 C = 10을 줬다.
- **예.** `part7-13-irq-affinity.md` `## 효과 확인 절차` L269-282 (결과 없는 절차인데 C = 10, 세 관찰이 같은 건) · 같은 글 평가 (C = 10·11, F = 9. - **규칙.** 대역 표와 anchor보다 먼저 rubric 3-1의 명시 상한을 적용한다(절차만 있으면 C ≤ 9, 출처·환경 없는 수치는 C ≤ 8). C ≥ 10은 관찰 결과나, 기대 관찰을 적은 재현 가능한 검증 절차를 가리킬 때만 준다. 출처에서 유도한 산술만 있으면 C ≤ 9다. C 근거에는 적용한 상한 조항을 인용한다. F ≥ 6은 관련 링크 대상을 모두 열어 라벨과 제목을 대조한 뒤에, F ≥ 9는 `audit:reading`이나 폰 폭 렌더 확인을 인용한 뒤에만 준다. E는 title 범위와 본문 범위(일반 제목 + 단일 MCU 본문)를 대조한 뒤에 6-8 대역을 쓴다. anchor가 상한을 넘을 수는 없다. 80점 이상 합계나 상위 anchor 제안은 평가자 자신의 불확실 목록이 비어 있고, 정리 수준 규칙까지 포함한 메커니즘 주장을 1차 자료로 다시 검증했고, 글이 커밋된 뒤에만 한다.
- **확인.** 평가 기록에서 C ≥ 10마다 관찰 결과나 재현 절차의 위치와 상한 인용이 있는지 본다. F ≥ 6이면 링크 대상 대조 기록이, F 9-10이면 모바일 확인 기록이 있는지 본다. 80점 이상이면 불확실 목록과 `git status`를 본다. 인용이나 기록이 없으면 평가를 다시 하게 한다.
