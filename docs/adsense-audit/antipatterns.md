# 콘텐츠 수정 안티패턴 카탈로그

AdSense 개선 루프에서 글을 고치다가 나온 안티패턴을 모은 목록이다. 수정자(fixer), 평가자(evaluator), 이중 확인자(double-checker)는 라운드를 시작할 때마다 이 파일을 읽는다.

- **추가 방식.** 루프마다 이중 확인 결과를 이 파일에 합친다. 새 항목은 다음 번호를 받고, 기존 항목에 해당하면 그 항목의 `예`에 사례를 덧붙인다. 어느 쪽이든 루프 번호와 날짜를 적는다. 항목당 `예`는 5개까지 두고, 넘치면 가장 배울 것이 많은 사례를 남긴다.
- **rubric과의 관계.** `docs/adsense-audit/rubric.md`는 글에 점수를 매긴다. 이 파일은 수정 과정에서 같은 실수가 되풀이되지 않게 막는다. 규칙이 rubric 상한·안전 규칙을 가리키면 rubric이 정본이다.
- **ID.** `AP-C-NN`(C = content). 방법론 배치의 `AP-D` ID와 겹치지 않는다. 항목은 주제별 절에 두므로 절 안의 ID가 번호순이 아닐 수 있다.
- **파일 경로.** `예`의 파일은 모두 `src/content/blog/embedded/modern-recipes/` 아래에 있다. 줄 번호는 관찰 당시 기준이다. 루프 표시가 없는 예는 파일럿 1이다.
- **출처.** 파일럿 루프 1(2026-10-11, 글 3편, 관찰 73건)과 파일럿 루프 2(2026-10-11, 같은 글 3편, 관찰 37건)에서 정리했다.

## 1. 사실·수치

### AP-C-01 파생 수치를 다시 유도하지 않음
- **문제.** 수정자가 새로 쓴 분수·개수·클럭 같은 파생 값을 표를 만든 스크립트나 같은 출처의 다른 값으로 다시 확인하지 않는다. 결론이 맞더라도 유도가 틀리면 다른 숫자까지 의심받는다.
- **예.** `part1-10-can-electrical.md` L160 (14/16 → 16 TQ, 7/8로 약분 안 함) · `part12-01-edge-inference.md` L290 (ring ≥ 6이 자기 열거와 모순) · 같은 글 L135-140 (역산한 NPU 180 MHz가 같은 페이지의 160 MHz와 충돌)
- **규칙.** 새로 쓴 파생 수치는 표를 만든 스크립트나 열거로 전제까지 다시 계산한다. 분수는 기약분수로 쓴다. 업체 수치에서 역산했으면 같은 출처가 직접 공개한 관련 값을 옆에 두고, 맞지 않으면 그렇다고 적는다.
- **확인.** diff에서 새로 생긴 숫자를 뽑아 스크립트 출력이나 출처 값과 하나씩 대조한다.

### AP-C-02 선언한 조건 밖의 값을 같은 결론에 섞음
- **문제.** 앞에서 임의로 고른 파라미터나 선언한 가정 밖의 값이 뒤의 '한계'에 몰래 들어간다. 그 조건에서도 결론이 거짓이 된다.
- **예.** `part1-10-can-electrical.md` L199 → L218-226·L267·L282 (76.2% 선택이 '한계 약 19 m'로 굳음) · 같은 글 L210 vs L238 (PS2 ≥ 2라고 해 놓고 PS2 = 1로 계산)
- **규칙.** '조건 X에서의 한계'는 X가 허용하는 구성을 모두 열거해서 구하거나, 추가로 고정한 값을 숫자가 반복되는 모든 곳(Q 답변·함정·정리)의 X에 적는다. 가정 밖에서 구한 값은 같은 문장에 '가정 X 밖의 상한'이라고 붙인다.
- **확인.** 한계 수치가 나오는 모든 문장에서 조건 목록을 대조하고, 계산에 쓴 값이 선언한 가정 범위 안에 있는지 본다.

### AP-C-03 완전히 열거하지 않고 완전성을 주장함
- **문제.** '경계 표', 'N가지', 'CAN 2.0 준수' 같은 표현은 빠진 것이 없다는 뜻인데, 실제 열거나 확인은 빠진 행·분기·조항·경로가 있다.
- **예.** `part1-10-can-electrical.md` L216·L229 (지배되지 않는 행 누락) · `part7-13-irq-affinity.md` L92 ('조건은 네 가지', `no_irq_affinity` 분기 누락) · `part1-10-can-electrical.md` L169-176 ('분할 규칙' 열의 'CAN 2.0·Hartwich'는 PHASE_SEG2 조항만 확인했고, 같은 규칙의 PROP_SEG 1..8은 모든 행이 넘음) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L348-355 (hotplug 뒤 affinity 손실 대책으로 udev KOBJ_ONLINE 규칙만 제시, uevent가 없는 suspend/resume 경로는 빠짐) (파일럿 2, 2026-10-11)
- **규칙.** 열거 표는 스크립트로 만들고, 정의역과 필터를 본문에 적고, 출력과 diff한다. 'N가지'는 인용한 함수의 분기를 전부 셌을 때만 쓰고, 아니면 개수 없이 나열한다. 준수 라벨은 이름 댄 규칙의 조항을 모두 확인했을 때만 붙이고, 아니면 확인한 조항을 적는다(예: 'PHASE_SEG2 규칙'). 커널 상태 변화에 대한 대책은 그 변화를 일으키는 함수의 호출자를 모두 grep해 경로를 열거하고(예: `_cpu_down`을 거치는 `migrate_one_irq`), 대책이 덮는 경로와 덮지 못하는 경로를 적는다.
- **확인.** 'N가지', '모든', '경계', '전부'를 grep해서 근거 열거와 개수를 대조한다. 준수 라벨이 붙은 열마다 규칙의 조항 목록과 대조한다. 대책 문장마다 원인 경로 목록이 있는지 본다.

### AP-C-04 코드 경로를 끝까지 따라가지 않은 동작 주장
- **문제.** 함수 조각이나 문서 문장을 읽고 동작을 추론해, 출처를 단 채 틀린 예시나 메커니즘을 쓴다. 필드나 함수 이름만 대고 효과를 쓰지 않거나, 코드 조건을 '처음' 같은 시간 표현으로 줄여 실제 동작을 가린다. 고쳐 쓴 문장이 새로운 오류가 되기도 한다.
- **예.** `part7-13-irq-affinity.md` L264 (hotplug 마스크를 복사하는 시점 오독) · 같은 글 L221 (taskset 덮어쓰기, 실제로는 `sched_setaffinity`가 EINVAL) · 같은 글 L209 (고쳐 쓰며 ONESHOT 조기 반환을 빠뜨림) · 같은 글 L77 ('첫 CPU를 redirect 대상으로 저장'만 쓰고, 그 값을 읽는 `demux_redirect_remote`가 핸들러를 어디서 돌리는지는 안 씀) (파일럿 2, 2026-10-11) · 같은 글 L179 ('처음 시작할 때', 실제 조건은 IRQ가 시작되지 않은 상태라 shutdown 뒤 재요청에도 기본 마스크가 다시 적용됨) (파일럿 2, 2026-10-11)
- **규칙.** 코드에서 끌어낸 예시는 단계마다 구체 값(어느 마스크를, 언제, 어떤 호출 순서로)을 추적하고 각 단계를 인용한다. 사용자 공간 명령에 대한 주장은 시스콜 진입점과 커널 쪽 처리를 모두 확인한다. 주기 데몬은 '평가 주기'와 '쓰기 주기'를 나누고 쓰기 조건이 있는 함수를 인용한다. 문서와 코드가 다르면 코드 동작을 쓴다. 이름을 댄 커널 필드·함수는 관찰 가능한 효과를 한 문장으로 함께 쓰고, 저장되는 값은 그 값을 읽는 쪽까지 따라간 뒤 동작을 쓴다. 트리거는 '처음·한 번' 같은 서수어가 아니라 코드의 조건(상태 전이, 플래그)으로 쓴다. 고쳐 쓴 문장은 새 주장으로 보고 따로 출처를 단다.
- **확인.** 출처 링크가 그 문장 자체를 뒷받침하는지(옆 함수가 아닌지) 본다. 열거한 경우마다 조기 반환을 포함한 제어 흐름을 따라간다. '처음·한 번·다시' 같은 시간 표현을 grep해서 코드의 조건과 같은지 본다.

### AP-C-05 근거 범위와 주장 범위가 다름
- **문제.** 드라이버 하나, 기본 플래그 하나, 브랜치 하나에서 본 사실을 하드웨어군·파라미터군·릴리스 전체로 넓힌다. 거꾸로 일반 값을 특정 부품의 결과처럼 붙이거나, 일부 출처만 보고 '어느 자료에도 없다'고 쓴다.
- **예.** `part7-13-irq-affinity.md` L67 (GICv3 ITS 동작을 'arm64 SoC 전체'로) · 같은 글 L129·L175 (`isolcpus=`가 플래그와 관계없이 `isolated`를 채운다고 가정) · 같은 글 L245 (master grep을 '1.9.5 소스에는 없다'로) · `part1-10-can-electrical.md` L5·L101·L287 (SLLA270의 일반 CAN 컨트롤러 지연으로 구한 결과를 title·description에서 STM32 bxCAN 결과로 제시) (파일럿 2, 2026-10-11) · 같은 글 L89 ('어느 자료에도 없습니다', 인용한 Hartwich §6에 노드 지연 정의와 58 ns 컨트롤러 예가 있음) (파일럿 2, 2026-10-11)
- **규칙.** 한 드라이버에서 읽은 주장은 그 드라이버가 다루는 하드웨어로 한정한다. 하위 도구가 읽는 커널 인터페이스는 글이 권하는 정확한 구성에서 커널이 무엇을 쓰는지 확인한다. 부재 주장에는 검색 범위(파일 종류, 태그)를 적고 태그된 릴리스 트리에서 검색한다. 일반 값은 표에 들어가는 자리에 일반 값이라고 적고('일반 컨트롤러 50-75 ns, SLLA270'), 그 부품 자료를 쓰지 않은 결과에 부품 이름을 붙이지 않는다. '어느 자료에도 없다'는 인용한 출처를 모두 다시 검색한 뒤에만 쓰고, 아니면 확인한 출처로 범위를 좁힌다('SLLA270에는 없다').
- **확인.** '모든/전체/없다' 주장마다 검색하거나 읽은 범위가 주장 범위와 같은지 대조한다. title·description의 부품 이름마다 그 부품 자료가 계산에 들어갔는지 본다.

## 2. 출처·인용

### AP-C-06 출처가 정한 양·규칙·절차에서 말없이 벗어남
- **문제.** 출처를 인용해 놓고 기준량을 비슷한 다른 양으로 바꾸거나, 공식만 가져오고 절차와 범위 규칙은 버린다. 출처가 붙어 있어 맞아 보이지만 출처와 어긋난다.
- **예.** `part1-10-can-electrical.md` L99-108 (PROP_SEG 대신 sample point) · 같은 글 L100 (지배 엣지 LOOP1 대신 큰 LOOP2) · 같은 글 L114 vs L204·L199 vs L221-227 (PROP_SEG 1..8 TQ, PS2 = max(PS1, IPT) 위반)
- **규칙.** 판정 기준은 출처가 지목한 양 그대로 쓴다. 단순화하거나 여유값을 쓰면 그렇다고 밝히고 오차 방향과 원래 기준의 결과를 함께 적는다. 인용한 절의 수치 제약은 글의 모든 예제와 대조하고, 벗어난 예제는 사용하는 자리에서 밝히고 근거를 단다. 출처가 공식과 절차를 함께 주면 절차를 따르거나 이탈 이유를 적는다.
- **확인.** 인용한 절을 다시 열어 정의·범위·권장 절차를 뽑고, 본문 계산과 예제가 그 안에 있는지 확인한다.

### AP-C-07 출처의 조건·한정어·범위를 잘라냄
- **문제.** 데이터시트 조건, 표의 일부 행, 조건 목록 일부, '(preview)' 같은 성숙도 표시, 문서 제목을 잘라 옮겨 원문과 다른 뜻이 된다. 정리에서 조건부 메커니즘을 무조건 문장으로 줄이기도 한다. 반대로 '제목 절단' 지적을 고치려고 무엇의 제목인지 확인하지 않은 문자열을 통째로 인용한다.
- **예.** `part1-10-can-electrical.md` L43-44·L148·L248 (±20 V 행만 옮기고 요약에서 VCM 조건 삭제) · `part12-01-edge-inference.md` L101 (ORT 목록 일부를 전체처럼) · 같은 글 L177 (TensorRT sparsity 조건 중 2:4 zero와 `kSPARSE_WEIGHTS`만 옮기고 정밀도·레이어 종류·GPU 세대 조건은 뺌) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L331 (DWC MSI 정리 불릿 'parent IRQ를 따라갑니다', 본문의 redirect 조건이 빠져 한 분기에서 거짓) (파일럿 2, 2026-10-11) · `part1-10-can-electrical.md` L187 (파일럿 1의 CiA 601-3 '제목 절단' 지적을 고치며 목록 라벨을 그대로 인용했는데, 그 라벨은 문서가 아니라 평가 도구 첨부의 제목) (파일럿 2, 2026-10-11)
- **규칙.** 표는 조건 헤더를 그대로 옮기고, 글이 다른 곳에서 주장하는 범위를 다루는 행은 모두 포함한다. 요약에서 같은 값을 다시 말할 때도 조건을 달아 둔다. 목록과 조건 목록은 전부 옮기거나 '중 일부'라고 쓰고, 한정어(preview, deprecated, 버전)는 남긴다. 정리 불릿은 쓰거나 줄일 때 1차 자료로 따로 다시 확인하고, 코드의 분기 조건(if/else)을 남기거나 그 항목을 불릿에서 뺀다. 제목은 그대로 인용하거나 생략 부호를 쓴다. 목록 항목을 인용하기 전에 그 문자열이 어느 대상의 제목인지 확인하고, 글의 질문 밖 항목이면 다듬지 말고 지운다.
- **확인.** 인용 표·목록을 출처와 행 단위로 diff한다. 요약·정리 문장의 값과 메커니즘에 본문의 조건이 남아 있는지 본다.

### AP-C-08 판·버전이 고정되지 않은 출처
- **문제.** 본문은 버전을 적는데 링크가 master를 가리키거나, 구판 표준을 2차 자료로 옮기면서 판을 밝히지 않거나, '모든 링크가 태그를 가리킨다'는 문장이 사실이 아니다.
- **예.** `part1-10-can-electrical.md` L103·L147·L225 (v7.3-rc6라 쓰고 master 링크)·L28 외 (SLLA270이 다루는 ISO 11898:1993 한계를 현행처럼 씀) · `part7-13-irq-affinity.md` L28 (태그 고정 메타 문장, 미고정 링크 약 7개)·frontmatter L4 (4월 날짜 글이 10월 rc 인용) · `part12-01-edge-inference.md` L148·L321 (Vela main, '2026-10-10 기준 upstream')
- **규칙.** 저장소 링크는 본문이 말한 태그(`/blob/<tag>/`)로 고정하고, 본문에 커밋 해시는 쓰지 않는다. 개정 표시가 없는 페이지는 그렇다고 적는다. 표준에서 온 한계에는 판을 붙이고, 현행판보다 오래된 2차 자료는 그렇게 표시하거나 현행 1차 문서로 확인한다. 'X 기준으로 확인'은 `git describe --exact-match`로 태그를 확인한 뒤에 쓴다. 더 새 upstream으로 재검증했으면 `date`는 두고 `lastVerified:`를 쓴다.
- **확인.** 본문의 1차 자료 링크 중 `master`/`main`/버전 없는 URL을 grep한다. 출처 고정 메타 문장이 있으면 모든 링크를 그 문장과 대조한다.

### AP-C-09 출처에 있는 값을 TBD로 둠
- **문제.** 같은 행에 링크한 페이지에 값이 있는데 '공개된 값이 없다'며 TBD로 둔다. 출처에 대한 거짓 진술이다.
- **예.** `part12-01-edge-inference.md` L123 (Alif E7 메모리 칸)
- **규칙.** TBD는 인용한 페이지를 처음부터 끝까지 다시 읽고 그 항목을 찾은 기록을 수정 보고에 남긴 뒤에만 쓴다.
- **확인.** 표의 TBD 칸마다 같은 행 링크를 열어 해당 항목을 검색한다.

### AP-C-27 출처끼리, 또는 출처와 자기 계산이 어긋나는데 맞추지 않음
- **문제.** 예산은 출처 X에서, 판정 기준은 출처 Y에서 가져오면서 두 출처가 같은 항을 다르게 센다는 것을 말하지 않는다. 인용한 1차 자료 둘이 같은 파라미터에 다른 규칙을 주는데 한쪽만 쓰거나, 한 출처의 한정어를 다른 출처에 붙인다. 자기 계산이 인용 출처의 대표 수치를 뒤집는데 그 수치를 언급하지 않거나, 글의 모델과 맞지 않는 upstream 예시를 인용한다. 출처를 연 독자는 설명 없는 모순을 본다.
- **예.** `part1-10-can-electrical.md` L108 vs L128 (SLLA270 예산은 컨트롤러 지연을 한 번, Hartwich 조건은 노드마다 세어 길이가 5-7.5 m 낙관적일 수 있음) (파일럿 2, 2026-10-11) · 같은 글 L86-96·L225·L287 (SLLA270은 ISO 11898이 40 m에서 1 Mbps를 규정한다고 하는데, 글은 그 문장을 인용하지 않고 40 m 불가로 결론) (파일럿 2, 2026-10-11) · 같은 글 L195·L207-216 (홀수 분할은 Hartwich에서 가져왔는데, 인용한 CAN 2.0은 PHASE_SEG2 = max(PHASE_SEG1, IPT)라 'Hartwich (홀수)' 행 몇 개가 CAN 2.0 문자 그대로는 아님) (파일럿 2, 2026-10-11) · 같은 글 L152 ('최소 프로그래밍 범위'는 Hartwich 표 1의 표현인데 CAN 2.0에 귀속) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L99 vs L83 (IO-APIC 문서 예시는 IRQ 하나를 CPU 4개에 분산, 본문은 x86이 CPU 하나를 고른다고 함) (파일럿 2, 2026-10-11)
- **규칙.** X의 예산과 Y의 기준을 합치면 각 항이 Y의 정의에 어떻게 대응하는지 한 문장으로 적고, 다르면 결과가 얼마나 바뀌는지 준다. 인용한 1차 자료 둘이 같은 파라미터에 다른 규칙을 주면 둘 다 보이고 각 행을 양쪽 규칙에 대해 표시한다. 인용 문장의 한정어(최소·최대·권장·전형)는 그 문장이 이름 댄 출처에 있어야 하고, 아니면 그 표현이 있는 출처를 인용한다. 자기 계산이 인용 출처의 수치를 뒤집으면 그 수치를 판정 옆에 인용하고 달라진 입력(부품 최대 지연, 컨트롤러 수, 레지스터 폭)을 적는다. upstream 예시는 출력이 글의 메커니즘과 맞을 때만 쓰고, 아니면 차이를 설명하거나 뺀다.
- **확인.** 출처가 둘 이상 들어간 계산마다 항별 출처를 적어 대조한다. 판정 수치를 인용 출처의 대표 수치(제목·요약·표 값)와 비교한다. 인용 문장의 한정어를 이름 댄 출처에서 검색한다.

## 3. 완곡·단정

### AP-C-10 수치 대신 방향·완곡 문장
- **문제.** 근거 없는 수치를 지운 자리, 또는 계산할 입력이 본문에 이미 있는 자리를 '줄여야 한다', '측정해서 정한다', '이 값을 기준으로 정한다' 같은 문장이 채운다. 독자의 질문이 반쯤만 답해진다.
- **예.** `part1-10-can-electrical.md` L108·L122·L143 · `part7-13-irq-affinity.md` L237 · `part12-01-edge-inference.md` L40·L91·L93·L210·L306
- **규칙.** 입력이 본문에 있으면 값을 계산해 보인다(예: ≈32 m). 출처를 못 찾은 수치는 문장째 지우거나 TBD로 둔다. '확인합니다/측정합니다/정해야 합니다'로 바꾸지 않는다. 비교 글이면 비교하는 쪽마다 1차 자료로 확인한 정량 값을 하나 이상 둔다.
- **확인.** 수정 diff에서 지운 숫자 자리에 '-야 한다/제한된다/확인합니다/측정합니다'로 끝나는 문장이 새로 생겼는지 본다.

### AP-C-11 권고·추론을 단정 사실로 승격
- **문제.** 출처의 '권고'를 '제약'으로 바꾸거나, 출처에 없는 해설을 덧붙이거나, 본문에서 추론이라고 밝힌 값이나 출처가 말하지 않은 해석에 기댄 값을 정리·description에서 무조건 사실처럼 쓰거나, 측정하지 않은 원인을 실행 결과에 붙인다.
- **예.** `part1-10-can-electrical.md` L152 ('0.3 m가 실제 제약') · `part12-01-edge-inference.md` L171·L700 ('dense 값과 일치'를 사실로) · 같은 글 L571 (측정 안 한 원인 설명) · `part1-10-can-electrical.md` L101 → L287 (컨트롤러 지연을 두 번 세는 해석이 모든 수치에 퍼져 '어떤 클록으로도 불가'라는 무조건 결론이 됨, 한 번 세면 795 ns로 여전히 불가) (파일럿 2, 2026-10-11) · `part12-01-edge-inference.md` L173 → L704 (Alif GOPS를 dense/INT8로 가정한 162배가 정리에 다시 나옴, 파일럿 1의 L168·L939 지적 뒤 재발) (파일럿 2, 2026-10-11)
- **규칙.** 출처의 양상(recommends / shall / typical)을 유지한다. 출처가 말한 것만 바꿔 쓴다. 결론이 출처가 말하지 않은 가정에 기대면 그 가정을 결론 문장에 넣고, 다른 가정에서의 결과도 보인다. 판정이 뒤집히면 뒤집히는 지점을 적는다. 그런 가정에 기댄 파생 수치는 가정 옆 본문에만 두고 정리·한 줄 요약·description에 다시 쓰지 않는다(라벨을 달아 옮기는 것도 하지 않는다). 런타임 동작의 원인은 계측한 출력이나 1차 자료가 있을 때만 쓴다.
- **확인.** 정리·한 줄 요약·description의 문장마다 본문 출처 문장으로 거슬러 올라가, 양상이 같은지, 거기 있는 파생 수치가 출처에 없는 가정에 기대지 않는지 대조한다.

### AP-C-12 출처 없는 한정·빈도 부사
- **문제.** '흔히', '만', '뿐', '항상', '모든', '없다' 같은 단어 하나가 출처에 없는 새 주장을 만든다. 코드에 대한 '만·뿐·없다'는 호출자 하나만 따라가고 쓰기 쉬운데, 놓친 참조 하나로 거짓이 된다.
- **예.** `part12-01-edge-inference.md` L99-104·L568 ('흔히 새는 것') · 같은 글 L187 ('EP 목록만 바꿀 수 있습니다') · `part7-13-irq-affinity.md` L195·L360 (`irq_startup` → `irq_setup_affinity` 하나만 따라가 기본 마스크를 거기서만 읽는다고 씀, `desc_smp_init`도 `irq_default_affinity`를 읽음) (파일럿 2, 2026-10-11) · 같은 글 L177·L274·L318 ('하나뿐', '읽는 코드가 없습니다', '에서만', L318은 `add_cpu`도 `device_online`을 불러 이미 틀림) (파일럿 2, 2026-10-11)
- **규칙.** 빈도 부사는 지우거나 사례·보고서를 인용한다. '만·뿐·항상·모든·없다'는 그 자체에 출처가 있어야 한다. 코드에 대해 '만·뿐·없다·한 번'을 쓰려면 고정한 태그 트리 전체에서 심볼의 참조를 모두 grep하고(예: `irq_default_affinity`는 `manage.c`·`irqdesc.c`·`proc.c`), 읽는 쪽을 모두 인용하고, 검색 범위를 본문에 적는다. 전체 검색을 하지 않았으면 실제로 확인한 긍정 사실로 다시 쓴다.
- **확인.** 수정 diff에서 '흔히·흔한·대부분·만 ·뿐·항상·모든·반드시·없습니다'를 grep한다. 코드에 대한 한정어마다 수정 보고에 `git grep <심볼>` 결과가 있는지 본다.

### AP-C-13 문장 구조가 결론을 뒤집거나 거짓 추론을 유도함
- **문제.** 방향이 모호한 부정, 또는 '도/역시' 같은 연결어가 판정을 뒤집거나 확인하지 않은 추론을 독자에게 넘긴다.
- **예.** `part1-10-can-electrical.md` L195 ('어떤 길이도 엄격한 선을 넘지 못합니다') · `part7-13-irq-affinity.md` L187 ('IRQF_TIMER … 도 hardirq로 남습니다')
- **규칙.** 예산 판정은 '만족한다/만족하지 못한다' 또는 'X ns > Y ns'로 쓴다. 제외 항목을 나열한 뒤에는 각각의 런타임 결과를 따로 쓰고, 연결어로 주장을 넘기지 않는다.
- **확인.** 판정 문장에서 '넘다/못하다' 조합, 나열 직후의 '도/역시'를 찾아 읽는다.

## 4. 측정·실행 결과

### AP-C-14 개발 머신에서 돌린 결과를 글에 넣음
- **문제.** 개발 머신에서 실행한 출력은 하네스·원본 로그·실행 횟수·같은 실행 여부를 갖추기 어렵고, 다시 돌리면 값이 바뀐다. 독자는 재현할 수 없고 검토자는 조작된 숫자와 구별할 수 없다.
- **예.** `part12-01-edge-inference.md` L328-333 (하네스 없는 NEON 표)·L438-451 (원본 로그 없음)·L548 (3회 실행 범위, 재실행 119.1 ms)·L296·L680 (출력하지 않은 실행의 범위)·L517 (다른 실행끼리 비교)
- **규칙.** **운영자 결정 2026-10-11 (a):** 개발 머신에서 프로그램을 돌려 얻은 결과는 글에 넣지 않는다. 수치가 필요하면 1차 자료의 공개 값을 인용하고, 그런 값이 없으면 문장을 지우거나 TBD로 둔다. 독자가 직접 돌릴 수 있는 절차와 코드는 남겨도 된다.
- **확인.** '실행 결과', '측정했다', 출력 블록, ms·µs·FPS 수치를 grep해서 출처가 1차 자료인지 본다.

## 5. 구조·내비게이션

### AP-C-15 글이 약속한 것을 본문·코드가 하지 않음
- **문제.** 도입부의 '이 글은 X를 보인다'나 기록 표의 단계를 본문이나 코드가 실제로 하지 않는다.
- **예.** `part12-01-edge-inference.md` L106 → L568 (코드·빌드 설정을 약속하고 체크리스트로 끝남)·L122-164 vs L179·L168 (표의 warm-up, V4L2 t_start가 코드에 없음)
- **규칙.** 'X를 보인다'는 문장마다 X가 있는 절을 가리킬 수 있어야 하고, 없으면 문장을 지운다. 본문이나 표에 이름이 나오는 절차 단계는 코드에 있거나 '독자 확장'으로 표시한다.
- **확인.** 도입·description의 약속 목록과 절 목록을 대조하고, 표의 단계 이름을 코드에서 검색한다.

### AP-C-16 수정한 뒤 요약·설명·같은 주장의 다른 문장을 맞추지 않음
- **문제.** 표나 본문 한 곳만 고치고, 같은 숫자나 주장을 반복하는 산문·함정·정리·한 줄 요약·description은 옛 내용 그대로 둔다. 숫자뿐 아니라 주장의 출처·라벨·범위를 바꿨을 때도 같은 일이 생긴다. 글이 스스로 모순되고, rubric 3-1은 내부 모순을 오류 확인으로 보아 점수와 관계없이 우선 조치로 보낸다.
- **예.** `part1-10-can-electrical.md` L195 vs L192 (표는 39.7 m, 산문은 40 m 통과) · 같은 글 L15 vs L210-224 (한 줄 요약) · `part7-13-irq-affinity.md` L57 vs L296 (EOVERFLOW 범위) · `part12-01-edge-inference.md` L5 vs L41-45 ('결정 표'가 불릿으로 바뀜) · `part1-10-can-electrical.md` L231 vs L308 (본문은 14+2+4가 어느 규칙도 따르지 않는다고 재분류했는데 정리는 여전히 'Hartwich 설정 순서로 고른 한계') (파일럿 2, 2026-10-11)
- **규칙.** 결론·수치·구조·출처 귀속·라벨·범위를 바꿨으면 같은 라운드에서 옛 숫자와 옛 표현을 글 전체에서 grep하고, 한 줄 요약·함정·정리·수정 이력·description·title을 다시 읽어 맞춘 뒤에 보고한다.
- **확인.** 수정 diff에서 바뀐 숫자·용어·출처 이름 목록을 만들어 수정 후 본문 전체를 grep한다.

### AP-C-17 편집이 문단 맥락과 참조를 흐림
- **문제.** 본문의 절 번호와 인용 문서의 절 번호가 한 문단에 섞이거나, 인용을 고치면서 문장을 상관없는 문단에 끼워 넣는다.
- **예.** `part1-10-can-electrical.md` L56·L89·L134·L140·L178·L196 ('4절'과 'SLLA270 4.9절')·L35 (CANopen/DeviceNet 문장)
- **규칙.** 외부 문서의 절 번호를 인용하는 글에서는 본문 절을 번호가 아니라 제목이나 앵커 링크로 가리킨다. 인용은 제자리에서 고치거나 그 주제를 다루는 절로 옮기고, 문단의 주제문이 여전히 성립하는지 확인한다.
- **확인.** 'N절'을 grep해서 대상이 본문인지 외부 문서인지 구별되는지 본다. 수정으로 들어간 문장이 문단 주제와 맞는지 읽는다.

## 6. 중복·범위

### AP-C-18 형제 글의 모순을 그대로 둠
- **문제.** 한 글에서 사실을 고쳤는데 같은 주장이 형제 글, 선수 글, 다른 시리즈에 남는다. 두 글을 '충돌'로만 적고 어느 쪽이 맞는지 판정하지 않거나, 형제 글을 '다음 패스'로 미루면 틀린 쪽이 계속 발행된다.
- **예.** `part1-10-can-electrical.md` L103·L160 vs `part5-10-can-communication.md` L61·L287·L297 (87.5%) · 같은 쌍 (part1-10 L107은 Linux CiA 표의 '800 kbit/s 초과 75%'로 고쳤는데, 형제 글은 '87.5% 권장'을 '별도 패스'로 미뤄 발행 상태로 남음) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L26·L334·L335 (선수 글 RTOS 5-07이 taskset 권장) · `part12-01-edge-inference.md` L131·L162 vs part12-02 L46·L192
- **규칙.** 사실을 고친 뒤 같은 주장 문자열을 사이트 전체에서 grep한다. 모순이 있으면 1차 자료로 어느 쪽이 맞는지 정하고 같은 라운드에서 형제 글을 고친다. 같은 라운드에 고치지 못하면 확인된 오류 문자열을 `data/known-falsehoods.yaml`에 반드시 등록하고 형제 글을 다음 루프 대상에 올린다. `시리즈 공통 문제` 기록만으로 닫지 않는다.
- **확인.** 수정 보고에 grep 범위와 결과가 있는지 본다. 형제 글이 그대로면 `known-falsehoods.yaml`에 그 문자열이 있는지 보고 `npm run audit:falsehoods`를 돌린다.

### AP-C-19 지적된 한 건만 고침
- **문제.** 평가자가 이름을 댄 사례 하나만 고치고, 같은 유형의 다른 사례(넓은 표, 완곡 표현, 형제 글과 겹치는 함정 항목)는 남긴다. 한 행의 수치를 다시 출처 잡으면서 같은 행의 분류 라벨은 두기도 한다. 다음 라운드에서 같은 지적이 다시 나온다.
- **예.** `part12-01-edge-inference.md` L43·L151·L545 (넓은 표 하나만 분할) · `part1-10-can-electrical.md` L238-240 vs `part5-10-can-communication.md` L270 (중복 함정 하나만 제거) · `part12-01-edge-inference.md` L131·L173 (Alif 페이지로 수치는 모두 다시 잡았지만, 같은 페이지가 반박하는 'MCU' 분류는 그대로. E7은 MMU가 있는 Cortex-A32 두 개를 가짐) (파일럿 2, 2026-10-11)
- **규칙.** 지적을 유형으로 읽는다. 같은 유형을 글 전체에서 찾아 같은 라운드에 모두 고치고, 형제 글과 중복을 정리할 때는 함정·주의 항목을 전부 대조해 겹치는 것을 링크로 바꾼다. 표의 행을 다시 출처 잡을 때는 수치만이 아니라 범주 라벨까지 같은 1차 자료로 확인한다.
- **확인.** 지적 유형별로 수정 전후 개수를 센다(예: 열이 5개 이상인 표의 수). 다시 출처 잡은 행마다 라벨 칸도 출처와 대조했는지 본다.

## 7. 분량·질

### AP-C-20 단일 출처를 바꿔 써서 절을 채움
- **문제.** 절 전체가 한 앱 노트나 문서를 단락별로 다시 쓴 것이다. 정확도는 오르지만 원래 가치(A)는 그대로이고, 글이 출처 요약처럼 읽힌다. 라운드마다 일부를 줄여도 글의 질문에 답하지 않는 재진술 절과 문장이 남는다.
- **예.** `part1-10-can-electrical.md` L56-75 · 같은 글 L112-134 · 같은 글 L55-59·L77-82·L141·L143-161 (라운드마다 줄였지만 앱 노트·데이터시트 재진술 절이 남음) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L42·L59·L157·L320 (호출 사슬은 지웠지만 문서·man page를 바꿔 쓴 문장은 남음) (파일럿 2, 2026-10-11)
- **규칙.** 한 출처로 만든 절에는 출처에 없는 계산이나 판단을 하나 이상 넣는다(예: 글에서 고른 트랜시버의 tR/tF에 출처 규칙을 적용해 stub 길이 계산). 라운드를 닫기 전에 H3마다 '이 글이 답하는 질문' 불릿 하나에 대응시키고, 대응이 없는 절은 지우거나 그 질문을 목록에 명시한다. 출처를 인용하는 문장마다 독자가 할 일을 바꾸는지 묻고, 아니면 문장을 지우고 링크는 주장이 필요한 자리에만 남긴다.
- **확인.** 절마다 인용 출처가 하나뿐인지, 출처에 없는 계산·결정이 있는지 본다. H3 목록과 질문 목록의 대응을 적어 본다.

### AP-C-21 점수를 올리려고 분량을 늘림
- **문제.** 루브릭 점수를 올리려고 문단·표·예시를 덧붙이거나, 두 질문을 한 글에 몰아 글을 키운다. 질이 아니라 길이가 늘어난다.
- **예.** 파일럿 루프 1·2에서 이 항목 그대로의 사례는 없다. 운영자 결정으로 미리 둔 규칙이다. 지적에 답하며 늘어난 경우는 AP-C-25, 반복으로 늘어난 경우는 AP-C-26을 본다.
- **규칙.** **운영자 결정 2026-10-11 (b):** 길이보다 질이다. 고정된 길이 상한은 없고, 점수를 올리려고 내용을 덧붙이지 않는다. 한 글이 두 질문을 다뤄야 하면 늘리지 말고 분할을 제안한다. 분할 여부는 운영자가 정한다.
- **확인.** 수정 diff에서 줄이 크게 늘었으면 새 문단마다 독자 질문에 답하는지 본다. 한 줄 요약이 질문 두 개를 담으면 분할 제안으로 돌린다.

### AP-C-25 출처·검증 과정을 독자용 산문으로 풀어 씀
- **문제.** 평가자의 출처 지적에 답하려고 어느 규칙·문서가 무엇을 말하는지 해설하는 문단을 본문에 더하거나, 커널 함수 호출 사슬(A가 B를 부르고 B가 C를 설정해 D가 실패)을 한 단계씩 서술하거나, 편집 과정을 수정 이력에 적는다. G는 조금 오르지만 군더더기가 늘어 A·B·F가 내려가고 결론이 묻힌다. 라운드마다 단계가 늘어난다.
- **예.** `part1-10-can-electrical.md` L199·L231·L326 (출처 해설 문단, L231은 AP-C-16 모순을 만듦) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L125·L145·L180·L244·L327·L338 (중간 커널 함수를 모두 나열한 호출 사슬) (파일럿 2, 2026-10-11) · `part12-01-edge-inference.md` L711-712 ('개발 머신 출력 삭제', 'TRM을 다시 열 수 없음' 같은 작업 메모가 수정 이력에 있음) (파일럿 2, 2026-10-11)
- **규칙.** 출처는 인용 괄호, 표의 열, 참고 자료에 둔다. 출처 해설 문단은 독자의 결정이 그 출처 차이에 달려 있을 때만 쓴다. 본문에는 관찰 가능한 결론과 그것을 정하는 함수·파일 하나의 링크를 두고, 전체 호출 사슬은 커밋 본문이나 팩트체크 보고에 둔다. 수정 이력에는 주장을 바꾼 내용 수정만 적는다(옛 값 → 새 값, 출처). 과정 메모는 커밋 본문에 쓴다.
- **확인.** 수정 diff의 새 문단이 출처 이름이나 함수 이름으로 시작하는지, 한 문장에 함수 이름이 셋 이상 나오는지 본다. 수정 이력에 '삭제·다시 열 수 없음·검증' 같은 과정 단어가 있는지 grep한다.

### AP-C-26 같은 결론·수치를 본문·함정·정리에 되풀이함
- **문제.** 라운드마다 바뀐 본문 수치와 판정을 함정·정리에도 덧붙이고, 지적받은 자리에 판정을 다시 쓰면서 앞의 사본은 지우지 않는다. 함정이 본문 절을 거울처럼 따라가고 정리가 절 목록이 된다. 길이만 늘고, 사본마다 맞춰야 할 자리가 생기며(AP-C-16), 글마다 같은 골격이 반복돼 rubric 3절의 scaled content 신호와 A·B·D 감점이 된다.
- **예.** `part1-10-can-electrical.md` L116·L192-196·L228·L254 (같은 판정이 네 절에) (파일럿 2, 2026-10-11) · 같은 글 L280-311 (함정·정리에 본문 수치가 라운드마다 쌓임) (파일럿 2, 2026-10-11) · `part7-13-irq-affinity.md` L298-323 vs L59·L65·L79·L133·L156·L178 (함정이 본문 절을 되풀이) (파일럿 2, 2026-10-11) · 같은 글 L351-358 (정리 불릿 8개가 절 목록) (파일럿 2, 2026-10-11) · `part12-01-edge-inference.md` L665-707 (함정·정리가 본문 유도와 수치 목록을 다시 씀) (파일럿 2, 2026-10-11)
- **규칙.** 결론 하나는 한 절에만 둔다. 다른 자리에서는 그 절을 이름으로 가리키거나 그 자리의 국소 수치(예: 이 BTR의 PROP_SEG = 643 ns)만 쓰고 다시 판정하지 않는다. 함정은 본문이 다루지 않은 증상이나 메커니즘이 있을 때만 두고, 아니면 한 줄 증상과 본문 절 포인터로 줄인다. 정리는 독자가 가져갈 결정 3-4개로 쓰고, 불릿마다 핵심 수치는 하나까지, 새 조건은 넣지 않는다.
- **확인.** 정리 불릿 수와 불릿별 숫자 수를 센다. 함정 항목마다 본문에 같은 메커니즘이 있는지 찾는다. 판정 문장(만족·불가·통과)을 grep해서 같은 판정이 몇 곳에 있는지 센다.

### AP-C-28 기준을 고르지 않고 변형을 모두 나열함
- **문제.** 해석이 갈리는 선택마다 모든 조합을 남겨 고르는 일을 독자에게 넘긴다. 독자는 같은 양의 수치를 열 개쯤 받고, 판정을 말하려면 분기 나무가 필요하다. 글이 스스로 틀린 파라미터라고 한 변형이 기준이 되기도 한다.
- **예.** `part1-10-can-electrical.md` L91-99·L116·L178·L190-196·L228 (LOOP1/LOOP2 × 컨트롤러 지연 한 번/두 번 × typ/max × PHASE_SEG2 ≥ 1/≥ 2를 모두 유지해 왕복 지연 수치가 약 10개) (파일럿 2, 2026-10-11)
- **규칙.** 인용한 1차 자료가 뒷받침하는 변형을 기준으로 쓴다(여기서는 엣지에 맞는 LOOP1과 Hartwich의 두 노드 공식). 나머지 변형은 길이가 얼마나 바뀌는지 민감도 문장 하나로 준다. 글이 틀렸다고 한 파라미터를 기준으로 삼지 않는다.
- **확인.** 같은 양(왕복 지연, 최대 길이)에 서로 다른 값이 몇 개 나오는지 센다. 셋 이상이면 기준 하나와 민감도 문장 하나로 줄일 수 있는지 본다.

## 8. 검증·평가 절차

### AP-C-22 요약형 fetch로 표 수치를 확인함
- **문제.** 요약하는 웹 fetch가 병합 열(colspan) 표를 잘못 읽어, 맞는 값을 '틀렸다'고 하거나 틀린 열을 '확인'한다.
- **예.** `part12-01-edge-inference.md` 검증 과정 (Jetson AGX Orin 64GB를 Industrial 열 248 TOPS로, Orin Nano 8GB를 34/17로, QNN을 IoT 열로 보고. 원본 HTML은 275 TOPS, 67/33, GPU 열)
- **규칙.** 표 속 수치는 원본 HTML(curl과 셀 파서)이나 데이터시트 PDF로 열 헤더를 맞춰 확인한다. 출처 목록에 값과 함께 열 이름을 적는다.
- **확인.** 검증 기록에 원본 HTML 파싱이나 PDF 쪽수가 있는지 본다. 요약 fetch만 있으면 미검증으로 본다.

### AP-C-23 재현할 수 없거나 실제보다 강한 검증 기록
- **문제.** 존재하지 않는 clone 경로, 브라우저에서만 읽은 JS 렌더 문서, `cc -c`뿐인 '컴파일됨', 커밋하지 않은 수정, 수정 전 줄 번호처럼 검증 기록을 다시 따라갈 수 없거나 실제보다 강하게 적는다.
- **예.** `part1-10-can-electrical.md` 수정 보고 ('로컬 clone에서 git show', 경로 없음) · `part12-01-edge-inference.md` L130·L148·L155 (Ethos-U55 TRM, 저장한 trm.html이 비어 있음) · 같은 글 수정 보고 (pthread 파이프라인 'compiles'는 `-c`만) · 같은 글 작업 트리 (diff 503+/162-, 미커밋) · `part7-13-irq-affinity.md` 수정 보고의 'L195' 항목 (수정 전 줄 번호라 검증자가 문장을 바로 찾지 못함) (파일럿 2, 2026-10-11)
- **규칙.** 검증은 고정 태그·sha URL이나 실제로 쓴 로컬 경로로 커밋 본문에 남긴다(`06-remediation-evidence`). JS 렌더 문서는 인용 문구나 스크린샷 경로를 저장하고, 재현할 수 없으면 TBD로 둔다. 컴파일 검증은 모드(`-c` / 링크 후 실행)를 적는다. 검증한 수정은 출처를 커밋 본문에 적어 커밋한다. 수정 보고의 줄 번호는 수정 후 파일에서 다시 뽑거나, 바꾼 문장을 인용한다.
- **확인.** 기록된 경로·URL을 다시 열어 본다. `git status`로 미커밋 수정이 없는지 본다. 보고의 줄 번호 몇 개를 수정 후 파일에서 열어 문장이 맞는지 본다.

### AP-C-24 평가자가 rubric 상한을 넘겨 점수를 줌
- **문제.** 평가자가 rubric 3-1의 명시 상한이나 대역 문구의 조건을 적용하지 않고 기준 글(anchor) 점수를 따라간다. 합계가 80 경계를 넘고 상위 anchor 후보로 잘못 제안된다.
- **예.** `part7-13-irq-affinity.md` `## 효과 확인 절차` L269-282 (결과 없는 절차인데 C = 10, 세 관찰이 같은 건) · 같은 글 평가 (C = 10·11, F = 9. F 9-10의 '모바일 포함 읽기 쉬움'을 확인하지 않았고, 합계가 80을 넘어 상위 anchor 제안까지 감, 관찰 3건) (파일럿 2, 2026-10-11)
- **규칙.** 대역 표와 anchor보다 먼저 rubric 3-1의 명시 상한을 적용한다(절차만 있으면 C ≤ 9, 출처·환경 없는 수치는 C ≤ 8). F·E는 대역 문구의 조건(F 9-10은 모바일 가독성 확인)을 확인한 뒤에만 그 대역을 준다. C 근거에는 적용한 상한 조항을 인용한다. anchor가 상한을 넘을 수는 없다. 정리의 주장을 1차 자료로 다시 검증하기 전에는 80점 이상 anchor를 제안하지 않는다.
- **확인.** 평가 기록에서 상한 조건(절차만, 출처 없는 수치)에 해당하는 글의 C 점수와 상한 인용을 대조한다. F 9-10이면 모바일 확인 기록이 있는지 본다. 인용이나 기록이 없으면 평가를 다시 하게 한다.
